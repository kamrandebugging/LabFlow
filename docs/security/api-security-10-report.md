## Topic 1 — API1:2023 Broken Object Level Authorization (BOLA / IDOR)

### 1. Research

**What it is (OWASP).** An endpoint takes an object ID from the client (path, query, body, header) and acts on it without checking the caller may access *that specific object*. Authentication ("logged in") and coarse role checks are not object checks. OWASP's canonical attack: `GET /api/orders/1042` → change the ID to `1043` → another customer's order is returned. OWASP rates API1 "easy to exploit, widespread and easy to detect". Real-world cases OWASP cites: a shop platform exposing revenue data for thousands of stores through a predictable URL pattern, and a carmaker API letting any user start/unlock a vehicle by supplying any VIN. Test: two accounts; replay A's request with B's token; any success is a failure — repeat for IDs in paths, query strings, bodies and headers.

**What "done" looks like (OWASP cheat-sheet level).** (1) An ownership/permission check in *every* function that loads an object by a client-supplied ID, ideally through one shared policy layer. (2) Scope the lookup inside the query itself (`WHERE id=? AND owner=?`, 404 if absent — never 403, so existence is not leaked; LabFlow's own Doc 03 P-7 anti-oracle rule matches this). (3) Bind the decision to subject + action + resource + **tenant** and intersect predicates. (4) Cover *every* data path — list, search, export, count, aggregate, direct-object read, and later update/delete (an authorized list does not authorize a later write). (5) UUIDs / unpredictable IDs are **not** a fix — IDs leak through logs, shared links and other responses. (6) Automated cross-account tests that fail the build on regression. (7) Fail closed — a missing filter is never an unrestricted result.

**Concrete LabFlow attack flows (the shape to test).** (a) A receptionist at branch B02 takes a sample UUID seen on a label/WhatsApp link from branch B03 and calls `GET /api/v1/samples/{id}/label`, `POST …/reject`, `POST …/recollect` — today these fetch unscoped. (b) The same receptionist takes a patient UUID learned from the cross-branch search (BS-4, designed to return other-branch identifiers) and creates an invoice for that patient at her own branch. (c) A technician at B02 swaps `report_id` in `POST /api/v1/reports/{id}/access-token` and mints a patient link for a B03 report, then sends it. (d) Any staff member swaps `invoice_id` in `POST /api/v1/invoices/{id}/payments` — this one is defended (scoped fetch), which is the control the other endpoints lack.

### 2. LabFlow current state (verified at 5e98a06)

**Tenant isolation — STRONG (the outer boundary works).** `TenantMainMiddleware` resolves the schema from the host (`backend/config/settings/base.py:77`); JWT auth validates the token's `tenant` claim against the request schema and rejects mismatch (`backend/apps/accounts/authentication.py:71-81`), then resolves the user inside that schema (`:75-81`). All PKs are UUIDs (`apps/accounts/models.py:20`, `apps/billing/models.py:27`, `apps/patients/models.py:23`). Cross-tenant tests exist (`backend/tests/test_cross_tenant_security.py`, `test_tenant_isolation.py`). **Cross-tenant BOLA via ID swap is therefore not the live risk; cross-*branch* BOLA inside one tenant is.**

**The good pattern exists — `scoped_to()` (Doc 04 §8.5).** `BranchScopedQuerySet.scoped_to(user)` filters to the caller's `staff_branch` assignments on OPEN branches only; Owner/Pathologist bypass as tenant-wide (`apps/branches/scoping.py:59-70`); `StaffUser.assigned_branch_ids()` is the scope source and `staff_user.branch` is explicitly "a display default and is never consulted here" (`apps/accounts/models.py:73-89`); `BranchScopedAPIView.get_scoped_queryset()` + `IsInBranchScope` permission (`apps/branches/scope_views.py:44-60`); structural guard TN-20 `assert_branch_scope_conformance` (`scope_views.py:150-…`). **Correctly scoped today:** patient list/detail/update/delete (`apps/patients/services.py:254` list, `:262-293` detail with explicit branch check + 404, `:370-…` delete); invoice list/detail/cancel/payment (`apps/billing/services.py:675` list, `:714` detail, `:753` cancel, `:470` payment — all `Invoice.objects.scoped_to(actor).get(pk=…)`); report list/detail/exceptions (`apps/reports/services_query.py:108` list, `:212` detail, `:376` exceptions); session revoke is scoped `WHERE user_id=:caller AND id=:sessionId` (`apps/accounts/auth_service.py:370-379`); idempotency replay is scope-aware (`apps/billing/services.py:310-360` — another branch's key returns 422, never their invoice); 404-not-403 anti-oracle is honoured in all scoped fetches.

## Topic 2 — API2:2023 Broken Authentication

### 1. Research

OWASP's official API2 page defines the risk as: "Authentication mechanisms are often implemented incorrectly, allowing attackers to compromise authentication tokens or to exploit implementation flaws to assume other user's identities temporarily or permanently." Exploitability **Easy**, prevalence **Common**, technical impact **Severe** (https://api-security.owasp.org/editions/2023/en/0xa2-broken-authentication/).

**Vulnerable if the API:** permits credential stuffing (brute force with a list of valid username/password pairs); permits brute force on one account without captcha/account lockout; permits weak passwords; sends auth tokens/passwords in the URL; allows email/password/sensitive changes without password confirmation; doesn't validate token authenticity; accepts unsigned/weakly signed JWTs (`{"alg":"none"}`); doesn't validate JWT expiry; uses plaintext/weakly hashed passwords; uses weak encryption keys; uses weak or predictable tokens.

**OWASP's example scenarios:** (1) A login endpoint rate-limited to 3 req/min is bypassed by batching many login mutations into a single GraphQL request — per-request limits that don't count *attempts* fail. (2) An account-email update (`PUT /account`) that doesn't require the current password lets a token thief start a password-reset flow to the attacker's email and take over the account.

**"Done" per OWASP (API2 "How to Prevent" + Authentication Cheat Sheet + REST Cheat Sheet):** know every auth flow (mobile/web/deep links); use standards, don't reinvent auth/token generation/password storage (OAuth is not authentication; OpenID Connect adds the identity layer; API keys are not user auth); treat forgot-password/reset endpoints exactly like login endpoints for brute-force, rate-limiting and lockout — stricter than regular API limits; require re-authentication for sensitive operations (email/2FA changes); implement MFA where possible; anti-brute-force mechanisms stricter than normal rate limits, plus account lockout/captcha and weak-password checks; JWTs: integrity-protected (signature/MAC, never `alg:none`), single pinned algorithm (RFC 8725), and validate `iss`, `aud`, `exp` (mandatory per RFC 9068 §2.2) — the REST Cheat Sheet adds: on explicit session termination, submit the token's `jti` to a denylist until expiry; generic error messages regardless of whether the user ID/password was wrong, the account doesn't exist, or it's locked (no enumeration, incl. timing); passwords: minimum length enforced (NIST SP 800-63B: <8 chars weak with MFA, <15 weak without; max ≥64 to allow passphrases), no composition rules, screen against common **and breached** passwords (e.g. HaveIBeenPwned), Argon2id-class storage, constant-time comparison, no periodic forced rotation; change-password requires current-password verification; all auth traffic over TLS only.

**Real-world analogues:** credential-stuffing waves against login endpoints with no lockout (OWASP's canonical case); the OWASP API9 scenario (a beta host running the same password-reset endpoint *without* the rate limiter, letting a researcher brute-force a 6-digit reset token and reset any password) is the textbook reset-flow failure; JWT `alg:none`/weak-secret forgeries are the canonical token-validation failure.

### 5. Residual risk

Even after all of the above: a stolen **access** token is usable for up to 15 minutes from anywhere (no DPoP/token binding in this design); a stolen **refresh** token is usable until the legitimate user refreshes and trips reuse detection, or until fingerprint mismatch is enforced (and fingerprinting breaks on legitimate IP churn, so it is a tripwire, not a guarantee); TOTP codes are 6-digit with a ±30 s window, so a phished code is usable within ~90 s — phishing-resistant factors (passkeys/WebAuthn) are out of scope for LAB-49. No control here stops an attacker who already owns the victim's email account (reset flow) or device. No "1000x" claim: these controls raise the cost of credential stuffing, token theft and TOTP bypass from trivial to requiring a targeted, time-boxed attack — they do not eliminate account takeover.

## Topic 3 — API3:2023 Broken Object Property Level Authorization (BOPLA)

### 1. Research

OWASP API Security Top 10 2023, API3: the 2023 merger of 2019 API3 (Excessive Data Exposure) and 2019 API6 (Mass Assignment), because both share one root cause: missing or improper authorization at the *object property* level. The caller is legitimately allowed to touch the object; the failure is which *fields* they may read or write. Read side: the endpoint serializes the whole object and trusts the client to hide sensitive fields. Write side: the API binds whatever JSON arrives onto its data model. (WSO2 guide summarising the OWASP 2023 list.)

**OWASP's own attack examples.** Booking flow: a host approves a reservation with `{"approved": true}`, then replays the request with an extra `"total_stay_price": "$1,000,000"` — the API accepts it because nothing checks whether a host may set that field. Same bug in another domain: `PATCH /users/me` accepting `"role": "admin"`. The DRF cheat sheet adds the framework-specific form: binding request data straight to a model, and warns that serializer controls do not replace authorization checks.

**Real-world example.** The First American incident (2019, ~885M records exposed) is cited in BOPLA literature as excessive-data-exposure cascading into massive privacy/reputational damage. The classic mass-assignment shape is a profile-update endpoint that lets an attacker add an admin/role flag to the body.

**What "done" looks like (OWASP cheat-sheet level).** (a) Explicit allowlist of readable *and* writable properties **per role** — never serialize whole objects with generic methods like `to_json()`. (b) For DRF, explicitly allowlist fields in `ModelSerializer.Meta.fields`; avoid `Meta.exclude` and `fields = "__all__"`, which silently expose newly added model fields. (c) Fields readable but not writable go in `Meta.read_only_fields` or `read_only=True`. (d) Reject unexpected/illegal content in input (REST cheat sheet: validate length/range/format/type, reject unexpected content). (e) Schema-based response validation as an extra layer. (f) Separate input DTOs from output DTOs. (g) Never rely on the client/UI to hide fields — hiding a button is not a control.

## Topic 4 — API4:2023 Unrestricted Resource Consumption

### 1. Research

**What it is (official API4 page — https://api-security.owasp.org/editions/2023/en/0xa4-unrestricted-resource-consumption/):** "Satisfying API requests requires resources such as network bandwidth, CPU, memory, and storage. Other resources such as emails/SMS/phone calls or biometrics validation are made available by service providers via API integrations, and paid for per request. Successful attacks can lead to Denial of Service or an increase of operational costs." Rated Prevalence **Widespread**, Detectability **Easy**, Technical impact **Severe**. An API is vulnerable if any of these limits is missing or mis-set: execution timeouts; maximum allocable memory; maximum file descriptors; maximum processes; maximum upload file size; number of operations per single request (e.g. GraphQL batching); number of records per page; third-party spending limits.

**OWASP's three example scenarios (same page):**
1. **SMS cost attack** — "forgot password" triggers a $0.05-per-message SMS; attacker scripts the call tens of thousands of times; "the company loses thousands of dollars in a matter of minutes."
2. **Batching defeats rate limiting** — GraphQL `uploadPic` with thumbnail generation; per-request rate limit + per-picture size check both bypassed by sending 999 mutations in one batched request → server memory exhaustion / DoS.
3. **Uncapped download + no cost alerts** — an 18 GB file bypasses a 15 GB cache; monthly bill jumps "from US$13, on average, to US$8k."

**Prevention (official API4 page):** container/serverless resource caps (memory, CPU, restarts, FDs, processes); maximum sizes on all incoming parameters/payloads (string length, array element count, upload size, local or cloud); rate limiting, fine-tuned per endpoint with stricter policies on expensive ones; per-client/per-operation throttling (explicitly: "validate an OTP, or request password recovery"); server-side validation of the parameter controlling records-per-page; spending limits for all providers, or billing alerts where hard limits are impossible.

**Cheat-sheet layer:** REST Security Cheat Sheet — return `429 Too Many Requests` when requests arrive too quickly; "define an appropriate request size limit and reject requests exceeding the limit with HTTP 413"; API keys for public endpoints because unfettered public endpoints get "farmed leading to excessive bills for bandwidth or compute cycles." Webhook Security Cheat Sheet — both publisher and subscriber need limits: publisher applies per-subscriber delivery limits, exponential backoff with jitter, a maximum retry count, and disables endpoints failing for days; subscriber rate-limits and answers excess with `429` + `Retry-After` (RFC 6585 §4), acknowledges fast and processes via an async queue.

**"Done" looks like:** every endpoint has a documented rate (per user, per IP, per tenant, global), tighter on expensive/auth endpoints; every list clamps page size server-side; every body/array/upload has a max size enforced with 413; expensive work is async with concurrency caps, timeouts, and retry ceilings; metered third-party calls have per-tenant quotas + spend alerts; 429s carry `Retry-After`; limiter state is shared (not per-process memory) across instances.

**Concrete LabFlow attack flows:**
- A1. Unauthenticated flood of `POST /api/v1/demo-requests` (public lead capture) → unbounded `DemoRequest` rows; `POST /api/v1/webhooks/n8n/*` callbacks (DB lookup + audit write per call); `GET /api/v1/exports/{id}/download?sig=` (7-day signed link, no throttle) → repeated full-ZIP downloads.
- A2. Authenticated staff token (any compromised/low-privilege credential) hammers unthrottled endpoints: patient trigram search (expensive `pg_trgm` similarity per call), invoice creation with a giant `items` array, report delivery (each fans out to Celery + n8n + WhatsApp).
- A3. Owner enqueues many `POST /api/v1/exports` → each builds a whole-tenant ZIP fully in worker memory → worker OOM; PDF renders (seconds of WeasyPrint CPU each) share one 4-concurrency worker with all queues → delivery/settlement starvation.
- A4. Cost attack, OWASP scenario #1 mapped: report-deliver / notification paths trigger n8n → WhatsApp/email sends with no per-tenant spend cap.

## Topic 5 — API5:2023 Broken Function Level Authorization (BFLA)

### 1. Research

**What it is (OWASP).** A regular user calls a function meant for another role. BOLA is the wrong *object* through a function you may use; BFLA is a *function* you should not reach at all. Attack: developers hide admin features in the UI and assume that is enough; the attacker reads API docs/traffic, finds `DELETE /api/users/{id}`, and calls it with a regular token; switching HTTP method (GET→DELETE) often exposes the same gap. OWASP's example: an attacker switches from `GET /api/invites/{invite_guid}` to admin-only `POST /api/invites/new` and issues an invite with the admin role. "Done": deny-by-default — every function declares which roles may call it, enforced through **one consistent authorization module** (not per-route hand checks); admin functions clearly separated from regular ones; test by logging in as a low-privilege user and calling every privileged endpoint, trying alternate methods and guessed paths (`/admin`); a route with no declared policy must fail the build. UI hiding is cosmetic: "If an admin button is invisible but the endpoint still accepts the call, the function is unprotected." NIST SP 800-228 REC-API-12: authorize the calling service *and* the end user for each request.

**Concrete LabFlow attack flows.** (a) Receptionist calls `POST /api/v1/branches` (Owner-only create), `PATCH /api/v1/tests/{id}` (Owner-only), `POST /api/v1/settlements/{id}/approve` (Owner-only), `POST /api/v1/exports` (Owner-only) directly with her token — today each is individually guarded, so these fail; the risk is the *next* endpoint whose author forgets the guard. (b) Technician calls `POST /api/v1/invoices/{id}/payments` with `kind=refund` — refund is Owner/Manager-only *inside* the service (`apps/billing/services.py:481-489`), so the function-level check lives one layer down from the route; a future caller of `PaymentService.record_payment` that skips the view inherits no protection. (c) Manager calls `PUT /api/v1/staff/{id}/branches` (Owner-only write) — guarded in the service (`apps/accounts/services.py:236-…`); same layering concern. (d) Any staff role calls `GET /api/v1/patients/{id}` — **no role gate exists at all** on that read (see below).

### 2. LabFlow current state (verified at 5e98a06)

## Topic 6 — API6:2023 Unrestricted Access to Sensitive Business Flows

### 1. Research

OWASP's official API6 page (https://api-security.owasp.org/editions/2023/en/0xa6-unrestricted-access-to-sensitive-business-flows/): "APIs vulnerable to this risk expose a business flow — such as buying a ticket, or posting a comment — without compensating for how the functionality could harm the business if used excessively in an automated manner. **This doesn't necessarily come from implementation bugs**." Exploitability **Easy**, prevalence **Widespread**, technical impact **Moderate**, business impact specific. It is new in 2023 — the 2019 list had no equivalent.

**Sensitive-flow examples from OWASP:** purchasing (scalping — buy all stock of a high-demand item and resell); creating comments/posts (spam); making reservations (book all slots, block legitimate users). **Attack scenarios:** (1) console scalping — a bot distributed across IPs buys the majority of limited stock on release day; (2) airline seat-hoarding — book 90% of seats with free cancellation, force a price drop, cancel, rebuy cheap; (3) referral farming — script account registration so each new user credits the attacker's wallet, then sell the credited accounts.

**"Done" per OWASP (API6 "How to Prevent") — two layers:** *Business*: identify the flows that would harm the business if excessively used. *Engineering*: device fingerprinting (deny headless/unexpected devices), human detection (captcha, biometrics/typing patterns), non-human pattern detection (e.g. add-to-cart → purchase in <1 s), blocking Tor exit nodes and well-known proxies, and securing/limiting machine-consumed (B2B/developer) APIs, which are easy targets because they often skip these protections. Complementary controls from the REST Cheat Sheet and the API6 literature: per-account (not just per-IP) velocity limits linking user/device/payment-method/address/inventory/time-window, idempotency keys, reservation/hold expiry, step-up verification for high-value actions, anomaly detection and manual review, separate quotas for legitimate automation partners. API6 differs from API4 (resource consumption): API4 is about exhausting compute/cost; API6 is about *legitimate* requests distorting business outcomes — no request needs to be malformed.

**Real-world anchor:** the FTC fined three people $3.7M for using bots to buy thousands of concert/event tickets and resell them (cited in OWASP API6 coverage) — the canonical business-flow abuse case.

Rate limits and velocity caps are tripwires, not proof of humanity: a determined attacker with many accounts, IPs and devices can stay under per-actor caps (OWASP's scalping scenario is explicitly distributed). ## Topic 7 — API7:2023 Server Side Request Forgery (SSRF)

### 1. Research

**What it is (official API7 page — https://api-security.owasp.org/editions/2023/en/0xa7-server-side-request-forgery/):** "Server-Side Request Forgery (SSRF) flaws occur when an API is fetching a remote resource without validating the user-supplied URL. It enables an attacker to coerce the application to send a crafted request to an unexpected destination, even when protected by a firewall or a VPN." Rated Exploitability **Easy**, Prevalence **Common**, Detectability **Easy**, Technical impact **Moderate**. Modern drivers: webhooks, file fetching from URLs, custom SSO, URL previews. "More dangerous — modern technologies like cloud providers, Kubernetes, and Docker expose management and control channels over HTTP on predictable, well-known paths."

**OWASP's two example scenarios (same page):**
1. **Avatar by URL → internal port scan** — `POST /api/profile/upload_picture {"picture_url": "http://example.com/profile_pic.jpg"}`; attacker substitutes `"picture_url": "localhost:8080"` and infers open ports from response timing.
2. **Webhook registration → cloud credential theft** — `createNotificationChannel` with `url` + `send_test_req: true`; backend sends a test request and *returns the response to the user*; attacker sets `url: "http://169.254.169.254/latest/meta-data/iam/security-credentials/ec2-default-ssm"` and reads the cloud credentials from the response. (The widely reported Capital One 2019 breach followed this pattern — SSRF to cloud metadata, 100M+ records — and is the canonical real-world case for this category.)

**Prevention (official API7 page):** isolate the resource-fetching mechanism in its own network segment; wherever possible use allow-lists of remote origins, URL schemes and ports, and accepted media types; **disable HTTP redirections**; use a well-tested, maintained URL parser; validate and sanitize all client-supplied input; **do not send raw responses to clients**.

**Cheat-sheet layer (SSRF Prevention Cheat Sheet):** two cases — (1) app talks only to identified/trusted apps → allow-list + network restrictions; (2) app must reach arbitrary external destinations (e.g. webhooks) → allow-list is impractical, so use a deny-list of non-public ranges as a *last resort* (deny-lists are bypass-prone). Critical subtleties: **a domain allow-list alone does not prevent DNS rebinding** — validate the *resolved* destination IPs against permitted networks and connect only to the validated addresses (pin the IP, preserve the original hostname for `Host`/SNI/certificate); apply the policy to retries and fallbacks too; disable redirect following or re-validate every hop. (Webhook Security Cheat Sheet, publisher side: `https://`-only scheme allow-list plus a deny-list of every non-public address range, **enforced on the resolved IP at connect time**; disable redirects or apply the same checks to every redirect target — Stripe treats redirect responses as failed deliveries; isolate delivery workers/egress proxy in a segment that cannot reach internal services, e.g. an egress proxy like Smokescreen.)

**"Done" looks like:** one shared, reviewed "safe fetcher" used by every outbound call — allow-listed destinations where possible; otherwise scheme allow-list (https only), resolved-IP check against non-public ranges at connect time, redirects disabled (or re-validated per hop), response size + timeout caps, network egress rules blocking private ranges as backstop, and raw upstream responses never returned to callers.

**Concrete LabFlow attack flows (hypothetical — see Current state for what actually exists):**
- S1. Webhook URL registration: if any endpoint ever let a tenant register a callback URL, attacker sets `http://169.254.169.254/...` or `http://redis:6379/` / `http://postgres:5432/` / `http://minio:9000/` / `http://backend:8000/admin/` and the backend POSTs the signed payload there — blind SSRF at minimum (timing/status oracle), credential/metadata theft at worst.
- S2. PDF-from-HTML: if report HTML ever included a caller-controlled URL (logo/image), WeasyPrint would fetch it server-side during rendering.
- S3. Avatar/logo by URL: classic OWASP scenario #1 — no such feature exists today.
- S4. Redirect laundering: a validated public URL (e.g. an n8n webhook) answering 302 to `http://169.254.169.254/` — followed blindly by the default HTTP clients in use.

## Topic 8 — API8:2023 Security Misconfiguration

### 1. Research

**What it is.** OWASP API Security Top 10 2023, API8 — the broadest category: insecure configuration at *any* layer (server, framework, gateway, load balancer, cloud). OWASP's listed symptoms: missing TLS, missing or permissive CORS, stack traces in error messages, unnecessary HTTP verbs, missing cache-control headers, unpatched components. OWASP's two 2023 scenarios show the range: (1) a logging library resolving a JNDI lookup taken from a request header (Log4Shell-shaped — untrusted input reaching a dangerous resolver because of configuration); (2) a direct-message API omitting `Cache-Control`, so private conversations end up in the browser cache. The 2019→2023 change is only a renumbering (API7:2019 → API8:2023, "moved down one place"). **The video skips this topic entirely** — API8 is explicitly one of the topics the reel never covers.

**What "done" looks like (OWASP cheat-sheet level).** (a) A *repeatable hardening process* leading to fast deployment of a properly locked-down environment, plus an *automated process to continuously assess* configuration in all environments (DRF cheat sheet, API7:2019). (d) Define error response schemas and keep stack traces and secrets out of error messages. ## Topic 9 — API9:2023 Improper Inventory Management

### 1. Research

**What it is (OWASP).** APIs tend to expose more endpoints than traditional web applications, so proper and updated documentation is critical. Also, proper inventory management plays an important role in mitigating security issues such as deprecated API versions and exposed debug endpoints. OWASP's canonical scenarios: (a) an old API version (`/api/v1`) left running after `/api/v2` ships, with weaker auth — attackers target the old version; (b) a beta host running the same password-reset endpoint *without* the rate limiter, letting a researcher brute-force a 6-digit reset token and reset any password; (c) debug endpoints and interactive documentation left exposed in production, giving attackers a full inventory of the API for free.

**What "done" looks like (OWASP cheat-sheet level).** (a) A complete, living inventory of every API endpoint: owner, version, environment, authentication, and retirement date. (b) Documentation generated from the inventory, not hand-written separately. (c) Old versions retired on a published schedule — no silent shadow versions. (d) Hosts inventoried too: every host that serves the API must run the same protections (rate limiting, auth) as production; no "beta" host with weaker controls. (e) Debug endpoints, admin consoles and interactive docs disabled or gated in production. (f) A spec-vs-live diff in CI: if a route exists in code but not in the inventory (or vice versa), the build fails.

**Concrete LabFlow attack flows.** (a) Attacker reads the public `/api/docs` Swagger UI, enumerates every endpoint and field, then probes the ones with the weakest controls (see API3/API5). (b) Attacker finds the duplicate settlement callback (live, HMAC) vs the automation callback (new, key) and targets whichever has the weaker check. (c) Attacker uses a forgotten route — an old alias, a debug endpoint, an unversioned mount — that the team no longer tests or monitors.

**Sources actually read for this topic:** OWASP REST Security Cheat Sheet (read in full); WSO2 OWASP API Top 10 guide; QuantumSec and Scantitan API Top 10 explainers. The researcher's guessed `owasp.org` per-risk URLs all returned 404 and are **not** cited. The OWASP API Top 10 2023 PDF was not reachable.

## Topic 10 — API10:2023 Unsafe Consumption of APIs

### 1. Research

**What it is (OWASP).** APIs do not only serve data — they consume other APIs. Unsafe consumption means trusting third-party data and services without validation: the API blindly trusts data from an upstream service, follows redirects to attacker-controlled destinations, buffers unbounded responses, or retries forever. OWASP's own example: a service that fetches a URL from an upstream response and follows a 308 redirect to an internal address — the redirect, not the original URL, is the attack. The 2023 edition added API10 because modern APIs are chains: LabFlow → n8n → WhatsApp/email, LabFlow → R2/MinIO, LabFlow → SMTP.

**What "done" looks like (OWASP cheat-sheet level).** (a) Validate and sanitize all data received from third-party services exactly as if it came from a user — never trust upstream data. (b) Outbound calls: allow-listed destinations, no redirect following (or re-validation per hop), response size caps, timeouts, and a circuit breaker. (c) Inbound webhooks/callbacks: HMAC signature + timestamp + replay window, not a static bearer key alone. (d) Bounded retries with a terminal state (max attempts, then dead-letter, never infinite). (e) Every external dependency's configuration (email, storage, webhooks) validated at startup — fail fast on missing or wrong config, never fail open with a localhost default. (f) The Webhook Security Cheat Sheet: subscriber rate-limits inbound callbacks and answers excess with `429` + `Retry-After`; publisher applies per-subscriber delivery limits, exponential backoff with jitter, a maximum retry count, and disables endpoints failing for days.

**Concrete LabFlow attack flows.** (a) Attacker controls an n8n webhook response (or compromises the n8n instance) that 308-redirects LabFlow's outbound POST to `http://169.254.169.254/` — LabFlow follows it (see API7). (b) Attacker replays a captured n8n callback (no timestamp/nonce) to flip a report delivery to SENT without the report ever being sent. (c) A `whatsapp_url` value stored verbatim from a callback is later rendered in the frontend as a link — attacker-supplied URL, user clicks it. (d) The password-reset flow "fails open" because no email backend is configured — users cannot recover accounts, or a misconfigured backend silently drops security mail.

**Sources actually read for this topic:** OWASP REST Security Cheat Sheet (read in full); WSO2 OWASP API Top 10 guide; QuantumSec; Scantitan. The researcher's guessed `owasp.org` per-risk URLs all returned 404 and are **not** cited.

### 2. LabFlow current state (verified at 5e98a06; tenant URLconf verified identical at main 23b0964)

**Strongest existing controls (verified, do not break):** constant-time HMAC/callback-key comparison (`signing.py:40`, `services.py:265-278`); fail-fast on missing webhook secret; idempotent state-machined callbacks with audit rows; report-file download re-validating signature + tenant row (`reports/views.py:234-284`).

**Outbound consumption — the gaps:**
- **G10-1:** outbound POSTs follow redirects with no allowlist (`automation/services.py:98-101`, `notifications/tasks.py:175-182`) — OWASP's own 308 example.
- **G10-4:** `whatsapp_url` stored verbatim, no allowlist/scheme validation (`services.py:490`).
- **G10-5:** unbounded outbound response buffering + unbounded webhook retry, no max attempts/terminal state.
- **G10-6:** **NO email configuration in `base.py` at all** (Django defaults localhost:25, no TLS/auth) — activation mail fails open.
- **G10-7:** R2/MinIO not wired (no `STORAGES`, no django-storages/boto3; PDFs on local disk) while compose defaults `minioadmin`/`minioadmin123`.
- **G10-8:** no startup validation of `N8N_WEBHOOK_URL(S)`, callback host hardcoded to `labflow.app`.

**Inbound consumption — the gaps:**
- **G10-2:** inbound n8n callbacks bearer-key-only, no HMAC/timestamp/replay window; n8n-side HMAC verify unimplemented (bones node throws).
- **G10-3:** no throttle/logging on callback auth failure, no bad-signature alert in base.

### 4. Implementation

1. **Redirect/size policy (G10-1, G10-5) — shared with API7.** Route all outbound POSTs through the new `backend/apps/core/safe_fetch.py` (API7 step 1): `allow_redirects=False` (or re-validate every hop), response body cap (e.g. 1 MB, streaming read), timeout kept (15 s/30 s). Files: `automation/services.py:98-101`, `notifications/tasks.py:175-182`, `partners/tasks.py:250-258`.
2. **Inbound HMAC + 5-min timestamp (G10-2) — new SE-43 proposed.** Add timestamp header + 5-min skew window and nonce/`idempotency_key` replay rejection to `automation/services.py::verify_callback_key` / `handle_delivery_callback` and the settlement HMAC callback; implement the n8n-side HMAC verify node (the bones node currently throws — finish it). Tests: `test_callback_rejects_stale_timestamp`, `test_callback_rejects_replayed_nonce`.
3. **Callback throttling + logging (G10-3) — new.** Per-IP rate limit on the three callback endpoints; log every failed callback auth with IP + key fingerprint; add the LAB-49 task-8 alert (bad-signature >50/hr pages).
4. **`whatsapp_url` allowlist (G10-4) — new.** Validate on store: scheme must be `https`, host must be `wa.me` (or an explicit allow-list); reject anything else with 422. Apply the same validation at render time in the frontend (defence in depth).
5. **Bounded retries + circuit breaker (G10-5) — new SE-44 proposed.** Max attempts (e.g. 5) with exponential backoff + jitter, then a terminal FAILED state + dead-letter row; per-subscriber delivery limits; disable endpoints failing for days (Webhook Cheat Sheet). Files: `automation/services.py` retry path, `automation/tasks.py` sweep.
6. **Email decide-and-configure (G10-6) — new.** Decide the prod mailer (Gmail SMTP app password is the chosen direction; Resend was at 200% of its 100/day quota on 2026-11-06) and configure it explicitly in `base.py` (host, port, TLS, auth) with a startup check that refuses to boot in prod without it; trace the password-reset delivery end-to-end (see API2 A2-7).
7. **R2 wire-or-stop-claiming (G10-7) — new.** Either wire `STORAGES` + django-storages/boto3 to real R2 with fail-fast env validation, or stop claiming R2 and document local-disk storage with its backup implications. Remove the `minioadmin` defaults (see API8 A8-4).
8. **Startup URL allowlist (G10-8) — new.** Validate `N8N_WEBHOOK_URL(S)` at startup (fail fast on non-https/private destinations, explicit local-dev override); replace the hardcoded `labflow.app` callback host with an env-derived value.

**SE mapping:** new SE-43 (inbound callback HMAC + timestamp + replay window) and SE-44 (bounded retries + circuit breaker) proposed. G10-6/G10-7 are pre-deploy decisions, not SE items.

### 5. Residual risk

Even after the safe-fetcher and HMAC work, LabFlow trusts n8n as a component: a compromised n8n instance can still send well-formed, correctly-signed callbacks (it holds the key) and can fetch arbitrary URLs through its own HTTP Request nodes (see API7 G-15). The mitigation is n8n's network isolation (edge only, no direct DB access) and key rotation — not a code fix in Django. Email deliverability (spam folders, provider outages) remains an operational risk, not a code risk. No multiplier is claimed.
