1. Purpose, scope, inputs, consistency check

1.1 Purpose

Doc 01 fixed the architecture and the n8n protocol in outline (§13). Doc 02 fixed the delivery tables. Doc 03 fixed how reports reach patients. Doc 05 fixed how statements reach partners, and left the n8n workflow internals to this document (OQ-42). This document fixes the automation layer: what happens between Django and n8n, and back.

After reading it, a developer should be able to build the webhook emitter, the four callback endpoints, and the n8n workflows without inventing rules. Anything this document needs that Doc 01 or Doc 02 does not have is marked Proposed and listed in §15.

n8n is a transport, not a brain. Every decision — who gets a message, what it says, when a delivery has failed for good — is made in Django and recorded in Doc 02 tables. n8n carries out one instruction at a time and reports back. If n8n vanished tomorrow, no LabFlow data would be lost: every unsent message would still be a row in a tenant schema, waiting.

1.5 Assumptions

  • AS-1. One n8n instance serves all tenants (Doc 01 §15 runs one n8n Compose service). There is no per-tenant n8n (§16).
  • AS-2. Platform staff operate n8n. Tenants never see it, log into it, or configure it (§4).
  • AS-3. Django and n8n run on the same VPS (Doc 01 §15) with clocks kept in step by the host OS. The 5-minute timestamp window assumes skew stays well under 5 minutes (§5, §12).
  • AS-4. Email leaves through one SMTP provider account for the whole platform. Which provider is OQ-46 (§14); the choice changes no rule in this document.
  • AS-5. Message text is rendered by Django from notification_template before the webhook fires. n8n never reads a LabFlow table, so it cannot fetch a template (§4, §7).
  • AS-6. Dates and times in payloads are UTC, ISO 8601. Display converts to Asia/Karachi in the SPA, as everywhere else.

2. Research findings

Each finding states what was found, the source, and what it changes here. One topic is covered by Doc 01 and is referenced, not re-researched: WhatsApp Business API pricing (F-6).

#FindingEffect here
F-1HMAC is the standard way to sign a webhook. RFC 2104 defines HMAC: a keyed hash that proves a message came from a holder of the shared secret and was not altered. HMAC-SHA256 over the raw body, sent in a header, is the pattern used by major webhook senders. Source: RFC 2104 — HMAC: Keyed-Hashing for Message Authentication.Confirms Doc 01 §13 unchanged: Django signs the raw body with N8N_WEBHOOK_SECRET and sends the hex digest in X-LabFlow-Signature (§5). The signature covers the exact bytes sent — any re-serialised body fails verification (AU-33).
F-2n8n does not verify HMAC signatures by itself. The Webhook node accepts the request; signature verification is a step the workflow author adds immediately after the trigger, computing HMAC over the raw body and comparing in constant time, before any side effect runs. Sources: Verify webhook signatures in n8n (Stripe, GitHub, raw body) — Lumadock; Secure Webhooks in n8n — RapiDevelopers.Every workflow in §7 has the same shape: Webhook trigger → verify (HMAC, timestamp) → dedupe → act → callback. A failed verify stops the workflow before anything is sent. Verification is workflow code, so it is reviewed like code (§7).
F-3A client-generated unique key makes retries of a POST safe. The IETF HTTPAPI draft for the Idempotency-Key header defines the pattern: the client generates one unique value per logical operation (a UUID is recommended), the server recognises repeats of the key and does not repeat the work. Source: The Idempotency-Key HTTP Header Field — IETF draft.LabFlow carries the key in the payload body rather than a header, because the same key must survive the trip Django → n8n → callback and live on the webhook_delivery row. The pattern is the draft's; the transport is Doc 01 §13's (§5).
F-4SMTP failures split cleanly into temporary and permanent, and the reply class digit says which. A 4xx reply is temporary (try again later); a 5xx reply is permanent (the same send will fail again). RFC 3463 enhanced status codes add detail: 5.1.1 is “bad destination mailbox address” — the mailbox does not exist; 4.2.2 is a mailbox over quota — full now, maybe fine later. Sources: What SMTP replies and enhanced status codes mean — GreenArrow; A guide to email bounce codes — Mailmodo.§9's rule is mechanical: the SMTP reply class decides. 4xx → soft failure, retry on the sweep. 5xx → hard failure, hard_bounce: sentinel, retries stop. n8n copies the SMTP code and text into the callback's last_error; it does not interpret them. Django classifies.
F-5A 5-minute timestamp tolerance is the common replay window. Widely used webhook verifiers reject signatures whose timestamp is more than about 5 minutes old, which bounds how long a captured request stays useful to an attacker while tolerating normal clock skew. Source: Verify webhook signatures in n8n — Lumadock (Stripe-style verification with a 300-second tolerance).Confirms Doc 01 §13's 5 minutes. §5 states the point plainly: the window is a replay guard, not a claim that the two clocks agree to the second (§12, AU-32).

Per the brief for this document, the topic is not re-researched here.No effect on v1. WhatsApp stays a staff-clicked wa.me link (Doc 01 §13). F-7n8n's default single-process mode has a throughput ceiling; queue mode is the documented way past it. n8n's own benchmark shows the single mode saturating under load while queue mode — webhook intake separated from workflow execution, workers pulling from Redis — handled the same load with no failures. Queue mode needs its own Redis-backed worker topology and is a scaling decision for Doc 10, not a v1 need (§16). The retry design (§9, §12) never depends on n8n being up — that is what makes a single instance acceptable.

3. Design principles

Doc 03's principles P-1 to P-10 govern the lab modules, and P-1 (patient safety first) still outranks everything here. These govern the automation layer.

#PrincipleWhat it means here
AP-1n8n is a transport, not a brain.n8n makes no decisions. It does not choose recipients, templates, or retries. Django decides, records the decision as a row, and hands n8n one instruction.
AP-2Every send is a row first.No row, no send. The webhook_delivery row and the notification or report_delivery row exist before the webhook fires. If the process dies between deciding and sending, the row is the recovery.
AP-3The callback is the truth.A send is not done when n8n accepts the webhook, and not done when n8n sends the email. It is done when the callback lands and Django records it. Doc 05 DL-3 states the same rule for settlements; §9 applies it everywhere.
AP-4Idempotency at both ends.The same idempotency_key travels out with the webhook and back with the callback. Retries are safe in both directions: n8n does not send twice for one key, and Django does not apply one outcome twice (§5).
AP-5Failure is a state, not an exception.Every failure lands as a visible row state — FAILED with last_error set — that a sweep can retry and a person can inspect. There is no dead-letter queue and no silent drop (Doc 01 §13).
AP-6Least data in flight.A payload carries only what its message needs: a link, a name, an address, a rendered text. n8n holds nothing after the workflow ends. Sentry strips patient fields before an error leaves the platform (Doc 01 §14).
AP-7One n8n, and tenant isolation does not depend on it.The same workflows serve every tenant. Isolation comes from the callback landing on the tenant's own host, the tenant_slug match, and the row living in that tenant's schema — never from n8n-side routing or n8n-side data.
AP-8Money never rides this layer.No event payload carries a share amount, an invoice amount, or any money figure. A settlement payload carries identifiers, a period, and the rendered statement PDF — the figures are inside the PDF, which LabFlow rendered. If a future payload ever must carry money, it is Decimal-as-string, per Doc 03 §6.1.

4. The n8n role and the trust boundary

n8n sits outside the trust boundary of LabFlow data. It is a delivery tool the platform operates, in the same class as the SMTP provider itself: it sees a message because it is asked to carry it, and it keeps nothing.

4.1 What n8n is allowed to do

  • Receive a signed webhook from Django, verify it, and run the one workflow the event names (§5, §7).
  • Send email through the platform's SMTP credential, with the subject, body, recipient and attachment exactly as given in the payload.
  • Build a wa.me click-to-send URL for WhatsApp events and return it in the callback. Building the URL is all it does; a staff member clicks it and sends from their own WhatsApp (Doc 01 §13).
  • Call back to the callback_url in the payload — one of the §10 endpoints, on the tenant's own subdomain — and report the outcome.
  • Keep its own execution logs for operations (Doc 09). Those logs are platform operations data, not LabFlow records.

4.2 What n8n is never allowed to do

  • Never read PostgreSQL. n8n has no database credential and no network path to postgres. Doc 01 §15 defines two Compose networks, edge and internal, and states it plainly: n8n cannot reach postgres. The boundary is enforced by the network, not by politeness.
  • Never write to a LabFlow table except through the callback endpoints in §10. Those endpoints are the only doors, and each one checks the callback key and the tenant slug before it touches a row.
  • Never hold patient data beyond the in-flight payload. A workflow receives the fields its message needs, uses them, and ends. No workflow stores patient data in n8n, writes it to a file, or passes it to any other service.
  • Never send a message LabFlow did not ask for. Every send begins with a signed webhook that names a webhook_delivery row. n8n has no schedules of its own for LabFlow messages, no lists, and no templates of its own — the message text arrives rendered, in the payload (AS-5).
  • Never render a PDF. Reports and statements are rendered by Django with WeasyPrint (Doc 03 §9, Doc 05 §8). n8n transports bytes; it does not create them (§8, §16).

4.3 Ownership

Platform staff own n8n: the instance, the workflows, the SMTP credential, and the two secrets (N8N_WEBHOOK_SECRET, N8N_CALLBACK_KEY). Tenants never touch it — no tenant login, no tenant workflow, no tenant-visible setting. A tenant experiences n8n only as “the email arrived” or “the delivery shows FAILED”. Workflow definitions are platform code: they are reviewed and deployed like code (Doc 09 owns operations, Doc 10 owns configuration values).

Why the boundary is this strict. n8n is a general automation tool with a broad plugin surface, running outside Django's permission system. If it could read the database, every tenant's data would depend on the security of a tool that was never designed to hold it. The design instead gives n8n exactly two capabilities — receive a signed instruction, report an outcome — and takes everything else away at the network layer, where a workflow mistake cannot undo it.

5. The signed webhook contract

This is Doc 01 §13's protocol, written out in full. It does not change the protocol; it pins the details a developer needs: headers, check order, error codes, rotation.

5.1 Outbound: Django → n8n

When a module decides a message must go out, Django does three things in order:

  1. Writes the delivery rows: one webhook_delivery row (status PENDING, attempts = 0) and the matching notification or report_delivery row (status PENDING). Both carry the same idempotency_key.
  2. Builds the payload and stores it, unchanged, in webhook_delivery.payload_jsonb. A retry re-sends this exact payload. Nothing is rebuilt.
  3. POSTs the payload to the n8n webhook URL for the event, signed as below.
{
  "event": "settlement.approved",
  "tenant_slug": "city-diagnostics",
  "callback_url": "https://city-diagnostics.labflow.app/api/v1/webhooks/n8n/settlement-delivery",
  "idempotency_key": "3f8c2e1a-7b4d-4e5f-9a1c-0d2b3e4f5a6b",
  "timestamp": "2026-10-20T08:15:30Z",
  "data": { }
}

The payload shape is Doc 01 §13's, unchanged. data is per-event; §6 defines it for each event.

5.2 The timestamp rule

  • TS-1. n8n's verify step reads timestamp first. If it is more than 5 minutes in the past, the workflow stops. No side effect, no callback. The webhook is treated as a replay or a stale retry.
  • TS-2. A rejected-stale webhook is not retried by re-sending the same payload — its timestamp would only get older. When the Beat sweep retries a webhook_delivery row, Django re-stamps timestamp at send time and re-signs. The stored payload_jsonb keeps the original timestamp for audit; the wire copy is re-stamped. The idempotency_key never changes, so n8n still recognises the delivery.
  • TS-3. The window is generous on purpose. Both processes run on one VPS (AS-3). A skew large enough to break a 5-minute window is a host fault, and it shows up as verify failures in n8n's log and a rise in PENDING rows — both alerted (§13).

5.3 The idempotency key

  • IK-1. One key names one logical delivery. A manual re-send is a new logical delivery: new rows, new key (Doc 05 DL-6). A sweep retry is the same logical delivery: same rows, same key.
  • IK-2. n8n's dedupe step checks the key against the keys it has already processed, before any side effect. A key it has seen ends the workflow with no send and no second callback. This is what makes the §12 crash case safe.
  • IK-3. The hard guarantee lives in LabFlow, not in n8n. The key is UNIQUE on webhook_delivery and on notification, and every callback is idempotent by key (§5.4). If n8n's own dedupe record is ever lost, a duplicate send is possible but a duplicate state change is not: the second callback returns the row's current state and applies nothing (§10).

5.4 Inbound: n8n → Django (the callback)

The callback is a POST to the payload's callback_url. It carries the header X-LabFlow-Callback-Key with the value of N8N_CALLBACK_KEY (or N8N_CALLBACK_KEY_NEXT during rotation, §5.5). The body carries tenant_slug and the same idempotency_key as the outbound webhook. Django checks, in this order:

  • CB-1. A callback delivered twice must not double-apply. The second delivery of the same outcome returns 200 with the row's current state and changes nothing (IK-3).
  • CB-2. A failed check changes no state. A 401 or 403 callback is logged with its source and counted; a non-zero rate of either is an alert, because in normal operation it never happens (§13).
  • CB-3. The callback key is a platform secret in env only (Doc 01 §13, Doc 02 §8). No database table holds it, and it is never sent anywhere except this header.

5.5 Key rotation

Two secrets exist: N8N_WEBHOOK_SECRET (Django signs, n8n verifies) and N8N_CALLBACK_KEY (n8n presents, Django checks). They rotate independently.

Callback key rotation uses the _NEXT slot, with a defined cutover:

  1. Set N8N_CALLBACK_KEY_NEXT on Django to the new key and restart the backend. Django now accepts both keys at check 2 above. n8n still presents the old key; nothing changes yet.
  2. Update n8n's callback credential to the new key. This is the cutover. From this moment, new callbacks present the _NEXT key. Callbacks already in flight may still present the old key, and are accepted.
  3. Watch the callback 401 rate (§13) for 24 hours. It must stay zero: zero means every callback is presenting one of the two accepted keys.
  4. Promote: set N8N_CALLBACK_KEY to the new key, clear N8N_CALLBACK_KEY_NEXT, restart the backend. The old key is no longer accepted; a callback presenting it gets 401 (AU-25).

Webhook secret rotation has no dual-accept slot in Doc 01 §13, and Doc 06 does not invent one. It is a coordinated change in one maintenance window: set the new N8N_WEBHOOK_SECRET in n8n's verify step and in Django's env, restart both, and confirm with one test event. During the window, deliveries wait as PENDING rows and the sweep sends them after (§12). The window is minutes, and no message is lost by it.

7. n8n workflow catalogue

One workflow per delivery kind. Every workflow has the same skeleton, because every event has the same contract (§5):

Webhook trigger (receives the POST, raw body preserved) → Verify (a code step: recompute HMAC-SHA256 over the raw body with N8N_WEBHOOK_SECRET, compare in constant time, check timestamp is within 5 minutes; any failure stops the workflow — no send, no callback) → Dedupe (check idempotency_key against processed keys; a seen key stops the workflow) → Act (the one side effect) → Callback (an HTTP request to callback_url with the X-LabFlow-Callback-Key header and the outcome body). If the Act step fails, the workflow still runs the Callback step with a FAILED outcome — a failure that is never reported is the one failure mode this design refuses (§12).

The workflows use only built-in n8n nodes: the Webhook trigger, a code step for verify and dedupe, the email node with the platform SMTP credential, a set step to build the wa.me URL, and an HTTP request node for the callback. No community nodes. No workflow reads a database (§4). Workflow configuration values — URLs, credential names, the SMTP account — live in Doc 10; running and changing workflows lives in Doc 09.

8.2 Decision: option (a), base64 in the payload

  • PDF-1.   • PDF-2. In WF-EMAIL-SETTLEMENT, the email node takes its attachment from the binary data decoded out of data.pdf_base64, named by data.pdf_filename. There is no fetch step in the workflow. There is no URL anywhere in the flow.
  • PDF-3. The defence is the leak surface. A statement is a financial document (Doc 05 DL-4 makes the same point about WhatsApp). Option (b) turns every send into a short-lived public capability URL for that document and writes it into a third-party tool's logs. Option (a) creates nothing that outlives the request. The costs of (a) — payload size and signing — are real but trivial for a small monthly PDF, and they buy the simpler failure model: one step that can fail (the send), not two.
  • PDF-4. Failure path. If pdf_base64 is missing or does not decode, the workflow fails before the send and calls back FAILED. The notification row becomes FAILED with last_error set. The 15-minute Beat sweep re-fires the webhook, re-sending the stored payload from webhook_delivery.payload_jsonb — the PDF bytes are in that stored payload, so the retry needs nothing re-rendered and nothing re-fetched. There is no fetch, so there is no fetch-failure path.
  • PDF-5. The same mechanism is available to any future attachment-bearing email, unchanged. Report email does not use it in v1 (link only, above).

9.2 Soft failure — temporary, retry

  • DO-1. A soft failure is a temporary SMTP refusal: a 4xx reply — mailbox full (452 4.2.2), receiving server busy, temporary rejection (F-4). n8n calls back FAILED with the SMTP code and text in last_error.
  • DO-2. Django sets the row status = FAILED, increments attempts, and sets next_attempt_at from the retry policy (Doc 01 §13 notifications queue policy, as Doc 05 DL-5 states: 5 retries, backoff from 30 seconds to 30 minutes; the 15-minute Beat sweep performs the re-fires). While next_attempt_at is set and attempts is under the cap, the row is retryable and the sweep will re-fire its webhook with the same idempotency_key.
  • DO-3. A soft failure moves nothing else. The settlement stays APPROVED. The report stays final. Only the delivery row knows anything went wrong.
  • DO-4. When retries are exhausted, the row stays FAILED with last_error set and next_attempt_at = NULL. It does not disappear and it is not queued anywhere else — there is no dead-letter queue (Doc 01 §13). It surfaces where §13 says it surfaces, and staff recover by the owning module's re-send path (EV-2, Doc 05 DL-6).

9.3 Hard failure — permanent, stop

  • DO-5. A hard failure is a permanent SMTP refusal: a 5xx reply — the mailbox does not exist (550 5.1.1), the address is invalid, the domain does not resolve (F-4). Retrying the same send will fail the same way, so retries stop.
  • DO-6. The sentinel. n8n recognises the 5xx class and writes the callback's last_error starting with the exact prefix hard_bounce:, followed by the SMTP code and text — for example hard_bounce:550 5.1.1 mailbox does not exist. On a hard-failure callback Django sets status = FAILED, stores that last_error, and sets next_attempt_at = NULL. The Beat sweep skips any row whose last_error starts with hard_bounce:. That is the whole mechanism: a prefix on an existing text column, plus a NULL that already means “not scheduled”. No new column, no new status value, no amendment (§1.4, §15). A sentinel is the right tool here because “hard” is a fact about the error, not a state of the row — the row's state is FAILED, like any other failure; what differs is whether a retry can help, and next_attempt_at already encodes that.
  • DO-7. Classification rule, stated once: the SMTP reply class decides. 4xx → soft (DO-1). 5xx → hard (DO-5). n8n applies the class rule and the prefix; Django trusts the prefix, not a re-parse of free text. A failure with no SMTP reply at all (SMTP server unreachable, connection refused) is soft: the platform's own sending path is down, and a retry after recovery is exactly right.
  • DO-8. Statements. A hard bounce on a statement leaves the notification row FAILED with the sentinel, and the settlement stays APPROVED (Doc 05 DL-5: a delivery failure never un-approves money). The Owner is alerted (§13) and sees the failure on the settlement. The fix is a corrected partner email on the partner record, then a manual re-send (Doc 05 DL-6), which creates a fresh notification row; the bounced row stays as the record. The statement PDF is downloadable throughout (Doc 05 DL-7), so the lab is never locked out of its own document.
  • DO-9. Reports. A hard bounce on a report email moves the report_delivery row to BOUNCED — a status Doc 02 §5.7 already defines for exactly this. BOUNCED is terminal for that row: no sweep retry. The row also keeps the hard_bounce: text in last_error, so the report screen can show why. The bounced delivery lists on the report screen (§13); staff re-send through the report screen (EV-2), typically after correcting the patient's contact. The WhatsApp leg, if any, is a separate row and is unaffected.

9.4 OPENED

  • DO-10. OPENED belongs to report_delivery only. It is set by the patient's first use of the signed link (Doc 03 §6.8) — a LabFlow request, not a callback. A callback body that claims OPENED is not accepted: the callback endpoints take SENT or FAILED only (§10). OPENED is not applicable to settlements or notifications; email open-tracking does not exist in v1 (§16).

10. API reference — callback endpoints

These are the only endpoints in the LabFlow API that an external service calls. They live on the tenant subdomain, because n8n calls the callback_url from the payload, which is the tenant host (Doc 01 §13). They are not session endpoints: no JWT, no cookie. The only credential is the callback key.

10.1 Conventions for all callback endpoints

  • Authentication. Header X-LabFlow-Callback-Key carrying N8N_CALLBACK_KEY (or N8N_CALLBACK_KEY_NEXT during rotation, §5.5). Missing or wrong → 401 unauthorized_callback.
  • Tenant check. The tenant resolves from the host. The body's tenant_slug must equal it → otherwise 403 tenant_slug_mismatch. Check order is §5.4's.
  • Idempotency. Every endpoint is idempotent on (idempotency_key, event). Repeating a callback with the same key and the same outcome returns 200 with the row's current state and applies nothing (CB-1).
  • Success response. 200 with a body stating the new state of the row, for example { "idempotency_key": "…", "status": "SENT" }.
  • Errors. 401 unauthorized_callback · 403 tenant_slug_mismatch · 404 not_found (unknown path, unknown tenant host, or no row for the named object in this tenant) · 409 state_conflict (the outcome contradicts a final row state) · 409 row_not_ready (no row yet for the idempotency_key; the caller retries the callback, §12). Error bodies are { "error": "<code>" }, matching Doc 03 §6.1's shape.
  • Nothing else is callable. These routes are the entire n8n surface. A request bearing the callback key to any other path on the tenant host, with no session, returns 404. Holding the callback key grants no session, no staff endpoint, and no read access of any kind.

12. Concurrency and failure

n8n has no database access (§4), so no failure in this layer can corrupt LabFlow data. Every failure reduces to the same shape: a LabFlow row sits in a visible, retryable state; Sentry sees the error; the Beat sweep retries; an exhausted row stays FAILED; staff recover by re-send. The cases below are the ways reality produces that shape.

12.1 n8n is unavailable when the webhook fires

The POST times out or is refused. The webhook_delivery row stays PENDING with attempts incremented and next_attempt_at set. The Beat sweep re-fires it — re-stamped, re-signed, same key (TS-2). When n8n returns, the delivery proceeds as if nothing happened. A long outage shows up as PENDING rows ageing past 15 minutes, which alerts (§13). Nothing is lost, because the row was written before the first attempt (AP-2).

12.2 n8n accepted the webhook, but the side effect failed

n8n replies 2xx to the POST, so the webhook_delivery row becomes SENT — and then the SMTP send fails inside the workflow. The workflow still runs its callback step with FAILED (the §7 skeleton makes the callback unconditional). This is how LabFlow distinguishes “n8n failed” from “n8n never heard”: the webhook_delivery row's own state and attempts. Row SENT + a FAILED callback = received and failed. Row still PENDING with rising attempts = never accepted. The two cases never share a state, so nobody has to guess which one happened.

12.3 n8n crashes after sending, before the callback

The email went out; the callback never arrived. The notification or report_delivery row stays PENDING. The sweep re-fires the webhook with the same idempotency_key. n8n's dedupe step recognises the key and does not send a second email (IK-2); it re-runs only the callback. The patient gets one email, late. If n8n's dedupe record itself was lost in the crash, one duplicate email is possible — annoying, not harmful — and the duplicate callback still cannot double-apply state (IK-3).

12.4 The callback arrives before the row exists

The outbound write and the webhook fire are fast; n8n can, in principle, call back before the transaction that wrote the rows is visible. The callback endpoint looks the row up by idempotency_key inside the resolved tenant's schema. Not found → 409 row_not_ready, no state change. n8n treats a 409 callback response as “retry the callback” and retries it on its own short backoff until it lands or the workflow execution is marked errored — by which time the row exists and the sweep provides the second chance (§12.3's path). Found but already final → 200 with the current state (CB-1). The 409 is what buys correctness here: the endpoint never guesses, never creates a row to match a callback, and never applies an outcome to a row it cannot see.

12.5 HMAC verification failure

n8n's verify step stops the workflow: no send, no callback, and the mismatch is logged with the event name and source. LabFlow's rows stay PENDING and the sweep keeps re-firing until the cause — a rotated secret not yet updated on one side, a proxy rewriting the body — is fixed. A burst of verify failures after a deploy is a config bug, and it is loud: n8n's error log plus ageing PENDING rows (§13). Django never sees the bad request at all; there is nothing to roll back.

12.6 Replay

Two guards, either of which is enough. A replayed webhook carries its original timestamp: older than 5 minutes, the verify step rejects it (TS-1). A replay inside the window carries an idempotency_key that already exists: the database refuses a second webhook_delivery row (UNIQUE), and n8n's dedupe refuses a second send. A replayed callback is handled by CB-1: 200, current state, nothing applied twice.

12.7 Clock skew

The assumption (AS-3) is one VPS, one OS clock source, two processes. Skew of seconds is normal and the 5-minute window absorbs it (AU-32). The failure mode if the assumption breaks — a host clock fault — is total and obvious: every verify fails, no sends happen, rows age, alerts fire (§13). It cannot produce a wrong send, only delayed ones, because verification fails closed.

12.8 Read-only and past-due tenants

Doc 05 resolved OQ-36: settlement generation continues while a tenant is past due or read-only; approval, statement delivery and mark-paid pause in read-only mode and resume on reactivation. This layer follows that decision mechanically. While a tenant is read-only, Django fires no new delivery webhooks for it and the sweeps skip it; its rows wait in PENDING. A callback already in flight when the tenant became read-only is still applied — it records a fact about an email that was already sent, and dropping it would falsify the delivery record. On reactivation, the sweeps pick the waiting rows up in the normal way. Report delivery follows the same rule: Doc 04 §11 read-only mode blocks writes, and patient-facing delivery is a write-driven flow, so it pauses and resumes the same way.

16. What is NOT built in v1

  • No inbound n8n-created data. n8n originates nothing: no patient records, no results, no rows of any kind. Its only writes are outcome reports through §10.
  • No direct n8n writes to tenant tables. Ever, for any workflow (§4). The callback endpoints are the only doors.
  • No WhatsApp unattended sending. WhatsApp in v1 is a staff-clicked wa.me link (§7). No message leaves WhatsApp without a human clicking.
  • No WhatsApp Cloud API. It is the upgrade path (Doc 01 §13), with per-message pricing to check first (F-6, Unverified). Not built, not stubbed.
  • No SMS channel. No Doc 01–05 section defines one. Email and the WhatsApp hand-off are the channels.
  • No partner portal, no partner login (Doc 01 OQ-07, Doc 05 §15). Partners receive a statement by email and nothing else.
  • No in-n8n PDF rendering. WeasyPrint in Django renders every PDF (Doc 03 §9, Doc 05 §8). n8n transports bytes (§8).
  • No two-way sync with any external system. The flow is one instruction out, one outcome back. Nothing polls, imports, or reconciles an outside system.
  • No custom dead-letter queue (Doc 01 §13). Exhausted deliveries are FAILED rows. That is the end state, by design (AP-5).
  • No per-tenant n8n instance. One n8n serves all tenants (§4, AP-7).
  • No n8n queue mode. The single instance runs in regular mode (F-7). Scaling topology is a Doc 10 decision.
  • No critical-escalation automation (OQ-28): no workflow, no event delivery, no callback route, no reminder template (§7, §10, §14).
  • No automatic re-delivery on report amendment (EV-1). Staff re-send is the mechanism.
  • No email open-tracking. OPENED means “the patient used the report link” (Doc 03 §6.8), nothing more (DO-10). No tracking pixels, no per-message open receipts for settlements.
  • No asynchronous bounce (DSN) processing. v1 classifies a bounce from the SMTP reply at send time (§9). Parsing later bounce emails from a mailbox is not built; a mailbox that accepts a message and bounces it afterwards shows as SENT until staff learn otherwise — a known, accepted limit of send-time classification.

17. Interview talking points

  • Why HMAC + timestamp + idempotency key, and not just a shared secret in a header? A bare secret in a header proves the caller knew the secret once; it does not prove the body was not altered, and a captured request can be replayed forever. The three parts do three different jobs: the HMAC binds the signature to the exact bytes, so tampering fails; the timestamp bounds a capture's useful life to 5 minutes; the idempotency key makes the retries — which this design relies on everywhere — safe. Remove any one and a specific attack or a specific double-send becomes possible (§5, F-1, F-3).
  • Why can n8n not reach the database? Because it is a trust-boundary decision enforced by the network, not a convenience. Doc 01 §15 puts n8n on networks from which postgres is unreachable. n8n is a general tool with a broad plugin surface, operated outside Django's permission system; the moment it held a database credential, all tenant isolation would rest on its security. Instead it gets two capabilities — receive a signed instruction, report an outcome — and the callback endpoint checks key, host, slug and row before it applies anything. A fully compromised n8n can send spam until the credential is revoked; it cannot read a single patient's record (§4).
  • Why does the callback return 409 when the row does not exist yet? Because the alternatives are worse. Creating a row to match the callback would let an external caller mint LabFlow records. Guessing — applying the outcome to “the latest delivery for this report” — can mark the wrong attempt. The 409 says one true thing: “not yet; ask again”. The caller retries, the row appears, the outcome applies, and at no point did the system invent state. It costs one retry in a rare race and buys a callback endpoint that can never be tricked into writing fiction (§12.4).
  • Why base64 for the statement PDF, not a pre-signed URL? A pre-signed URL is a bearer credential for a financial document, and it would be written into n8n's execution logs on every send. Base64 inside the signed body creates nothing that outlives the request, needs no fetch endpoint and no TTL, and lets the HMAC vouch for the exact bytes attached. The price — about 33% size overhead and signing cost on a small monthly PDF — is trivial. Simplicity and leak surface both point the same way (§8).
  • Why one n8n for all tenants? Because n8n holds no tenant data, there is nothing per-tenant to isolate inside it. Isolation is enforced where the data lives: the callback lands on the tenant's own host, the body's slug must match that host's tenant, and the row it touches sits in that tenant's schema. A workflow bug cannot leak across tenants because the workflow has no cross-tenant state to leak — the worst a mix-up produces is a 403. Per-tenant instances would multiply the operations burden (Doc 09) to protect a boundary that is already enforced in Django (§4, AP-7).
  • Why is settlement email email-only — and how does that connect to the trust boundary? Doc 05 DL-4 decided it: a statement is a financial document that needs the PDF attached and a delivery record the lab can point to. WhatsApp in v1 is a human clicking a link, with no receipts — the lab could never prove a statement was delivered, and a doctor's personal WhatsApp is not a filing system. The same instinct runs through §4: the further a thing sits outside LabFlow's record-keeping, the less it may carry. Statements stay on the channel that produces a notification row, an SMTP outcome, and a callback — a complete, auditable trail (§9).
  • Why is the 5-minute window a replay guard and not clock accuracy? Because the two processes share one VPS clock source; if their clocks ever disagreed by 5 minutes, the host would be broken in ways that matter more than webhooks. The window exists to cap the value of a captured request: after 5 minutes, a replay is rejected on timestamp alone, and inside 5 minutes the idempotency key and the database UNIQUE constraint stop it. Stating the purpose matters operationally — a team that thinks the window measures clock health will widen it when alerts fire, and quietly disarm the guard (§5.2, §12.6).
  • Why does a hard bounce stop retries, marked by a text prefix instead of a column? Because “hard” is a fact about the error, not a state of the row. The row's state is FAILED, like every failure; what differs is whether a retry can help, and next_attempt_at already encodes the schedule — NULL means “not scheduled”. The hard_bounce: prefix on last_error records the reason in the column Doc 02 already provides, the sweep checks the prefix independently of the schedule (AU-40), and no schema change was needed for a distinction one sweep query expresses (§9, DO-6).
