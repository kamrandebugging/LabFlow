1. Purpose and scope

What this document covers: the complete data model — schemas, tables, columns, types, constraints, indexes, sequences, append-only enforcement, seed data, and the migration rules that keep multi-tenant deploys safe.

What it does not cover: behaviour and business workflows (Doc 03, Doc 05), API shapes (Doc 03), UI (Doc 07), and deployment (Doc 10). Where a decision here constrains those documents, the constraint is stated as a rule they inherit.

How to use it as ground truth: a table, column, status value, or index exists only if it is defined here. Additions beyond Doc 01 were marked Proposed at the table spec and listed in §20; as of v1.3 every one of them is accepted (§20), so no spec in this document carries a Proposed mark. Doc 01 references are cited by section throughout (for example, Doc 01 §8.5 step 3).

2. Conventions

AreaRule
Namingsnake_case. Tables singular (patient, invoice) — this matches every table spec, diagram and migration example in this document; columns singular (patient_id). Django models use Meta.db_table to get these short names instead of the {app}_{model} default.
Primary keyid uuid PRIMARY KEY DEFAULT gen_random_uuid() on every table. gen_random_uuid() is built into PostgreSQL 13 and later, so no extension is needed for it.
Timestampstimestamptz everywhere, stored UTC, rendered in Asia/Karachi at the API layer. created_at timestamptz NOT NULL DEFAULT now() on every table; updated_at on mutable tables only, set by the set_updated_at trigger. Append-only tables have only created_at — never an updated_at.
Money & percentMoney is numeric(12,2); percentages are numeric(5,2); other quantities declare their precision. No bare numeric, no float, ever (Doc 01 ADR-010). Python Decimal; strings on the wire.
EnumsDjango TextChoices in code — never Postgres ENUM types. A database CHECK constraint is added only on the highest-risk status columns: invoice.status, sample.status, result.status, settlement.status, payment.method, payment.kind. Every other status is application-enforced only and marked as such in its spec.
Foreign keysColumn named {referred_table_singular}_id. ON DELETE RESTRICT (Django PROTECT) on financial and clinical facts; CASCADE only for pure join tables (panel_test, staff_branch) and token rows owned by a user. No foreign key ever crosses the public / tenant boundary.
Soft deletedeleted_at timestamptz NULL, indexed where set, only on tables where recovery matters (named per spec, with a reason). Never on financial, audit, or clinical fact tables. Never cascaded through FKs.
Index namingidx_{table}_{columns}, uq_{table}_{columns}, chk_{table}_{rule}.
ExtensionsOnly one: pg_trgm (patient name / phone search only). pgcrypto is not installed — gen_random_uuid() has been built into PostgreSQL since version 13. Anything else is rejected.
JSONBOnly on audit_log.before_jsonb / after_jsonb, platform_audit.before_jsonb / after_jsonb, notification_template.template_context_schema, and webhook_delivery.payload_jsonb. Everything else is columns.
ExamplesNo SELECT * in any example in this document set. Column names are always explicit.

Deliberately not used: Postgres RLS (schema isolation is enough), partitioning, materialized views, and sharding. Volumes are small (Doc 01 §5: up to ~50,000 patient rows per tenant); none of these earns its complexity in v1.

3. Schema layout

LabFlow uses django-tenants, schema-per-tenant (Doc 01 ADR-003). The public schema holds the platform registry. Every tenant gets its own schema, tenant_<slug>, holding everything else.

SchemaTables
publictenant, domain, plan, subscription, platform_user, platform_audit
tenant_<slug> (one per lab)All tables in §5: branch, staff, patient, catalogue, billing, sample, result, report, referral partner and revenue share, notification, webhook, audit, tenant settings.
  • Allocation and switching: django-tenants creates the schema at provisioning (Doc 01 §8.5), sets search_path from the request host via TenantMainMiddleware, and runs tenant migrations per schema at deploy (Doc 01 §8.6). Celery workers enter tenant_context(tenant_slug) explicitly; a missing context raises an error.
  • Tenancy rule: tenant tables never carry a tenant_id column. Isolation is the schema itself. CI fails if a tenant-app model defines tenant or tenant_id (Doc 01 §8).
  • Users: platform_user lives only in public; staff_user lives only in each tenant schema. No foreign key ever crosses the public / tenant boundary — a tenant row that needs to name a platform actor stores the UUID as a plain column, not an FK.
  • Sequences: sequences live per schema (one set per tenant). Accession and MRN sequences are defined in §9.
  • No shared mutable tables: there are no cross-schema foreign keys and no table is written by two schemas.

5. Tenant-schema tables

Every table below exists once per tenant schema, identical in shape, isolated by the schema itself. Tables are ordered by dependency so the schema can be built top-down. Every table traces to Doc 01 §7 (module map) or §9 (tenant ERD); additions beyond Doc 01 carry their reason at the spec and are recorded as accepted in §20.

Figure 5.1 — Tenant ERD A: people, catalogue and billing. A branch has many staff and patients; staff branch assignment is many-to-many via staff_branch (§5.1), and tenant-wide roles (Lab Owner, Pathologist) carry no branch. An invoice belongs to one patient and one branch, has many items, and is settled by append-only payments.

Figure 5.2 — Tenant ERD B: the clinical chain. One report per sample in v1 (§11); corrections are new report_version rows, never edits. sample_test (§5.5) links each sample to its ordered invoice items and component tests — pending results are its rows with no approved result. A result flagged critical carries an append-only critical_notification record (§5.6).

Figure 5.3 — Tenant ERD C: revenue share and cross-cutting tables. One ledger entry per payment is the idempotency guarantee (§12). The ledger is fully append-only (UPDATE and DELETE revoked, §6): it has no status or settlement column — status is derived from settlement_line → settlement.status. The settlement unique rule is partial (WHERE status <> 'CANCELLED'), so a cancelled settlement never blocks its re-draft.

5.1 Branch, staff, 2FA

branch

Purpose: a lab branch or collection centre inside the tenant. Doc 01 ref: §4, §7, §9. Columns: id uuid PK · code text NOT NULL UNIQUE (3-char, used in MRNs, §9) · name text NOT NULL · address text NULL · phone text NULL · is_collection_centre boolean NOT NULL DEFAULT false · result_entry_enabled boolean NOT NULL DEFAULT false (A-8, §20 — the switch that lets the owner enable result entry at a collection centre, Doc 03 OQ-27; result entry stays off until the owner turns it on) · created_at / updated_at. Append-only: no. Soft delete: yes — deleted_at, because invoices and samples keep FKs to a closed branch and the row must stay recoverable. Indexes: uq_branch_code, idx_branch_deleted_at. Referenced by: staff_user, staff_branch, patient, test_price, invoice, sample, sample_transfer.

staff_user

Purpose: staff accounts inside this tenant only. Doc 01 ref: §4 roles, §9 (auth fields added by the Doc 01 fix list), §13/§14 in Doc 01. Columns: id uuid PK · branch_id uuid NULL FK → branch(id) RESTRICT (Django PROTECT) (home branch; NULL = tenant-wide — the Lab Owner and Pathologist work across the whole tenant, Doc 01 §4, and are not pinned to a single branch; branch assignments live in staff_branch below) · role text NOT NULL · email text NOT NULL UNIQUE per tenant (uq_staff_user_email) · password_hash text NOT NULL (argon2) · totp_secret_encrypted text NULL (NULL until enrolment; encrypted with the environment-held key in §14) · totp_backup_codes_hash text[] NULL (argon2 hashes, §14 decision: fields on staff_user in v1, a totp_device table is the v2 path — not created now) · totp_enabled boolean NOT NULL DEFAULT false · is_active boolean NOT NULL DEFAULT true · created_at / updated_at. Statuses: role owner | manager | reception | technician | pathologist — application-enforced only. Append-only: no. Soft delete: no — deactivate via is_active so audit actors stay resolvable.

staff_branch

Purpose: the branches a staff member is assigned to — the many-to-many link that replaces the old single-branch rule. Accepted (OQ-24, §20): Doc 01 §4 has the Lab Owner and Pathologist working across the whole tenant, which a single NOT NULL branch_id cannot express. Columns: staff_user_id uuid NOT NULL FK → staff_user(id) CASCADE · branch_id uuid NOT NULL FK → branch(id) CASCADE · is_primary boolean NOT NULL DEFAULT false · created_at only. Composite PK (staff_user_id, branch_id) (uq_staff_branch_staff_user_id_branch_id). Rules: branch-scoped roles (manager, reception, technician) need at least one row — application-enforced. Tenant-wide roles (owner, pathologist) may have no rows and a NULL home branch, which means access to every branch in the tenant. Append-only: no. Soft delete: no — removing an assignment deletes the join row only.

5.2 Patients

patient

Purpose: a person registered for testing at this lab. Doc 01 ref: §7, §9, §12 Flow A. Columns: id uuid PK · branch_id uuid NOT NULL FK → branch(id) RESTRICT (Django PROTECT) (registering branch) · mrn text NOT NULL UNIQUE per tenant (uq_patient_mrn, format §9) · name text NOT NULL · phone text NOT NULL · sex text NOT NULL (M | F, application-enforced; drives reference-range selection §10) · date_of_birth date NULL (not always known at a collection centre) · created_at / updated_at. Append-only: no. Soft delete: yes — deleted_at, because a mistaken duplicate registration must be reversible without touching clinical facts. Indexes: uq_patient_mrn, idx_patient_branch_id, idx_patient_name_trgm (gin, name gin_trgm_ops), idx_patient_phone_trgm (gin, phone gin_trgm_ops), idx_patient_deleted_at.

patient_contact

Purpose: additional contact channels (email, alternate phone, WhatsApp number) without widening patient. Accepted (OQ-24, §20): report delivery needs an email distinct from the primary phone (Doc 01 §12 Flow B). Columns: id uuid PK · patient_id uuid NOT NULL FK → patient(id) RESTRICT (Django PROTECT) · kind text NOT NULL (email | phone | whatsapp, application-enforced) · value text NOT NULL · is_primary boolean NOT NULL DEFAULT false · created_at / updated_at. Append-only: no. Soft delete: no.

patient_consent

Purpose: record of consent for report delivery by email / WhatsApp link. Accepted (OQ-24, §20): patient data is treated as sensitive (Doc 01 §5); a consent record is the evidence. Columns: id uuid PK · patient_id uuid NOT NULL FK → patient(id) RESTRICT (Django PROTECT) · channel text NOT NULL · granted_at timestamptz NOT NULL · granted_by uuid NULL FK → staff_user(id) RESTRICT (Django PROTECT) · revoked_at timestamptz NULL · created_at only. Append-only: no (revocation is a timestamp update, not a fact rewrite). Soft delete: no.

5.3 Catalogue

test

Purpose: one orderable laboratory test. Doc 01 ref: §7 catalog, §8.5 starter catalogue. Columns: id uuid PK · code text NOT NULL UNIQUE · name text NOT NULL · category text NULL · unit text NULL (default reporting unit; ranges carry their own, §10) · is_active boolean NOT NULL DEFAULT true · created_at / updated_at. Append-only: no. Soft delete: no — retire via is_active; results keep FKs.

panel · panel_test

Purpose: a panel is a named group of tests (e.g. LFT); panel_test is the pure join. Doc 01 ref: §9, §23 glossary. Columns: panel — id, code UNIQUE, name, is_active, timestamps. panel_test — panel_id FK → panel(id) CASCADE, test_id FK → test(id) CASCADE, composite PK (panel_id, test_id). Append-only: no. Soft delete: no. CASCADE is permitted here only because panel_test is a pure join table (§2).

test_price

Purpose: the price of a test or panel at a branch, effective-dated. Accepted (OQ-24, §20): Doc 01 §7 gives the catalog module pricing and §4 gives the Lab Owner pricing control, but no price table appears in Doc 01 §9. Columns: id uuid PK · branch_id uuid NULL FK → branch(id) RESTRICT (Django PROTECT) (NULL = tenant-wide price) · test_id uuid NULL FK → test(id) RESTRICT (Django PROTECT) · panel_id uuid NULL FK → panel(id) RESTRICT (Django PROTECT) · price numeric(12,2) NOT NULL CHECK price >= 0 · effective_from timestamptz NOT NULL · effective_to timestamptz NULL · created_at / updated_at. CHECK: exactly one of test_id, panel_id is set. Append-only: no — a price change closes one row (effective_to) and opens another, so history is preserved without edits to amounts already billed (invoice items snapshot the price, §5.4).

6. Append-only enforcement

Six tenant tables and one public table are append-only: share_ledger_entry, audit_log, report_version, payment, sample_event, critical_notification (tenant), and platform_audit (public). Append-only tables have created_at (or at) only — never updated_at.

-- Run in public at provisioning, and repeated in EVERY new tenant schema
-- (Doc 01 §8.5 step 3), and by migration for existing tenants:
REVOKE UPDATE, DELETE ON platform_audit FROM labflow_app;        -- public only
REVOKE UPDATE, DELETE ON payment FROM labflow_app;
REVOKE UPDATE, DELETE ON sample_event FROM labflow_app;
REVOKE UPDATE, DELETE ON report_version FROM labflow_app;
REVOKE UPDATE, DELETE ON critical_notification FROM labflow_app;
REVOKE UPDATE, DELETE ON audit_log FROM labflow_app;
REVOKE UPDATE, DELETE ON share_ledger_entry FROM labflow_app;  -- fully immutable: it has no status or settlement column to transition (see §5.8)
TableHow a "change" is modelled
share_ledger_entryA new negative (compensating) row against the same partner, in the current open period if the original period is closed (§12). Amounts on existing rows never change.
paymentA new row with kind = refund and the method the money was actually returned by (e.g. cash), never an edit. The amount stays positive; kind supplies the sign.
report_versionA new row with the next version number; report.status becomes amended.
sample_eventA new event row.
critical_notificationNever changed — the record of who was notified, when, and whether the value was read back stands as written; a further notification is a new row.
audit_log / platform_auditA new row. Audit is never corrected in place.

No exceptions: share_ledger_entry is fully immutable. It carries no status and no settlement_id: settlement membership lives only in settlement_line, and an entry’s status is derived from that line’s settlement.status (§5.8). Nothing on a ledger row ever needs to change, so UPDATE is revoked outright — the earlier status-transition exception (old OQ-22) is gone.

Rule: application code never issues UPDATE or DELETE against these tables. If it does, the database rejects it — that rejection is the safety net, not the primary defence.

10. Reference ranges

Decision: reference ranges live in their own reference_range table — not as a string on test. Reason: a reference range is not a constant; it varies by sex and age, and a string cannot be selected on, validated against, or effective-dated.

  • Multiple ranges per test are supported, keyed by sex (M | F | B), age_min_days / age_max_days, and effective_from / effective_to. Age bands are in days, so newborn and infant ranges are expressible; seeded adult bands start at age_min_days = 6570 (18 years).
  • Result validation computes the patient's age in days at collection time (from sample.collected_at and patient.date_of_birth), picks the row whose day band contains that age and matches the patient's sex, and sets result.flag: low or high outside low / high, critical outside critical_low / critical_high when those are set, otherwise normal. A critical flag requires a critical_notification record (§5.6).
  • A pathologist may release an out-of-range result: the release sets result_approval.range_override = true and writes an audit_log row — overrides are audited (Doc 01 §4: pathologist range override, audited).

11. Report grouping — resolves OQ-15

Decision: one report row per sample in v1 (SAMPLE ||--o| REPORT). report_version captures corrections (version 1, 2, 3, …); a new version sets report.status = amended.

Justification: it matches the per-sample reading in Doc 01 §9/§12, it is simpler for the pathologist (one sample, one sign-off, one PDF), and the corrections path stays clean because versions are append-only.

Known limitation (v1), stated plainly: one report per sample means several PDFs per visit. A patient who orders CBC, LFT and Urine R/E on a single invoice receives three separate reports — one per sample — not one combined PDF. Staff hand over (and patients download) one link per sample. This is accepted for v1; the per-order grouping below is the v2 fix.

Rule for Doc 03: any result approved after its report is final produces a new report_version — never a mutation of the existing version or its PDF. Completeness is computed from sample_test (§5.5): a report may go final only when every sample_test row for its sample has an approved result; pending results are exactly the sample_test rows without one.

Per-order path (documented for v2, not built): a new report_order join table mapping report → invoice_id would group a whole order's reports. The change is additive; no v1 data is lost. The table is deliberately not created in v1.

12. Revenue share, partial payments, discounts, refunds — resolves OQ-16

Decision: the share is computed per payment, on the paid amount — never on the invoice total. Doc 05 defines behaviour on top of this model; it does not reopen it.

  • Ledger creation: one share_ledger_entry per payment, unique on payment_id (idempotency — a retried task cannot double-pay a partner). amount = payment.amount × rule.percent / 100, Decimal arithmetic, rounded with Decimal.quantize(Decimal('0.01'), ROUND_HALF_UP).
  • No partner, no entry: if invoice.referral_partner_id is NULL (walk-in), no ledger row is created.
  • Discounts: invoice.discount_amount numeric(12,2) DEFAULT 0 with discount_reason. Because the basis is the paid amount, a discount simply reduces what the patient pays and the ledger naturally reflects the lower amount. There is no separate discount ledger row.
  • Partial payments: each payment produces its own ledger row. No special handling.
  • Refunds: a refund is a new payment row with kind = refund, a positive amount, and method set to how the money was actually returned (cash, bank_transfer, …); every sum treats kind = refund rows as negative. Its ledger entry is a compensating negative share_ledger_entry. If the original period is already closed (settlement.status IN ('APPROVED','SENT','PAID')), the compensating row attaches to the current open period, not the historical one.
  • Settlement: on the 1st at 01:00 Asia/Karachi, Beat enqueues generation via Redis; entries are grouped per partner into a DRAFT settlement with settlement_line rows — that line is the only record of membership, and an entry’s status is derived from it (line on a DRAFT settlement = in-draft; on an APPROVED / SENT / PAID settlement = settled; no live line = pending) — the Lab Owner is notified, and approval (SPA → POST /api/v1/settlements/{id}/approve → finalize task) sets the settlement APPROVED, which is what makes its entries settled, renders the statement PDF (WeasyPrint), stores it at settlements/{partner_id}/{period}.pdf, and only then fires the "settlement approved" webhook that emails the partner (Doc 01 Flow C, as fixed).

Worked example (Decimal only)

Invoice total 10,000.00 PKR (after a 500.00 discount already applied at billing). Partner rule: 20.00%.

#PaymentAmountLedger entryComputationDerived status
1Full payment on a second invoice (no discount)10,000.00+2,000.0010,000.00 × 20.00 / 100 = 2,000.00PENDING
2Partial payment on the discounted invoice4,000.00+800.004,000.00 × 20.00 / 100 = 800.00 — on what was actually paid, not the 9,500.00 totalPENDING
3Refund of payment 2 (patient withdrew one test)4,000.00 (kind refund, method cash — returned the way it was paid)−800.00−4,000.00 × 20.00 / 100 = −800.00 — a new compensating row; row 2 is untouchedPENDING (current open period if row 2's period is closed)

Net partner share for these three events: 2,000.00 + 800.00 − 800.00 = 2,000.00 PKR. All arithmetic in Decimal; every stored amount is numeric(12,2); every percent is numeric(5,2).

13. Audit log

15. Migrations

Ordering (unchanged from Doc 01 §8.6): migrate_schemas --shared runs first (public), then migrate_schemas --tenant on every tenant schema in alphabetical order. django-tenants records applied migrations per schema; there is no custom migration-status table.

ChangeSafe rule
Add columnNullable, or NOT NULL with a DEFAULT that PostgreSQL 16 can backfill cheaply (constant default — no long lock, no table rewrite)
Add indexCREATE INDEX CONCURRENTLY, via a per-schema management command (the workaround for django-tenants: run the concurrent build schema by schema, outside a transaction)
Rename columnThree migrations: add-new + backfill (data command) + drop-old. Never a bare rename
Change typeAdd-new-cast-column + backfill + drop-old. Never ALTER COLUMN TYPE in place
Drop columnTwo-phase: mark deprecated in code, wait one deploy cycle, then drop
Data migrationA separate management command, run after the schema migration completes. Never inside a RunPython that also alters schema
RollbackEvery migration states its rollback. Irreversible migrations require sign-off in Doc 10
Staging rehearsalEvery migration is replayed on staging with a copy of production data before the tag is pushed (Doc 09's rule, repeated here)

TermMeaning
idempotency_key columnA nullable unique column that makes a create safe to retry: the second insert with the same key fails the unique check instead of duplicating the row
before_jsonb / after_jsonbThe changed-field snapshots on an audit row — field names and changed values only, PII hashed or truncated

Append-onlyRows may be inserted but never updated or deleted; enforced in the database with REVOKE, not just by convention (§6)
Compensating entryA new row that cancels an earlier financial row by amount (negative), leaving both visible — how refunds work in the ledger
Effective-datedA row valid for a period (effective_from / effective_to); a change closes one row and opens another instead of overwriting history
