4.3 Token lifetimes, rotation, reuse detection (R2)

Decision: Doc 01 ADR-005 is confirmed. Access token 15 minutes, refresh token 7 days, rotating. The mechanics ADR-005 did not spell out are fixed here.

RuleSpecification
Access tokenJWT, HS256, signed with JWT_SIGNING_KEY (§6). Claims: sub (staff_user id), tenant (slug — informational; the host, not the claim, selects the schema), role, jti, iat, exp = iat + 900. Verified per RFC 8725 (F-4): algorithm allowlist of exactly one, expiry and signature checked on every request, no none, no key confusion — the key is used for HS256 only
Refresh tokenJWT, HS256, same key, 7-day exp. Claims add fid (session family id, minted at login) and typ: "refresh" — a refresh token presented as an access token, or the reverse, is rejected on typ alone
Rotation-on-useEvery successful refresh mints a new refresh token with a new jti in the same family, and marks the presented jti as used in Redis. The old cookie value is worthless from that moment
Reuse detectionA refresh token whose jti is already marked used, or already denylisted, is presented again → treated as theft of the family. Response 401 refresh_reuse_detected. The server revokes every session of that staff_user: all family ids are denylisted and the per-user revocation marker (§4.6) is set to now. A login_event row and a Sentry alert (§11.4) record it; the audit action is auth.sessions_revoked with reason refresh_reuse
DenylistRedis only — no database table (Doc 02 §14). Three key families: used jtis (TTL = the token's remaining life, at most 7 days), revoked jtis from logout (same TTL), and the paired access-token jti at logout (TTL = its remaining life, at most 15 minutes — this is what makes logout immediate instead of "within 15 minutes")
Absolute session capA family dies at 7 days from login no matter how often it refreshes: the refresh exp is never extended past the family's original deadline. Staff log in again at most weekly

Why reuse means "revoke everything". A rotated-out token can resurface for two reasons: the real user's browser raced itself, or a copy exists somewhere it should not. The two are indistinguishable from the server. Revoking all of that user's sessions costs the real user one fresh login; not revoking costs a stolen session that lives for days. The race case is made rare by the SPA: Doc 07's auth module refreshes from one place, and a refresh already in flight is not duplicated.

Failure mode. Redis is the denylist's only home (AS-3). If Redis is flushed or down, used-token memory is lost and a stolen rotated-out token could be replayed once — bounded by the 7-day family cap and by throttles. This is accepted: the alternative (a database table) was already rejected by Doc 02 §14, and §17 records the decision again so it is not re-litigated silently.

4.4 TOTP enrolment and recovery (R3)

TOTP is required for the Owner, Manager and Pathologist roles, and for the Super Admin — the set Doc 01 §14 names. An account in a required role without TOTP enrolled cannot complete login: after password verification it is routed to enrolment instead of a session. All other staff roles may enrol voluntarily. Super Admin TOTP is tracked on platform_user.totp_enabled (Doc 02 §4.1); the requirement is Doc 01 §14's; the enrolment flow is the same shape as this section with platform_user as the subject. The secret lives on staff_user.totp_secret_encrypted and the backup codes on staff_user.totp_backup_codes_hash (Doc 02) — no new storage.

Enrolment flow

  1. The signed-in user requests enrolment — POST /api/v1/auth/totp/enroll (A-25, Proposed). The server generates a fresh secret, stores it pending (not yet active), and returns the secret and otpauth:// URI once, for the authenticator app and the SPA's QR code (Doc 07 renders it; the shape is §17 A-25).
  2. The user enters a code from the app — POST /api/v1/auth/totp/enroll/confirm {code}. On match, the pending secret is encrypted with the Fernet key from LABFLOW_TOTP_ENCRYPTION_KEY (env only, never the database — Doc 02 §14) and written to totp_secret_encrypted; enrolment is active.
  3. The server issues 10 backup codes, shown once, in the confirm response only. Each is stored as an individual argon2 hash in the totp_backup_codes_hash array. A code is single-use: a successful use removes its hash.
  4. Audit: auth.totp_enrolled. The secret, the codes and the QR payload never appear in the audit row, a log line, or a Sentry event (§9, §11).

Verify rules. The challenge created at login lives 5 minutes in Redis and allows 5 attempts; the counter is a Redis key on the challenge, not a column. The fifth failure destroys the challenge (401 totp_challenge_expired) and the user starts again from the password step — which is itself throttled (§10). A backup code is accepted in the same {code} field; the response does not say which kind matched. Codes accept the current 30-second window plus one window either side, for clock drift.

Recovery — device lost. Three paths, in order:

  1. Backup code. The user logs in with one of the 10 codes. They are then prompted to re-enrol (old secret and remaining codes are wiped on re-enrolment) or to finish enrolment later from settings; the account keeps working either way.
  2. Owner reset. If no backup code remains, the tenant Owner resets that staff member's TOTP from staff administration (Doc 04 §15.2 owns staff administration; the reset clears totp_secret_encrypted and totp_backup_codes_hash and forces enrolment at next login). Identity is verified out of band by the owner — they work in the same lab. Audit: auth.totp_reset naming both actor and target.
  3. Owner lockout. If the Owner loses both device and codes, the platform operator resets the owner's TOTP after verifying the owner through the tenant's registered contact channel (Doc 04 §12 support metadata). This is a platform action: it writes platform_audit, and it can only clear TOTP — the operator cannot set a password or read the secret (§5.4). Audit on both sides.

Key handling. LABFLOW_TOTP_ENCRYPTION_KEY is a Fernet key held only in the VPS environment (§6). A database dump alone cannot mint TOTP codes (Doc 02 §14). If the key is lost, every enrolled secret is unreadable: all TOTP users fall back to backup codes or owner reset, then re-enrol under a new key. If the key leaks, it is rotated and every user re-enrols — a forced reset, because old secrets must be treated as exposed (§14).

Failure mode. TOTP verify fails closed: Redis down or challenge state unreadable means no session is issued. There is no "skip TOTP this once" path for any role, including the Owner and the Super Admin.

4.5 Password policy and reset flow (R4)

Policy. Minimum length 12 characters, maximum 128. No composition rules (no required digit/capital/symbol mixes): length is what resists guessing, and composition rules push users to predictable patterns — the ASVS/NIST position (F-1). Two checks apply instead: the password must not appear in a bundled common-password blocklist (checked at set time, 422 password_too_common), and it must not equal the account email. Password managers are neither required nor blocked (§18).

Hashing. argon2id with the RFC 9106 second recommended profile (F-3): m = 64 MiB, t = 3, p = 4, 16-byte random salt, 32-byte tag — Django's Argon2PasswordHasher configured to these values, stored in staff_user.password_hash (Doc 02). The profile targets roughly half a second per verification on the VPS; login throttling (§10) bounds how often an attacker can make the server pay that cost. Hash parameters are stored in the encoded hash, so raising them later rehashes each user transparently at their next login.

Reset flow — password_reset_token, purpose = 'password_reset' (A-14, accepted in Doc 02 v1.3)

  1. POST /api/v1/auth/password-reset/request {email} (A-26, Proposed) on the tenant host. The response is always 202 {accepted: true} — for unknown emails, deactivated accounts and throttled addresses alike. Nothing about the response reveals whether the account exists.
  2. If the account exists and is active: any still-live reset tokens for that user are invalidated, a fresh 32-byte random token is generated, its argon2 hash is stored in password_reset_token with purpose = 'password_reset' and expires_at = now + 60 minutes (Doc 02 §5.11 shape), and the plaintext token leaves the server exactly once — inside the reset email (A-27, Proposed: template key + Doc 06 event).
  3. The link opens the SPA reset page on the same tenant host with the token in the URL fragment, so it is not sent to the server in a Referer or logged in access logs (§8.4). POST /api/v1/auth/password-reset/confirm {token, new_password} (A-26) verifies the hash, the purpose, used_at IS NULL and the expiry — in that order, with one error for all failures: 400 invalid_reset_token.
  4. On success: the new password is policy-checked and hashed (§4.5), used_at is set, all sessions for the user are revoked (§4.6 — a reset is a credential-compromise signal), and audit writes auth.password_reset. The user logs in fresh.
  5. Token rows are deleted 30 days after creation by the existing Beat cleanup (Doc 02 §5.11) — used, expired and superseded rows alike.

The same table and rules serve the other two purposes (A-14): purpose = 'activation' (owner activation, Doc 04 P-8, 72-hour expiry) and purpose = 'email_verification' (24-hour expiry). Only the expiry and the completing action differ; single-use, hashed storage and invalidation of predecessors are identical (§4.7).

Failure mode. A reset email that never arrives (Doc 06 delivery failure) leaves the account untouched — the old password still works — and the user requests again; each request invalidates the previous token, so at most one live reset link exists per user. Reset requests are throttled per email and per IP (§10), failing closed.

4.6 Session invalidation

One mechanism serves every invalidation: the per-user revocation marker in Redis — auth:revoked_before:<staff_user_id> = a timestamp, TTL 7 days (the longest any token minted before it can live). Authentication rejects any token, access or refresh, with iat earlier than the marker. Setting the marker kills every session the user has, on every device, at once.

Where the marker is checked. The revocation marker is checked on privileged writes only — settlements, refunds above the tenant threshold, staff administration, exports, and any write by an Owner account. Routine clinical and financial writes (results, samples, invoices, payments, patient records) skip the marker check during a Redis outage and proceed with a WARN log and alert (§11.4). The reason: the threat the marker defends is a stolen privileged session; the harm of a stolen routine write is bounded by the same audit and idempotency the normal path relies on, while the harm of blocking every write in a lab for a Redis outage is patient-facing.

5. Authorization

5.1 The one rule

Every authorization check is server-side, on every request, with no exceptions. The SPA hides buttons and menu items a role may not use — that is a courtesy to the user, not a control (Doc 07 FP-6). A hand-crafted request from a signed-in receptionist to an owner-only endpoint gets the same 403 as any other forbidden call, and an out-of-branch object id gets a 404 (§5.3). There is no endpoint whose security depends on the client behaving.

5.3 How a forbidden request is answered

  • Wrong role, right tenant: 403 forbidden. The object exists for this user to know about in principle; their role may not act on it.
  • Out-of-branch object: 404 not_found, not 403 (Doc 04 §8.5). A 403 would confirm the object exists in another branch and turn the API into an existence oracle for accession numbers.
  • Cross-tenant object: impossible to address — the id is resolved inside the caller's schema only, so it is a 404 by construction, not by check.
  • Read-only tenant (subscription): writes answer 403 subscription_read_only (Doc 04 §11.2); reads, exports and patient links keep working.
  • Every denial on a sensitive route (settlements, staff administration, exports, refunds) writes an audit row (§9) — a denial is a security signal, not noise.

5.4 The platform boundary, impersonation, and row counts (R7, R13)

Impersonation is not allowed (R7). Doc 04 §12.3 decided this with three reasons; this document restates it as a security decision, because the reasons are security reasons:

  1. Attribution dies. Every tenant audit row names a staff actor (Doc 03 P-3). An impersonated session writes real actions under a borrowed name. From that day, "who did this?" has two answers for every row, and the audit log — the tenant's evidence in any dispute — is worth less for every tenant, forever. A flag on the row does not fix this; it records that the trail is unreliable, which is the problem.
  2. The platform would hold every tenant's keys. Impersonation means a platform credential that can become any staff user in any lab. One compromised platform account becomes all tenants at once — the exact blast radius schema isolation exists to prevent (SP-1).
  3. It breaks the patient-data promise. The Super Admin's access is machinery metadata only (Doc 04 §12). Impersonation hands the operator patient names, results and reports — data Doc 01 promises the platform never sees — as a routine support tool.

Support alternatives (all already in Doc 04): platform metadata (tenant status, schema size, migration state, §5.4 below), the owner-driven export (Doc 04 §4.3 — the owner generates it, the operator never pulls tenant data), and screen-sharing with the owner driving. If none of those can solve a support case, the case waits — that is the accepted cost, stated in advance.

Row counts (R13): NO. The Super Admin may not see per-tenant row counts — patients per month, samples per month, or any other content volume — in v1 or as a standing capability. Schema size and migration state (Doc 04 §12) are the permanent limit. Two reasons. First, counts are business volume: patients-per-month is a lab's commercially sensitive throughput, and the platform has no operational need to know it — capacity planning works on schema size and its growth, which measure the same load without counting records. Second, computing a count requires a platform process to read inside a tenant schema, which breaks Doc 04 TP-4 (the public schema holds the registry; no platform feature reads a tenant table). The line is drawn at machinery versus business, and counts are business. If a support case genuinely needs a count, the Owner reads it from their own screens and shares it — the tenant discloses its own volume; the platform does not take it.

5.5 Read-only mode discovery (R14)

Doc 07 §6.4's SPA learns the tenant is read-only only when the first write fails with 403 subscription_read_only. That is a UX gap Doc 08 was asked to close. Decision: option (a) — A-24 (Proposed, §17): add mode: "full" | "read_only" to GET /api/v1/tenant-status (Doc 04 §6.3). Why (a) over (b) (a subscription_mode field on the login response): tenant-status is unauthenticated and stateless, so the SPA can render the Owner banner on a cold load before login; the mode can also change mid-session (a subscription is reactivated while staff are working), and tenant-status is already the endpoint the SPA polls for tenant state — a login field would go stale in exactly the case that matters. Interim: until A-24 is accepted, Doc 07 §6.4 stands as written — the banner appears after the first failed write, and that lazy path remains in the SPA permanently as the mid-session backstop even after A-24 lands (Doc 07 v1.1 already records this).

Failure mode. Read-only mode is an authorization state, not a security boundary: if the SPA never learns of it, the server still refuses every write. The worst case of the interim is a surprised user, never an unauthorised write.

7. Network and transport

The network shape is Doc 01 §15's; this section states it once, as security rules, and does not change it.

  • Caddy is the only public ingress. It terminates TLS for the apex and every tenant subdomain and is the only process with published ports (80/443). Everything else is reached through it or not at all.
  • Two Compose networks. edge (Caddy ↔ Django, Caddy ↔ n8n UI paths Doc 01 allows) and internal (Django, workers, PostgreSQL, Redis, n8n's engine side). A container on edge cannot open a connection to PostgreSQL or Redis.
  • n8n never reaches PostgreSQL or Redis (Doc 06 §15). n8n receives signed webhooks and posts signed callbacks (§6). It holds no database credential, so a compromised workflow cannot become a database read.
  • PostgreSQL and Redis publish no host port. They listen on the internal network only. Database access from outside the VPS does not exist — administration happens over SSH to the host, then inside the network.
  • TLS 1.2 minimum, Caddy's defaults above that floor. HSTS is §8's.
  • On-demand TLS authorisation is the ask endpoint only (Doc 04 §6.4, /internal/tls-check): Caddy asks before issuing, the endpoint allow-lists known tenant hosts plus the pre-approved apex, and /internal/* is answered 404 from the public side (Doc 01 §15 Caddyfile). This document references that design and does not re-specify it — including its rate behaviour (§10).
  • The patient report path follows Doc 01 §14: the backend checks the report token, then redirects to a pre-signed R2 URL valid about 15 minutes. The token is never sent to R2, and the redirect response carries Referrer-Policy: no-referrer (§8.4).

Failure mode. The single VPS is a single point of failure — accepted in Doc 01 and not re-litigated here. If Caddy stops, the platform is down but nothing is exposed: every other service is unreachable from the internet by construction, so an ingress failure fails closed for confidentiality while it fails open for nothing.

8.2 CSRF

API calls need no CSRF token. They authenticate with an Authorization: Bearer header. A cross-site page cannot set that header without a CORS preflight, and there is no CORS (§8.5) — so a forged cross-site request arrives with no token and gets 401. CSRF needs an ambient credential, and the API has none.

The three cookie-carrying routes (refresh, logout, totp/verify — the challenge cookie) are the exception, and they are defended in two layers:

  1. SameSite=Lax on both cookies (§4.1): a cross-site POST does not carry them (F-6), so the forged request has no credential to ride on.
  2. An Origin check: if an Origin header is present on one of these routes and is not the request's own origin, the answer is 403 csrf_origin_mismatch. Browsers always send Origin on POST; its absence means a non-browser client, which the HMAC-less public routes do not serve anyway.

Together these are sufficient for a same-origin SPA; a synchroniser-token pattern would add a token-distribution problem to defend three routes that SameSite already covers. Failure mode: a browser too old for SameSite still gets the Origin check; a client with neither gets refused, and the SPA (a modern browser by Doc 07's support matrix) is unaffected.

8.3 Content-Security-Policy

The policy is a CSP Level 3 strict policy (F-5). The strategy is hash-based: the Vite build inlines exactly one boot script in index.html; the deploy script computes its SHA-256 and writes it into the Caddy configuration, so the header and the page can never drift apart — a build whose boot script changed without a header update fails the deploy smoke check (§15.2 SE-18). A per-response nonce was the alternative: it needs the edge to rewrite HTML per request, which fights the static-file serving and immutable-asset caching Doc 01 §15 chose. Hashes give the same guarantee for a static SPA.

Content-Security-Policy:
  default-src 'self';
  script-src 'self' 'strict-dynamic' 'sha256-<boot-script-hash>';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: blob:;
  font-src 'self';
  connect-src 'self' https://o*.ingest.sentry.io;

  base-uri 'self';

  • script-src: no 'unsafe-inline'. The hashed boot script may load further scripts ('strict-dynamic') — those are the Vite bundles from 'self'. Any other inline script, including an injected one, does not run.
  • style-src 'unsafe-inline' is the deliberate exception: the component library sets inline styles at runtime, and style injection cannot execute script or exfiltrate to a network destination under connect-src 'self'. The script policy carries the security weight.
  • connect-src: the API is same-origin; the one external destination is the Sentry ingest host for the SPA's error events (§11). If the Sentry project region changes, this value changes with it — it is a Doc 08 value, updated here, not in code.
  • img-src data: blob:: label previews and generated images render from in-memory blobs (Doc 07); report PDFs are downloads and redirects, never framed content, so no storage origin is allowed anywhere in the policy.
  • Rollout: report-only first. The policy ships as Content-Security-Policy-Report-Only for the first release, with violations collected as Sentry events (tagged csp_report, quiet — §11.4). It is promoted to enforcing when two consecutive weeks show no violation that is not a browser extension (F-5's known noise source). The promotion decision and its timing belong to the launch checklist (OQ-51, Doc 10).

8.4 Cookies — the complete set

The application sets exactly two cookies, both in §4: labflow_refresh and the TOTP challenge cookie (same flags, 5-minute Max-Age, Path=/api/v1/auth). Both are HttpOnly; Secure; SameSite=Lax, host-only. No analytics, preference or tracking cookies exist in v1, so no other Set-Cookie should ever appear — the §15.2 header test asserts the full response header set, cookies included.

8.5 CORS

There is no CORS. SPA and API share one origin (Doc 01 §15), so the server sends no Access-Control-* headers at all, and cross-origin browser calls fail in the browser before they matter. Server-to-server traffic (n8n callbacks) is not CORS traffic — it is HMAC-authenticated (§6, Doc 06 §13). Any future need for a second origin (a separate patient portal host, a mobile app webview) is an amendment to this section, not a configuration tweak.

9. Audit log

9.1 The write contract (R9)

Doc 02 §13 defines the audit_log row; Doc 03 P-3 states the rule ("every write is audited"); this section fixes the shared contract every module's audit points (Doc 03 §6.1, Doc 04 §15, Doc 05 §10) write under.

  • Which requests write. Every non-GET request under /api/v1/ that changes state writes exactly one audit row, in the same database transaction as the change. If the audit insert fails, the transaction rolls back — there is no such thing as an unaudited write that succeeded. Failed requests (4xx/5xx before commit) write no row, except the security denials §5.3 names, which write in their own transaction.
  • Which reads write. Reads are not audited by default. The audited reads are the sensitive ones the modules already named: patient detail view and report download/preview (Doc 03 §6.1), settlement statement download (Doc 05 §10), and owner export download (Doc 04 §15). Read-audit rows carry before_jsonb = NULL and an after_jsonb holding only the entity reference (§9.2).
  • Platform actions write to platform_audit in the public schema (Doc 02 §4.1), never to a tenant's audit_log — the operator's actions and the tenant's actions are separate trails with separate readers (§5.4).
  • Row shape (Doc 02 §13, unchanged): actor (staff_user id + role snapshot), branch id where the action is branch-scoped, action (the module's dotted name, e.g. billing.payment_recorded), entity_type, entity_id, before_jsonb, after_jsonb, IP, request_id (the X-Request-ID of Doc 01 §11 — the thread that ties an audit row to its log lines and its Sentry event, §11), created_at.

Money is scrubbed from Sentry (§11), not from the tenant's own audit trail

Size capsAny string value is truncated at 200 characters (with a … marker in the stored value), arrays at 20 entries, nesting at 3 levels. The audit row describes a change; it is not a snapshot store

9.3 The correlated hash

One function, used by the audit log (§9.2) and the Sentry scrubber (§11.3): phash(value) = "h:" + first 16 hex chars of HMAC-SHA256(key, value), where the key is derived from DJANGO_SECRET_KEY by HKDF with the fixed label labflow-phash-v1. Properties that matter:

  • Correlation without recovery. The same phone number always hashes to the same h:… value, so an investigator can prove that the patient in an audit row, an error event and a second audit row is the same patient — without any of those places holding the number.
  • Keyed, therefore not enumerable. Phone numbers and MRNs have small search spaces; a plain SHA-256 of one could be reversed by trying every candidate. An HMAC cannot be tested without the key, and the key never leaves the server environment (§6).
  • Not encryption. There is deliberately no way back. If the value itself is needed, the investigator goes to the record itself, inside the tenant schema, under the normal access rules — the hash is a signpost, not a copy.

9.4 Enforcement and retention

Enforcement is the database's. At provisioning and by migration, the application role's UPDATE and DELETE on audit_log are revoked per schema (Doc 02 §6, F-8). The app can INSERT and SELECT only. Even a fully compromised application process cannot rewrite or erase history through its own connection — it could only append false rows, which is why audit rows are read alongside login_event and platform logs in any investigation (§14).

Retention. 24 months hot in the tenant schema (Doc 02 §13). Monthly, the retention job (§13.3) exports rows older than 24 months to an age-encrypted archive object in R2, verifies the object, then deletes the exported rows — the one sanctioned DELETE on audit_log, run by the ops role, not the app role. Archived audit is kept to a total of 5 years, then destroyed (§13). Platform audit follows the same clock in the public schema.

The archive has its own key. Archived audit objects are encrypted with a dedicated age recipient — separate from the backup recipient — whose identity is held 5 years (§13) and never rotated while any archive encrypted to it remains. The split exists because the two clocks differ: archived audit is cold, write-once, and has a 5-year clock; backups are hot, rewritten nightly, and have a 35-day clock. One shared key would force either yearly re-encryption of 5-year-old archives or keeping every rotated backup key for 5 years — both worse than one key per purpose (§6, §12.2).

Failure mode. If the monthly archive export fails, rows stay hot and the job alerts — the archive never deletes what it has not verified in R2. Audit storage growth is therefore a cost problem before it can become a data-loss problem.

10.2 What throttling is not

Throttles are abuse brakes, not quotas: no tenant is billed, warned or shaped at these levels in normal use — the numbers sit far above a busy branch's real traffic, and §15.2's tests assert that legitimate flows (a reception desk at morning peak, a family opening a report link) never touch them. Plan limits (branches, users) are Doc 04 §11's, enforced as product rules, not here.

10.3 Failure behaviour, stated once

  • Auth surfaces fail closed. Login, TOTP and reset without working counters would be unthrottled credential endpoints. They stop instead (SP-3).
  • Reads fail open. A Redis outage that also blocked reads would turn a cache failure into a platform outage. Reads proceed; the gap is logged, alerted, and bounded — Redis is a Compose service on the same host, so its outages are the operator's to fix in minutes, and the denylist loss is §4.3's accepted risk.
  • The revocation-marker check (§4.6) is narrowed to privileged writes. The revocation marker is checked on privileged writes only — settlements, refunds above the tenant threshold, staff administration, exports, and any write by an Owner account. Routine clinical and financial writes (results, samples, invoices, payments, patient records) skip the marker check during a Redis outage and proceed with a WARN log and alert (§11.4). The reason: the threat the marker defends is a stolen privileged session; the harm of a stolen routine write is bounded by the same audit and idempotency the normal path relies on, while the harm of blocking every write in a lab for a Redis outage is patient-facing. A privileged write during an outage still fails closed (503); read access may outlive revocation by at most the outage's length.

11.2 The rule

No patient name, phone, MRN, accession ID, result value, or money figure ever leaves the process in a Sentry event (Doc 01 §14, Doc 07 §1.5). Neither does a password, token, secret, signed URL or PDF payload. An event answers "what broke, where, for which tenant, under which request" — and the request_id tag is how the operator walks from the event to the server logs, where the full (access-controlled) picture lives. Sentry is a third-party service holding none of the platform's data by design, not by trust.

11.3 The before_send scrubber (R8)

Both SDKs run the same algorithm (F-7: scrub in the SDK, before anything leaves). The Django implementation is the reference; the React one mirrors it field for field.

  1. Drop wholesale. Stack-frame local variables are removed from every frame, on both sides. Scrubbing individual locals is a losing game — any variable can hold anything — so the category goes.
  2. Drop the request body and query string. The Django event keeps the route template (/api/v1/samples/{id}/), method and status — never the raw path (it carries ids), never the query string (it carries search terms, which are patient names), never the body. The SPA event keeps the route pattern from the router, never location.href.
  3. Walk what remains (extra data, contexts, breadcrumbs, exception chain) recursively, key by key, case-insensitively:
    • Drop-list — value replaced by [Filtered], never hashed: any key containing password, token, secret, authorization, cookie, pdf_base64, signed_url. A hash of a low-entropy secret is a guessing oracle; these values have no correlation value worth that risk.
    • Hash-list — value replaced by phash(value) (§9.3): keys containing patient_name, name in a patient context, phone, mobile, cnic, mrn, accession, email, result_value, value in a result context, and every money key (amount, total, discount, share, price, balance, refund — the list is a code-level constant, reviewed when a module adds a money field). Correlation survives (the same value hashes the same), recovery does not.
    • Allow-list — kept as-is: request_id, tenant_slug, staff_user_id and entity_id (UUIDs — pseudonymous, and the operator needs them to find the record), role, status codes, exception class names, counts and durations.
    • Anything not on a list: strings longer than 200 characters are truncated; unknown structured values are replaced by their type name. Default is suspicion, not trust.
  4. Breadcrumbs are kept only for navigation and API-status events, with URLs reduced to route templates as in step 2. Console breadcrumbs are disabled on the SPA — console output is uncontrolled text.
  5. The scrubber is tested like a security control (§15.2 SE-30–SE-32): a fixture event carrying one of every forbidden field must emerge with none of them present, in either implementation.

Sentry's server-side data-scrubbing settings are also enabled as a second layer (default PII rules on), but they are not the control: they run after data has left the process, which §11.2 forbids relying on.

12. Backup, restore, disaster recovery

12.1 The backup unit and the job (R10)

The unit is Doc 04 §14.1's: one pg_dump per schema — the public schema and each tenant schema separately, the same unit as provisioning, migration and deletion. Nightly (Doc 01 §15), the backup job on the VPS runs, in order:

for each schema in (public, tenant_<slug>...):
    pg_dump --schema=<schema> --format=custom --file=<tmp>/<schema>.dump
    age --recipient "$AGE_RECIPIENT_BACKUP" --output <tmp>/<schema>.dump.age <tmp>/<schema>.dump
    sha256sum <schema>.dump.age >> manifest.txt        # name, size, SHA-256 per object
    upload to R2: backups/daily/<yyyy-mm-dd>/<schema>.dump.age
upload manifest.txt beside the objects
delete local plaintext dumps (same run — plaintext never survives the job)
  • Where backups land: the R2 backups bucket under one flat backups/ prefix — daily/<date>/ and weekly/<date>/. There is no per-tenant folder hierarchy above the object name: the schema name inside the filename is the unit, and nothing about the bucket layout groups or ranks tenants (tenant prefix-free, as Doc 04 §14.1's format decision set).
  • Retention: 7 daily + 4 weekly (Doc 01 §15) — a Sunday run is also copied to weekly/. Maximum rotating age is therefore 35 days. Deletion of expired prefixes is part of the same nightly job and is logged.
  • A failed schema fails loudly. The job writes one manifest line per schema; a missing or zero-size object, or an upload error, aborts the run's "success" state and pages the operator (§11.4). A partial night is recorded as partial, never presented as complete.

12.2 The age key (R10)

  • What exists: two age keypairs for the platform (F-9), one per purpose (§6, §9.4). The backup recipient (public) sits in the VPS env as AGE_RECIPIENT_BACKUP — the backup job can encrypt and can never decrypt. The audit-archive recipient sits beside it as AGE_RECIPIENT_AUDIT_ARCHIVE — the retention job encrypts archived audit to it (§9.4).
  • Where the identities live: both identities live on the operator's own machine (encrypted disk), each with one offline copy (a printed key or a USB stick in a sealed, labelled envelope, stored away from the machine). Neither is ever on the VPS, in R2, or in the repo. Losing both copies of an identity makes its objects undecryptable — which is why there are two copies, in two places, and why the drill (§12.3) verifies the backup identity's offline copy once a year by actually using it.
  • Who has it: the platform operator only (AS-1). No tenant ever holds it; tenants' protection from backup exposure is the encryption itself, not key distribution.
  • Rotation: yearly, or immediately on suspicion of exposure. New pair generated offline; the recipient is swapped in env; new backups encrypt to the new key. The old backup identity is kept until the last backup under it ages out — at most 35 days (§12.1) — then destroyed. Rotation never re-encrypts old backups: they expire on schedule instead. Backup identity: rotates yearly (§12.2's main rule). Audit-archive identity: never rotated in v1 — the 5-year archive clock is its own custody rule, and rotating it would force a bulk re-encryption job the platform does not need.

Failure mode. Stolen R2 credentials (§6) yield ciphertext only. A stolen identity is the one backup catastrophe: it is handled as an incident (§14), and the response is a new keypair plus credential rotation — the already-exposed backups cannot be un-exposed, which is exactly why the identity never touches the server.

12.3 Restore

  • Per-tenant restore follows Doc 04 §14.3: download the schema object, decrypt off the VPS copy path (the operator supplies the identity at restore time), restore into a quarantine schema, verify (row counts against the manifest era, migration state, a login smoke test as the owner), then swap. RPO 24 h, RTO 1 h per tenant (Doc 04).
  • Monthly restore drill (Doc 01 §15, Doc 04 §14.3): the largest tenant's latest backup is restored to a scratch schema on the VPS and verified the same way, then dropped. The drill result (schema, backup date, duration, pass/fail) is written to platform_audit. A failed drill pages the operator and is not retried silently — an unproven backup is treated as no backup.
  • Full-platform recovery (Doc 04 §14.3): new VPS → install Compose stack → restore public schema → restore tenant schemas alphabetically → restore R2 report objects' bucket state (objects were never lost if R2 is intact; if the bucket is the loss, reports are re-derivable only from the database state — stated honestly: report PDFs are generated artefacts, and Doc 03's report regeneration is the recovery path) → point DNS/Caddy at the new host → on-demand TLS re-issues per tenant (§7). The env file and the age identity come from the operator's copies (§6, §12.2) — they are the two things no backup contains, by design.

12.4 OQ-38, answered here

After a tenant's schema is dropped (Doc 04 §4.2), two things still hold that tenant's data: the final export bundle and the rotating backups that contain the dropped schema. The export bundle is kept 90 days, then destroyed. The rotating backups are not purged per-tenant — they age out on the §12.1 schedule, so no backup containing the schema survives past 35 days. The full reasoning and the destruction mechanics are §13's; this section records that no special backup handling exists beyond rotation, deliberately: per-object surgery inside encrypted, shared backup sets would risk every other tenant's restore integrity to accelerate one tenant's exit by at most a few weeks.

13.2 The two paths, stated plainly

While a lab is a customer: archive, never delete. Clinical and financial records are kept whole; the only deletions are tokens, throttles and other exhaust with short clocks. When a lab leaves: export, grace, drop, destroy on a clock. The difference is consent and purpose — a customer's records are held for them; a former customer's records are held only as long as the exit process honestly requires, and then they are gone, with the destruction itself on the record.

13.3 Deletion mechanics

  • Monthly retention job (Beat, per tenant schema + the public schema): archives audit_log rows past 24 months (§9.4), deletes login_event rows past 24 months, deletes archived-audit objects past 5 years. Each action writes one summary row — action retention.archived / retention.destroyed, counts only, no content — into audit_log (or platform_audit for platform-side objects). The record of destruction survives the destroyed data; the summary rows themselves are never retention-deleted.
  • Offboarding destruction is the Doc 04 §4.2 ops script plus one step this document adds: at drop + 90 days, the same script deletes the retained export bundle and writes platform_audit action tenant.retention_completed with the bundle's manifest hash — proving what was destroyed without keeping any of it.
  • Nothing deletes on a user's request inside an active tenant. There is no "delete this patient" endpoint in v1 (Docs 03–05 define none). Correction flows (amend, void, supersede) are the v1 answer to bad data; erasure of a live clinical record is a legal question Pakistan's draft law has not yet settled (F-10), and the platform does not improvise it.

19. Interview talking points

The eight decisions in this document worth being able to defend out loud. Each states the decision, the defence, and the alternative that was rejected.

  1. JWT access + httpOnly refresh cookie + rotation-on-use + reuse detection (§4.1, §4.3). The SPA and API share one origin, so the classic objection to JWTs (where do you store the refresh token safely?) has a clean answer: an httpOnly, host-only cookie the browser guards for us. Stateless access tokens keep every API call free of a session lookup; rotation-on-use bounds a stolen refresh token to a single use; and reuse detection turns "a token appeared twice" into a full revocation, because a rotated token resurfacing is indistinguishable from theft. Server sessions would give instant revocation but cost a stateful lookup per call and still need the same cookie — the JWT design keeps the cookie and drops the lookup. Rejected: opaque session tokens with a server-side session store, and refresh tokens in localStorage (readable by any XSS, in a document that forbids patient data in browser storage for the same reason).
  2. Impersonation is refused — as a security decision, not a support preference (§5.4). The audit framing (Doc 04 §12.3) is that borrowed identity corrupts the trail. The security framing is sharper: impersonation is a standing privilege-escalation path from one platform account to every tenant, and it makes the platform a holder of patient data it promises never to hold. Support survives without it — metadata, owner-generated exports, screen-share. Rejected: impersonation with an audit flag and a time limit — the flag documents the escalation path; it does not close it.
  3. The Sentry scrubber hashes identifiers instead of dropping them (§9.3, §11.3). Dropping is safer per-field and useless in practice: an error event that cannot be tied to a patient, an accession or an amount cannot be investigated. The keyed HMAC gives correlation — the same value always produces the same tag — with no recovery path, because testing a guess needs the key, and the key never leaves the server. Passwords and tokens are dropped outright: their correlation value is zero and their guessing space is small. Rejected: sending raw values to a "trusted" Sentry (a third party holding patient data by policy), and plain SHA-256 (enumerable for phone numbers and MRNs).
  4. Rate limits fail open for reads and closed for auth (§10.3). The two failures are not symmetric. A read outage during a Redis failure strands a lab mid-clinic — a patient-safety problem. An unthrottled login endpoint during the same window is a credential-guessing invitation. So auth stops and reads continue, and the asymmetry is written down so nobody "fixes" it into uniformity later. Rejected: fail-closed everywhere (turns a cache failure into a platform outage) and fail-open everywhere (removes the only brake exactly when the system is already degraded).
  5. The tenancy check is the schema, not the application (§5, SP-1). Application-level tenant filters fail the way all hand-written checks fail: the tenth endpoint forgets. Schema-per-tenant makes the database itself refuse the question — a query in the wrong schema returns nothing because the data is not there, and PgBouncer's transaction-mode risk is handled with Doc 04's guardrails and an interleave test rather than by weakening the model. Rejected: shared tables with a tenant_id column and disciplined filtering — the discipline is the vulnerability (OWASP's #1 risk is broken access control, F-2).
  6. "No password-manager guidance" is fine; "no password reset flow" would not be (§4.5, §18). A password manager is the user's own tooling — the platform's job is to not obstruct it (long maximum length, paste allowed, no composition rules fighting the generator). A reset flow is different: it is an authentication path in its own right — it mints a session-equivalent from an email — so it gets the full treatment: hashed single-use tokens on the accepted A-14 table, purpose separation, non-enumerating responses, and total session revocation on completion. Features that authenticate get specified; preferences that don't, don't. Rejected: security questions and emailed temporary passwords, both weaker than the token flow and both older than the threats.
  7. Row counts are refused because they are business volume, not content-free metadata (§5.4, R13). The Super Admin line is machinery: schema size, migration state, tenant status. Patients-per-month sounds like the same kind of number and is not — it is a lab's throughput, commercially sensitive, and reaching it requires the platform to read inside tenant schemas, breaking the rule (Doc 04 TP-4) that keeps every other platform feature honest. The line matters because it is drawn where it costs something: support would genuinely like the counts. Rejected: a counts endpoint "for support only" — a capability that exists will be used routinely, and its existence, not its intent, is the exposure.
  8. Retention is archive-not-delete for customers and delete-on-a-clock for leavers (§13.2). The two paths differ because the relationship differs. A current lab's rejected samples, superseded reports and audit rows are its clinical memory — destroying them on a storage schedule would trade medico-legal evidence for disk space. A departed lab's data is held only to complete the exit honestly: export, 90 days to ask again, then destruction with the destruction itself on the record. The same platform that refuses to delete a live record also refuses to keep a dead one — both refusals are the tenant's data being treated as the tenant's. Rejected: uniform retention for everything (deletes live clinical history) and keep-everything-forever (makes offboarding a fiction).
