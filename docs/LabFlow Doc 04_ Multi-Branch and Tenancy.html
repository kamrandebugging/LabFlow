4. Tenant model and lifecycle

One tenant row per lab or chain (Doc 02 §4.1): id, slug (unique; subdomain and schema suffix), name, schema_name (unique; tenant_<slug>, stored, never recomputed), status, timestamps. 4.3 Offboarding

Offboarding is a procedure, not a button. It follows the order in F-11: export first, then closure, then deletion, with a grace period between the last two.

  1. Start. Super Admin calls POST /api/v1/platform/tenants/{id}/offboard. The tenant is suspended — staff access stops at once, not at month-end: departing staff must not keep writing into a record about to be exported. platform_audit: tenant.offboarding_started.
  2. Export. A Celery task (tenants.export_tenant, maintenance queue) runs in the tenant context and produces the owner's copy: one CSV per tenant table (the full record, not a summary), every report PDF at its stored pdf_key, and a manifest.json naming every file with row count or byte size and SHA-256 checksum. Secrets are never exported. The following columns are excluded from every CSV, without exception: password_hash (in staff_user), totp_secret_encrypted and totp_backup_codes_hash (in staff_user), and every token_hash column — in password_reset_token, report_access_token and any other token table. An export that carried password hashes or live token hashes would hand anyone holding the bundle working credentials and report links. The manifest records exactly which columns were excluded and why — excluded for security, not missing through corruption — so an absent column is never mistaken for lost data. The bundle sits under the tenant's storage prefix (§13.4), delivered to the Lab Owner via a signed download link valid 7 days — the report-link pattern. The Super Admin triggers it but never receives it (§12.2). platform_audit: tenant.export_generated with file count and total bytes — counts only.
  3. Grace period: 30 days. The tenant stays suspended, data intact; reactivation is one Super Admin action (§16, workflow 2). The owner is told in writing the exact drop date, and that patient links stop that day.
  4. Schema drop. After grace, the Super Admin calls POST /api/v1/platform/tenants/{id}/complete-offboarding with an explicit confirmation flag. An ops script (not request-handling code) then: takes a final per-schema pg_dump (§14.1 format) into the backups prefix; verifies it exists and is non-empty; runs DROP SCHEMA tenant_<slug> CASCADE; deletes the tenant's storage prefix except the final export bundle, kept for Doc 08's retention period (OQ-32, OQ-38); sets tenant.status = deleted; deletes the domain rows. platform_audit: tenant.schema_dropped. The tenant row itself is never deleted — it records that this lab existed, and its export and drop dates.
  5. Confirmation. The owner receives written confirmation naming the export date, the drop date, and what was retained (platform_audit rows, backup rotation §14.1).

Backups are not an escape hatch. After the drop, nightly dumps age out on the normal rotation (Doc 01 §15); restoring a deleted tenant inside that window is a Super Admin decision recorded in platform_audit. After rotation the data is gone — stated in the confirmation.

5.1 Slug rules and reserved subdomains

The slug does two jobs — subdomain label and schema suffix — so it gets one conservative alphabet: ^[a-z][a-z0-9]{2,29}$ (lowercase letters/digits, starts with a letter, 3–30 chars). No hyphens: legal in a subdomain, not in an unquoted PostgreSQL identifier. Allowing them would need a permanent slug→schema mapping.

Reserved slugs are refused at P-1 even if unused: platform/service names (www, api, admin, app, platform, internal, static, media, assets, cdn, n8n, sentry, minio, staging, health, metrics), account words (login, signup, register, account, billing, support, help), mail/protocol names (mail, smtp, imap, ftp), system words (public, tenant, tenants, system, root, labflow, test, demo, example, null). One constant in the tenants app, checked by set membership; TN-02 pins the list so it cannot quietly shrink.

5.2 Timing and failure posture

Per-step durations are logged with the tenant slug (§17); P-4 dominates, P-6 is second. A run over 3 minutes alerts but is not killed. A stuck tenant shows on the platform list, failed step named — no silent stuck state. Cleanup for abandoned provisioning is the provisioning → deleted transition (§4.2): the ops script drops any created schema; registry rows stay as the record.

6. Request-time tenant resolution

6.1 Host to tenant

Resolution is django-tenants' TenantMainMiddleware, first in the chain (Doc 01 §11): the host is matched exactly against domain.domain (uq_domain_domain), the tenant's schema becomes the search_path, the URLconf is selected. Two URLconfs exist (F-3):

  • Public URLconf (PUBLIC_SCHEMA_URLCONF) — served on the apex host and any unmatched host that is still ours: the platform API (§15.1), platform admin screens, /internal/tls-check (§6.4). Runs against the public schema.
  • Tenant URLconf — served on tenant hosts: the whole Doc 03 API, staff auth, the patient report-access endpoint — inside the tenant's schema. Platform routes do not exist here: a platform path on a tenant host is a plain 404.

The app split mirrors the URL split: SHARED_APPS = django-tenants, the tenants and platform_admin apps, contenttypes; TENANT_APPS = the Doc 01 §7 tenant modules (accounts, patients, branches, catalog, billing, samples, results, reports, partners, notifications, audit, automation). A model in the wrong list puts its table in the wrong schema.

6.2 Unknown host

A host with no domain row gets a generic 404 — never a fallback to a default tenant, never a redirect to a "nearest" one.

6.3 Provisioning and suspended tenants at request time

After tenant resolution, one middleware check reads tenant.status:

  • provisioning → 503 tenant_provisioning for every tenant-API path except GET /api/v1/tenant-status, which returns {slug, name, status} so the SPA can render its "setting up" page. That endpoint is unauthenticated; it returns only what the host already reveals.
  • suspended → 403 tenant_suspended for staff paths. Two exemptions: GET /api/v1/tenant-status (the SPA renders the suspension notice) and the patient report-access path (TP-8). The check runs before JWT authentication: suspended staff get the suspension answer, not a login prompt, and no session work happens against a suspended schema.
  • Read-only mode (§11.2) is a second, separate gate, running after authentication: it blocks writes, not access.

6.4 The TLS ask endpoint

Caddy obtains certificates on demand (Doc 01 §8, §15). Before issuing, it calls GET http://backend:8000/internal/tls-check?domain=<host> on the internal network. The Caddyfile refuses external access to /internal/* with a 404 (Doc 01 §15), so the only caller is Caddy. The logic is deliberately tiny — one fixed allow-list entry, then one indexed lookup:

  1. The apex is pre-approved. If the host is exactly labflow.app, answer 200. The apex is a fixed entry in the ask endpoint's allow list — a constant in code, not a domain lookup and not a wildcard. It must be there: Doc 01 serves the platform admin on the apex, and Doc 01's Caddyfile places the apex in the on-demand block — without this entry the platform admin's own certificate would never issue.
  2. Otherwise, the host must be exactly one label under the platform base domain (<label>.labflow.app). Anything else — two labels deep, a foreign domain — is refused (F-7: no nested subdomain is ever approved).
  3. The host must exist in domain with tenant status provisioning, active or suspended. (A deleted tenant has no domain rows left, so it fails by construction.)
  4. Step 1 true, or steps 2 and 3 both true → 200; anything else → 404, no body, no reason.

Abuse protection, in layers (F-7, F-8): (a) exact-match only — no code path approves an unregistered host; (b) negative answers cached in Redis for 60 s (platform:tls-ask:miss:<host>), so scans cannot hammer the database; (c) Caddy's on_demand_tls gets interval and burst limits (A-12) — with ask set, the only throttle on issuance itself (F-8); (d) misses counted hourly and alerted (§17) — a spike means a scan or a DNS mistake; (e) issuance failures (F-9) logged, never retried by provisioning.

6.5 Custom domains (v2)

Custom domains (reports.citylab.pk) are a Doc 01 non-goal for v1. The door stays open cheaply: domain already holds many rows per tenant, so resolution needs no change. What v2 must add first is ownership verification (a DNS TXT challenge): the ask endpoint must never return 200 for an unverified host. Until then, §6.4 steps 2–3 refuse every non-platform host; the only fixed approval is the apex itself (§6.4 step 1).

7. Migrations across tenants

Fleet migrations are the deploy script's job, never a Celery task (§1.4, finding 6) and never a request-path event. The order is Doc 01 §8.6 and Doc 02 §15, made operational:

7.1 Deploy script order

  1. Gate checks. Last night's backup exists (§14.1); no other deploy running (CI lock — one at a time); the tag passed the staging rehearsal (§7.4), timings attached.
  2. Shared migrations. migrate_schemas --shared against the public schema, on a direct PostgreSQL connection (§13.5).
  3. Tenant migrations. migrate_schemas --tenant, schema by schema in alphabetical order (Doc 02 §15), each schema's result (applied list, duration) in the deploy log. Application containers are not yet updated: old code runs on new schemas, safe only because every migration obeys §7.2.
  4. Data commands. Backfills run now, as separate management commands after the schema migrations (Doc 02 §15) — batched (§7.2), per schema, logged per schema.
  5. Roll out the new code. Application and worker containers update. Beat restarts last, so no scheduled task fires against a half-deployed fleet.
  6. Smoke check. One tenant-status request per tenant host (§6.3) plus the platform tenant list. A failing tenant is named in the deploy report, never skipped silently.

7.2 Long-migration rules

  • Backward-compatible only. Every migration must run safely under the previous release's code (expand → migrate data → contract, per Doc 02 §15: add-new + backfill + drop-old across two deploy cycles; never a bare rename, never ALTER COLUMN TYPE in place, never NOT NULL without a cheap default)
  • Per-schema time budget: 30 seconds. A migration whose rehearsal exceeds 30 s of lock time on the largest schema does not ship as a normal migration: split it (schema now, batched data command after) or make it a maintenance-window job. Fleet cost is per-schema time × tenant count (F-1).
  • Indexes are built concurrently, per schema. CREATE INDEX CONCURRENTLY cannot run inside a transaction or a normal migration, so it goes through Doc 02 §15's dedicated command (worked example 2): add_index_concurrently --app … --index … loops the schemas, checks pg_indexes first (resumable after a crash), builds outside a transaction. DROP INDEX CONCURRENTLY is the rollback.
  • No data work inside schema migrations. A RunPython that also alters schema is forbidden (Doc 02 §15). Backfills are commands: batched at 5,000 rows, each batch its own transaction, progress logged per schema, safe to kill and re-run.

7.3 When one tenant fails

The fleet run halts on the first failing schema: migrations in one release can depend on each other, the fleet is small (AS-1), and old code is safe against both shapes (§7.2) — stopping costs little, hides nothing. The failing schema keeps serving on old code; migrated schemas serve old code on the new shape; the rest are untouched The report names schema, migration and error (F-2).

Recovery is fix-forward: fix the data or the migration, then re-run the script — applied schemas are no-ops (django_migrations is per schema) — or re-run one schema (migrate_schemas --tenant --schema=tenant_<slug>). Nobody edits tenant data to "make it pass" without recording the fix in the deploy report.

7.4 Rollback and staging rehearsal

Rollback. Every migration states its rollback (Doc 02 §15). Fleet rollback = redeploy the previous tag, then migrate_schemas backwards per schema (tenant schemas first, then shared, so no schema sits behind the code that reads it). Irreversible migrations need Doc 10 sign-off before they merge; the contract step of a two-phase change is the usual point of no return, so it waits a full deploy cycle.

Staging rehearsal. Before a tag is pushed, every migration is replayed on staging against a copy of production data (Doc 02 §15) — all schemas, in order, timed per schema, with the report attached to the tag.

8. Branch model

Doc 03 §4 fixed the branch rules (BS-1 to BS-6) and the permission matrix. This section fixes the model underneath them: what a branch is, what each kind can do, how branches open and close, how staff are assigned, and how scope is enforced in code.

8.1 One table, two kinds

A branch is a branch row (Doc 02 §5.1): id, code (3 chars, unique per tenant — uq_branch_code — used in MRNs, Doc 02 §9), name, address, phone, is_collection_centre (boolean, default false), deleted_at (soft delete). A collection centre is the same row with is_collection_centre = true (OQ-27). There is no second table, no type hierarchy: the kinds differ in capabilities, not shape — a centre that grows an analyser is promoted by flipping one boolean, history, MRNs and samples untouched.

The hub-and-spoke shape of real lab chains (F-15). The model records no centre's "hub" — any processing branch may receive from any centre (§9.1).

result_entry_enabled semantics (A-8). A processing branch enters results per the Doc 03 role rules regardless of branch.result_entry_enabled. Only when is_collection_centre = true does the flag gate entry — default false, owner must turn it on (Doc 03 OQ-27, Doc 02 v1.3 A-8). So the default does not break a fresh tenant: a new processing branch enters results from day one, and only a collection centre is held back until the owner enables it. Doc 03 RS-3 enforces the gate: at a collection centre with the flag off, entry is refused with 403 result_entry_disabled_at_branch.

8.2 Branch codes

code is exactly 3 characters, uppercase letters and digits, chosen by the Owner at creation, and immutable once any patient or sample references the branch: it sits inside every issued MRN (MRN-{code}-{seq}, Doc 02 §9). Name, address and phone are editable (audited). A lab needing a new code opens a new branch and closes the old one (§8.3).

8.3 Closing a branch

Closing is Doc 02's soft delete: the Owner sets deleted_at (§15). Preconditions, checked in the close transaction: no open transfers in or out (§9.2), no samples held there in collected, received or in_process. Effects: the branch leaves pickers and default queries (the scope layer filters deleted_at IS NULL, §8.5); its staff_branch rows remain but grant nothing; its invoices, samples and reports stay readable by ID (FKs are RESTRICT). Reopening: the Owner clears deleted_at (audited), allowed whenever the row exists.

8.4 Staff assignment

Assignments live in staff_branch (Doc 02 §5.1): composite PK (staff_user_id, branch_id), is_primary. Rules:

  • SB-1. Branch-scoped roles (manager, reception, technician) need at least one row: creating or updating such an account with zero assignments is refused (422 staff_branch_required, Doc 03 BS-2). An account losing its last assignment can still log in but sees empty lists and gets 403 branch_scope_denied on writes (Doc 03 BS-2).
  • SB-2. Tenant-wide roles (owner, pathologist) take no assignments. The API refuses staff_branch writes for them (422 tenant_wide_role): a row would mean nothing — their scope is the tenant (Doc 03 BS-1).
  • SB-3. staff_user.branch_id is the home branch: a display default (which worklist opens first), never the scope source — scope comes from staff_branch only. Two fields that both look like scope is how scope bugs happen, so one is named display-only.
  • SB-4. Exactly one is_primary = true per staff member. Setting a new primary clears the old one in the same transaction.
  • SB-5. Only the Owner writes assignments (§15). A Manager reads the roster of their own branches; they cannot grant anyone — including themselves — a new branch.
  • SB-6. Assignment changes are audited in the tenant's audit_log (actor, staff member, branch set before/after) — access changes are security events.

8.5 How branch scope is enforced in code

Doc 03 P-7: scope is enforced in the query, not the UI — one implementation, in three layers: one place to audit, one place to test.

Layer 1 — the queryset mixin. Every branch-scoped model declares one class attribute naming its scope path:

# branches/scoping.py — the only place branch scope is implemented
class BranchScopedQuerySet(models.QuerySet):
    scope_field = None  # e.g. "branch_id", or "sample__branch_id"

    def scoped_to(self, user):
        if user.is_tenant_wide:            # owner, pathologist (BS-1)
            return self
        branch_ids = user.assigned_branch_ids()   # staff_branch, open branches only
        return self.filter(**{f"{self.scope_field}__in": branch_ids})

class BranchScopedManager(models.Manager):
    def get_queryset(self):
        return BranchScopedQuerySet(self.model, using=self._db)

    def scoped_to(self, user):
        return self.get_queryset().scoped_to(user)

Scope paths: patient.branch_id (registering branch, BS-3), invoice.branch_id, sample.branch_id (the holding branch — moves on transfer receipt, BS-3/SM-7), result/report via sample__branch_id. Catalog models declare no scope path — tenant-wide reference data (BS-5). assigned_branch_ids() excludes closed branches, so closing a branch revokes access everywhere at once (§8.3).

Layer 2 — the base viewset. Every viewset for a scoped model inherits one base class whose get_queryset() returns Model.objects.scoped_to(request.user) — lists, details and actions alike. Detail views fetch through the same queryset, so an out-of-scope object is simply not found: 404, indistinguishable from a missing one (Doc 03 P-7); no scoped viewset touches the unscoped manager.

Layer 3 — the permission class. IsInBranchScope sits on the same viewsets as defence in depth, re-checking an object's scope branch against the caller's assignments It covers what the queryset cannot see — actions receiving a branch in the body (transfer destination, staff assignments) — and Doc 03's explicit refusal: a zero-assignment write returns 403 branch_scope_denied, not a misleading 404 (BS-2).

The one exception is named, not hidden: BS-4's identifiers-only search is a separate method, identifiers_only_across_branches(), used by exactly one endpoint, returning exactly the BS-4 fields through a restricted serializer — the only method allowed to cross branch scope.

How it is tested (§18, TN-19–TN-24): a generated scope matrix, a structural test that fails if a viewset skips the base class, and Doc 03's BS scenarios as integration tests.

9. Sample transfer between branches

Transfer mechanics — the sample_transfer row, the TRANSFERRED_OUT / TRANSFERRED_IN events, custody, the state guards — are Doc 03 §5.4 (SM-7) and its workflow 3, not repeated here. This section adds only what Doc 03 left to Doc 04: routing rules, late and lost definitions, and the exception reports.

9.1 Routing rules

  • TR-1. Transfers exist only inside one tenant: the schema makes a cross-tenant transfer inexpressible — no endpoint, at any layer, moves a sample between schemas.
  • TR-2. The destination must be an open (deleted_at IS NULL) processing branch (is_collection_centre = false) different from the source. Anything else is refused at creation: 422 branch_cannot_receive (a centre or closed branch), 422 same_branch. A centre can be a source, never a destination (§8.1).
  • TR-3. Any processing branch may receive from any branch; there is no fixed hub assignment in the data model (§8.1). A strict hub pattern is a tenant's rota, not a schema constraint.

9.2 Late and lost — definitions on the A-9 columns

The lifecycle is read from the columns Doc 02 v1.3 stores (A-9, §1.4 finding 4): sample_transfer.status is open | received | cancelled | lost (application-enforced); dispatched_at is the moment the sending branch hands the sample to the courier, set when the transfer is created; received_at is set at receipt. Cancel and mark-lost also write the sample_event values TRANSFER_CANCELLED and TRANSFER_LOST, each naming the transfer ID in the event note — the audit trail Doc 03 §5.4 expects. Rows written before A-9 are read by the old rule (dispatch time = created_at; open = received_by IS NULL and no closing event) until the backfill sets their status.

  • Late. An open transfer older than transfer_late_after_hours (default 24, §10) is late. Late is a report state, not a sample state: no status moves, no auto-receipt, no auto-loss (Doc 03 §5.4). The sample sits on both branches' and the Owner's exception lists (§9.4) until resolved by a human.
  • Cancel. Only the sending branch (Manager or Owner) may cancel an open transfer (POST /api/v1/transfers/{id}/cancel, §15). Cancellation sets status = cancelled and writes TRANSFER_CANCELLED; the sample stays at the sender, in its prior status (collected or received), transferable again or processed locally. A cancelled transfer is terminal: it cannot be received or marked lost. The receiver cannot cancel a transfer it never agreed to hold.
  • Lost. Only the sending branch (Manager or Owner) may declare a transfer lost (POST /api/v1/transfers/{id}/mark-lost, with a mandatory note). The declaration sets status = lost and writes TRANSFER_LOST. Marking a transfer lost does not change sample.status. The sample is then resolved through reject-sample (Doc 03 SM-8) and recollect (SM-9) on the same invoice. A lost transfer is terminal: it cannot be cancelled or received. In Doc 03's terms: the sender rejects the sample with reason code other and a note naming the loss (SM-8), and recollection (SM-9) creates the replacement against the same invoice. There is no "lost" sample status in v1 (Doc 02's CHECK list has none) and none is invented here — a developer must not assume a lost transfer auto-closes the sample.
  • Custody is never ambiguous. Exactly one branch holds the sample at every moment (SM-7): the sender, until receipt, cancellation or loss. "In transit" is a custody state of the sender, which is why late and lost are the sender's to raise.

9.3 The receiver's view before receipt

Before receipt, sample.branch_id still names the sender, so branch scope (§8.5) hides the sample from the destination. The destination's "expected arrivals" list queries sample_transfer rows addressed to it (open only), showing accession ID, source branch, dispatch time and ordered tests — for bench planning and spotting a missing dispatch. On receipt, Doc 03 SM-7 takes over and scope moves with the sample.

9.4 Exception reports

Three read-only reports, all computed from sample_transfer and sample_event — no new tables. Owner sees all branch pairs; a Manager sees pairs touching their assigned branches.

11. Plans and limits

11.1 The plan and subscription rows

Doc 02 §4.1: a plan has name (unique), price (numeric(12,2) PKR/month), max_branches (int, NULL = unlimited) and is_active. A tenant's plan is its one active subscription — the partial unique index uq_subscription_one_active_per_tenant makes "two active subscriptions" inexpressible. subscription.status: active | past_due | cancelled | expired.

Plan rows are effectively immutable. Once a subscription references a plan, its price and max_branches are not edited in place — a price change creates a new plan row; tenants move to it at renewal by a new subscription. Editing in place would silently re-price every lab on that plan (Doc 03 P-2 applies to platform money too). Retiring a plan is is_active = false: existing subscriptions keep working; no new ones.

Read-only mode, defined exactly. All GET endpoints work for all staff roles — a lab can always read its own records. Every write returns 403 subscription_read_only, with three exemptions: patient report-access (TP-8); the Owner's data export (§15) — a tenant that cannot pay must still leave with its data; and platform actions, which are not tenant writes. Lock vs read-only — why not a full lock. A hard lock (no reads) was rejected: these are clinical records patients and regulators may need, the data is the lab's, and reads cost almost nothing. Read-only keeps the pressure — no new work — without the hostage optics.

Who enforces it, and where. One service function, tenant_access_mode(tenant), computes full | read_only from the subscription. The §6.3 middleware calls it (after authentication); the result is cached per tenant in Redis (tenant:<slug>:access-mode, §13.3), 60-second TTL, invalidated immediately by any platform write to that subscription — so fixing a subscription unblocks the lab within seconds. No view re-implements the check.

11.3 max_branches enforcement

Enforcement point: the branch-create service (§15), inside the create transaction. The count is branch rows with deleted_at IS NULL — collection centres count: a site holds staff, samples and scope. At the limit: 409 plan_limit_reached with count and limit in the body. Concurrent creates racing the last slot are serialised by a transaction advisory lock keyed on the tenant (pg_advisory_xact_lock — transaction-scoped, so PgBouncer-safe, F-5). Plan changes bite on the next create: raising unblocks at once; lowering below the count blocks new branches, closes nothing.

There is no "log in as this lab" feature, and none may be added without an amendment to this document and Doc 01 §4. Three reasons, in order of weight:

  1. Audit integrity. Every tenant audit row names a staff actor (Doc 03 P-3). An impersonated session writes real actions under a borrowed name — from that day, "who did this?" is "maybe us, maybe support" for every tenant, and the audit trail is worth less for all of them.
  2. The role is defined without patient data. Doc 01 §4 gives the Super Admin "no tenant patient data"; impersonation is precisely that access with a friendlier name, quietly repealing the platform's clearest privacy promise.
  3. Support does not need it. Platform metadata (§12.2), the owner-sent export, and screen-sharing with the owner driving cover real support needs.

13. Isolation and noisy-neighbour

13.1 The isolation model, restated as rules

  • Isolation is the schema (TP-1). Cross-schema SQL exists in exactly three platform-side places — provisioning, fleet migration, backup — each on one named schema at a time (TP-5)
  • Content types and permissions exist per schema (F-3); Django caches them per process (F-14). So nothing framework-cached is tenant truth across a context switch; app caching follows §13.3's prefix rule, and the suite includes a cache-poisoning scenario (TN-33).
  • Goal G5 (zero cross-tenant leakage, proven by tests on every merge, Doc 01 §3) is discharged by the suite in §13.6, not code review.

13.2 Celery tenant context

Doc 01 §8's rule, made mechanical: every tenant task's payload carries tenant_slug first. All tenant tasks inherit one base class: __call__ looks the tenant up by slug (unknown slug raises — fail loudly, not in the worker's current context), enters tenant_context(tenant), and resets to public in a finally block (F-13: a surviving context is the next task's leak). Beat fan-out (TP-5): one child task per active tenant, never a schema loop, so one tenant's exception cannot abort the rest.

13.3 Cache key prefixing

Redis is shared (broker and cache, Doc 01 §15), so cache isolation is a naming discipline enforced by construction: all tenant cache access goes through one wrapper prefixing every key with tenant:<slug>: (tenant:citylab:settings, tenant:citylab:access-mode); platform keys use platform:. Raw cache access from tenant apps is banned mechanically — a CI import-linter rule (Doc 01 §7) fails any build importing the raw client outside the wrapper. No patient data is cached at all (Doc 01 §15); cached values are settings, access mode and other inert state.

13.4 Storage prefixes

Every object a tenant owns lives under tenants/<slug>/ in the bucket. Doc 02 §9's keys are relative to that root: a report PDF's stored pdf_key is reports/{report_id}/{version}.pdf, its effective path tenants/<slug>/reports/{report_id}/{version}.pdf; statements and exports follow the same pattern (settlements/…, exports/…). Pre-signed URLs are minted only after Doc 03 RP-8's tenant-context and token checks. Deleting a tenant deletes exactly its prefix (§4.3).

13.5 Rate limits and fairness per tenant

  • API. A DRF throttle keyed by tenant slug — not IP (a chain's branches share one NAT address). Separate budgets: staff API per tenant; the unauthenticated report-access path by token + IP; the platform. Values are configuration (§17).
  • Queues. Doc 01's queues are shared by design; fairness inside them is a per-tenant concurrency cap on the reports queue (at most 2 concurrent generate_pdf tasks per tenant, counted in Redis; a task finding the cap full re-queues with a short countdown instead of failing) (F-12). Settlements and exports already fan out per tenant (§13.2).
  • Database. statement_timeout is set for the app role, so one tenant's runaway query dies instead of holding the shared PostgreSQL — set generously, as catastrophe insurance, not query tuning.

13.6 Connection pooling: the PgBouncer decision

Doc 01 §16's scaling order puts PgBouncer second, after a reports worker on a second VPS. It is not in the day-one Compose stack; until it lands, Django connects directly, connections capped well under max_connections. The decision is recorded now, so no code is written a pooler would break:

Decision: when PgBouncer is introduced, it runs in transaction pooling mode (pool_mode = transaction). Session mode was rejected: it pins one backend per client for the connection's life, which at tenant scale recreates the connection-count problem PgBouncer exists to solve.

The risk, stated exactly: django-tenants switches tenants by setting search_path. In transaction mode a backend serves a different client at every transaction boundary, so a session-level SET search_path does not survive the transaction — and session-level state can be observed by the next client on that backend (F-4, F-5). That failure mode is not "wrong results"; it is one tenant reading another tenant's schema.

Guardrails: (1) tenant switching must be transaction-scoped (SET LOCAL) before PgBouncer is enabled — verified by gate test TN-34 (§18); if it fails, PgBouncer does not ship; the fallback is session mode with a small pool, recorded as a new decision; (2) CONN_MAX_AGE = 0; (3) migrations and provisioning always connect directly (F-4); (4) server-side prepared statements disabled at the driver unless the deployed PgBouncer's max_prepared_statements support is enabled and covered by the same gate test.

13.7 The cross-tenant test suite

The suite (Doc 01 §8's two-tenant proof, generalised) is generated from the model registry: every TENANT_APPS model gets tenants A and B with one factory row each — A's row ID on B's host → 404; B's lists never contain A's key; a B-context query returns only B's row. New models are covered on landing. Opting out needs an allow-list entry with a written reason, reviewed like a schema change. The named §18 scenarios sit on top (tokens across hosts, callback slug mismatch, cache poisoning, context reset).

14. Backup, restore and disaster recovery per tenant

14.1 Backup unit: one schema, one file

Nightly, from the maintenance path (never in the migration window, F-16): pg_dump --schema=public, then one pg_dump --schema=tenant_<slug> --format=custom per tenant, each encrypted (age, Doc 01 §14) and uploaded as backups/<date>/…, with a manifest of sizes and checksums. Retention: 7 daily, 4 weekly (Doc 01 §15) Per-schema files (F-10) mean one tenant's dump can fail, be re-run or be restored without touching another, and a restore never loads another lab's data to get one lab back. A schema missing from the manifest is an alert (§17), not a log line

14.2 Restoring one tenant

Procedure (workflow in §16):

  1. Suspend the tenant (§4) so nothing writes during the restore.
  2. Rename the live schema aside: ALTER SCHEMA tenant_<slug> RENAME TO tenant_<slug>_quarantine_<date> — kept for diagnosis, nothing dropped yet.
  3. Create a fresh tenant_<slug> schema and pg_restore the chosen night's per-schema dump into it.
  4. Re-apply the Doc 02 §6 REVOKEs (a dump may carry privileges; the script runs unconditionally) and migrate that schema forward to the current release — the dump may predate it (§7.3's single-schema command).
  5. Smoke checks: row counts for the core tables against the dump manifest, owner login, one report PDF opens.
  6. Reactivate. The quarantine schema is dropped after 7 days by the ops script, the drop recorded in platform_audit (tenant.restored covers the event).

No other tenant is suspended, dumped, restored or locked at any point in this procedure — the entire reason for §14.1's file layout.

14.3 Targets and the monthly drill

RPO: 24 hours — nightly dumps lose at most a day of data, the honest number for a free-tier single VPS (Doc 01 §5); PITR via WAL archiving would lower it and is not built in v1 (§21). RTO: one tenant within 1 hour; the whole platform within 4 hours (new VPS, Compose up, public dump, then tenants alphabetically; object storage is already off-VPS in R2). Both are targets proven by drill, not guarantees: monthly, the largest tenant plus public are restored into a scratch database and smoke-tested, duration recorded; an overrun changes the RTO or the procedure, in writing. Full-platform recovery: same procedure at fleet scale, public first — the registry must exist before any host resolves.

22. Interview talking points

The eight decisions in this document worth being able to defend out loud. Each states the decision, the defence, and the alternative that was rejected.

  1. Schema-per-tenant, with its ceiling named (§2 F-1, §7). Isolation is strong and per-tenant operations (backup, restore, delete) are clean, but costs are linear in tenant count: every migration runs N times, catalogues grow with N schemas. At tens of tenants the trade is obviously right; the document says where it stops being right. Rejected: shared tables with tenant_id — one missed filter is a breach — and database-per-tenant, whose ops cost a solo developer cannot carry.
  2. Provisioning is an idempotent, resumable state machine (§5). Schema DDL, migrations, seeding and an email cannot be one transaction, so pretending provisioning is atomic just moves the failure into a half-built tenant. Each step checks before it acts, re-runs are safe, and G4 is measured per step so slowness has an address. Rejected: one big provisioning script run by hand — unrepeatable, unresumable, and exactly how tenant number nine ends up different from tenants one to eight.
  3. The host is the only tenant selector (§6, TP-2). No request field can name a tenant, so an entire class of cross-tenant bugs — swapping an ID or a header to reach another lab — has no surface to live on. Credentials issued inside one schema simply do not exist in another. Rejected: a tenant header or claim trusted from the client — flexible for APIs, and a permanent invitation to test whether every endpoint really checks it.
  4. PgBouncer in transaction mode — with the search_path risk stated, not waved away (§13.6). Transaction pooling is the only mode that scales, but it makes session state unreliable, and tenant switching is session state in django-tenants. So the decision comes with guardrails: transaction-scoped switching, direct connections for migrations, and a two-tenant interleave gate test that must pass before the pooler ships. Rejected: session mode (safe, and quietly re-creates the connection ceiling), and enabling transaction mode on faith.
  5. Branch scope lives in one queryset mixin, one base viewset, one permission class (§8.5). Scope bugs are born in the tenth hand-written filter, not the first. A single implementation, a structural test that fails if a viewset skips it, and 404-not-403 answers mean the property "staff see only their branches" is enforced by architecture. Rejected: per-view filtering (drifts immediately) and UI hiding (not access control at all).
  6. Past-due becomes read-only, never a lock, and suspension never deletes (§11.2, §4). The lab's data is the lab's — clinical records its patients may need. Read-only mode applies real commercial pressure (no new work) while keeping every record readable and every issued patient link alive. Deletion sits at the end of a 30-day grace with an export in the owner's hands. Rejected: hard lockout on a missed payment — maximum pressure, and the platform holding patient records hostage to a billing dispute.
  7. No impersonation, even though support will ask for it (§12.3). "Log in as the lab" would write real actions under a borrowed identity and quietly devalue every tenant's audit trail, and it hands the Super Admin the patient data Doc 01 promises they never see. Metadata, owner-driven exports and screen-sharing cover real support needs. Rejected: impersonation with an audit flag — the flag records that the trail is unreliable, which is the problem, not the fix.
  8. Backups are per-schema so restore is per-tenant (§14). One pg_dump per schema means the worst day — restoring a lab — never touches another lab's data, and the monthly drill proves the 1-hour RTO on the largest tenant rather than asserting it. Rejected: one full-database dump — simpler to write, and it makes every restore an all-tenants event with all-tenants risk.
