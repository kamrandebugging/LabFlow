1. Purpose, scope, inputs, consistency check

1.1 Purpose

Docs 01–06 fixed everything behind the API. This document fixes everything in front of it: the single-page application (SPA) that lab staff use all day, and the one public page a patient ever sees.

After reading it, a developer should be able to build the SPA without inventing rules: what screens exist, what each screen shows and calls, what state each screen holds, how auth flows, how English and Urdu (RTL) work, how errors surface, how labels print, and how PDFs open. Anything this document needs that Docs 01–06 do not have is marked Proposed and listed in §17.

The SPA is a display surface, not a second brain. Every rule — money, state transitions, permissions, share percentages — is decided and enforced by the API. The SPA renders what the API returns, sends what the staff member did, and explains what the API answered. Where the SPA and the API disagree, the API is right and the SPA has a bug.

1.5 Assumptions

AS-1. One SPA build serves every host. On a tenant host it runs in tenant mode; on the apex host labflow.app it runs in platform mode (§4.4). The build is identical; the host decides.

AS-2. Staff work on desktop browsers at branch counters and benches. The layout targets desktop first and must not break at narrow widths, but there is no tablet-specific or phone-specific design in v1 (§18).

AS-3. Every staff browser can reach the API on the same origin. There is no offline-first requirement in v1 (Doc 01 §5's patchy-connectivity case is handled by R3, §16).

AS-4. The lab's printers are ordinary office printers plus label printers driven by the browser's print dialog. There is no print server (§18).

AS-5. Sentry is wired into the SPA build the same way Doc 01 §14 wires it into the API: patient fields are stripped before an error leaves the browser.

3. Design principles

Doc 03's principles P-1 to P-10 govern the lab modules, and P-1 (patient safety first) still outranks everything here. These govern the frontend.

#PrincipleWhat it means here
FP-1The API is the source of truth.The SPA never derives a status, a total, or a permission. If the API did not say it, the screen does not show it. Derived-looking numbers on dashboards are counts of rows the API returned, labelled as such.
FP-2The access token lives in memory only.Never localStorage, never sessionStorage, never a JavaScript-readable cookie (Doc 01 ADR-005). A page reload loses the token; the refresh cookie silently restores the session (§5). That trade is deliberate: a reloaded tab costs one refresh call, a stolen stored token costs a tenant.
FP-3No patient data in browser storage. Ever.No patient, sample, result, invoice or partner data is written to localStorage, sessionStorage or IndexedDB — not as a cache, not as a draft, not “temporarily”. The TanStack Query cache lives in memory and dies with the tab. The only values persisted are UI preferences with no patient content: language and theme (§9).
FP-4Branch on code, never on text.Every error decision in the SPA reads the problem+json code field (Doc 03 §6.1). detail is for humans and may be shown; it is never parsed, matched or translated by the client.
FP-5Money is display-only text.Money arrives as a string and is shown as that string. The SPA does no money arithmetic — no sums, no balances, no “remaining” figures computed in the browser (R2, §16). If a screen needs a total, the API already sent it.
FP-6Hidden by role, enforced by the API.Buttons and nav items a role may not use are not rendered. That is a usability rule, not a security rule: the API re-checks every call and answers 403 regardless (§6, §15).
FP-7The host is the tenant.The SPA reads window.location.hostname once at startup and never sends a tenant identifier anywhere (Doc 04 §6.1). There is no tenant switcher. A staff member who works at two labs opens two hosts.
FP-8Skeletons, not spinners.Lists and detail screens render skeleton shapes while loading, so the page does not jump when data lands. A spinner appears only inside a button whose mutation is in flight.
FP-9No silent failure.Every failed call ends in one of the §7.4 surfaces: inline field error, toast, modal, banner, or the screen boundary. A button that does nothing on failure is a defect (§15).
FP-10The SPA talks to the API, and only the API.The SPA never calls n8n, never calls the Doc 06 §10 callback endpoints, never calls storage directly. PDFs open through API redirects (§12). Delivery state is read from API responses, never from the automation layer.

Three hard rules

  1. Money is never green or red. In a lab app, green and red already mean “normal” and “critical” in staff minds. Money is black text on slate-50, always. A paid invoice is not “green money”; it is the word paid beside a black figure.
  2. Colour is never the only signal. Every status pairs its colour with a letter or a word, per WCAG 1.4.1 (F-7). A flag is H in orange, never orange alone. A delivery state is its full word, never a coloured dot alone.
  3. Urdu uses the same palette, one step darker for muted text. Small Urdu (Nastaliq) text at muted weights is hard to read in slate-500, so muted text on Urdu pages is slate-600. Nothing else changes. Latin digits and IDs stay LTR inside RTL blocks (§9, §10).

Print surfaces are stricter than screens. PDF documents (Doc 03 §9, Doc 05 §8) are print-safe: black on white, flags as the letters L / H / CRITICAL, one amber accent line under the header. Barcode labels (§11) are black on white only. The SPA does not restyle either document; it only opens and prints them.

4. The app shell and routing

4.1 The shell

Every authenticated screen renders inside one shell. The shell has four parts:

  • Header. Lab name (from tenant-status, §6), the current branch context for branch-scoped roles, the language switcher (§9), and the user menu (name, role, logout).
  • Sidebar. Role-filtered navigation (§6.3) with count badges (§13.2). Items a role may not see are not rendered (FP-6).
  • Main. The routed screen. One screen, one scroll region.
  • Toast container. Fixed at the bottom inline-end corner, above everything except modals (§13.1). Banners (offline, read-only) render at the top of main, below the header, and are not dismissible while their condition holds.

Public screens (§4.3) render without the shell: no sidebar, no header, no badges — a patient holding a report link must never see staff chrome.

4.3 Guards

Tenant gate (runs first, once). At startup the SPA reads window.location.hostname and calls GET /api/v1/tenant-status (§6.1). Until that call answers, the SPA shows a plain loading screen — never a login form for a tenant that may not exist. Provisioning and suspended states replace the whole app (§6.2).

Auth gate. Every non-public route requires a live session. On a cold load there is no token in memory (FP-2), so the gate first attempts one silent refresh (§5.3). If the refresh succeeds, the user lands where they asked. If it fails, the SPA redirects to /login?returnTo=<path>; after login it returns to that path. The public routes never trigger a refresh attempt and never redirect to login.

Role gate. Each route names its roles (§8). A signed-in user who opens a route their role excludes is redirected to / with a toast (“That screen is not part of your role”). The redirect is a courtesy; the API would answer 403 anyway (FP-6).

Read-only gate. When the tenant is in read-only mode (§6.4), write controls across the app are disabled in place. Routes still load; reads still work.

4.4 Platform mode (apex host)

On labflow.app the same build runs in platform mode for the Super Admin: tenant list and tenant detail, backed by GET /api/v1/platform/tenants and GET /api/v1/platform/tenants/{id} (Doc 04 §15.1). Platform mode has no patient data, no branch context and no settlements. Tenant-mode routes do not exist on the apex, and platform routes do not exist on a tenant host — matching the API, which answers them with 404 (Doc 04 §6.2). The Super Admin never impersonates a tenant user (Doc 04 §12); there is no “view as lab” in the SPA.

5. Auth flow

5.1 The login screen

One screen, two steps. Step 1: email and password. Step 2, only when the account requires it: a six-digit TOTP code. Owner, Manager, Pathologist and Super Admin accounts always require TOTP (Doc 01 §14). Receptionist and Technician accounts sign in at step 1 unless the tenant has enabled TOTP for them — the SPA does not decide this; the login response says whether a TOTP step follows.

The screen shows the lab name from tenant-status so staff can see which lab they are signing in to. It shows no other tenant data. A failed login shows one message — “Email, password or code is not correct” — for every failure kind. The SPA never reveals which part failed.

The routes are Proposed (A-21). The SPA calls POST /api/v1/auth/login with {email, password}. The response is either a session ({access, expires_in, user}) or {totp_required: true}, in which case the SPA calls POST /api/v1/auth/totp/verify with the code and receives the session. Only the refresh route exists in Docs 01–06 today (§1.4, gap 1); Doc 08 owns the final auth contract and may rename these — the SPA's auth module is one file, so a rename is one edit.

5.2 Where the token lives

The access token (15 minutes, Doc 01 §14) lives in a Zustand store, in memory, in a module that is never persisted:

authStore = {
  accessToken: string | null,   // memory only — no persist middleware, ever
  user: { id, name, role, branch_ids } | null,
  setSession(access, user), clear()
}

The refresh token is never visible to the SPA at all: it is the httpOnly cookie the API set at login, scoped to /api/v1/auth/ (ADR-005). The browser sends it only to auth endpoints, which is exactly the set of calls that need it.

Logout clears the store, clears the TanStack Query cache (it holds tenant data in memory; FP-3 means it must not outlive the session), and calls POST /api/v1/auth/logout (Proposed, A-21) so the API invalidates the refresh cookie server-side. Clearing only the client would leave a live cookie behind on a shared counter PC — the server call is the logout; the client clear is tidiness.

5.3 The interceptor: refresh and retry once

Every API call goes through one fetch wrapper. No screen calls fetch directly. The wrapper:

  1. Attaches Authorization: Bearer <accessToken> when a token exists, and If-Match when the caller supplies one (§7.4).
  2. On a 401 whose problem+json code is token_expired: starts — or joins — the single in-flight refresh: POST /api/v1/auth/refresh (the browser sends the cookie; the SPA sends no body). “Single-flight” means ten simultaneous 401s cause one refresh call, not ten.
  3. On refresh success: stores the new access token and retries the original request once, with its original body and headers. If the retry also returns 401, the wrapper does not loop — it ends the session (step 4).
  4. On refresh failure: clears the auth store and the query cache, and redirects to /login?returnTo=<current path>.
  5. Any other 401 (no token, revoked token, wrong host) goes straight to step 4 without a refresh attempt. A 401 from the login or TOTP calls themselves is returned to the login form — the interceptor never intercepts auth endpoints.

§14 workflow 1 draws this dance in full.

5.4 Session expiry and unsaved work

Forms hold unsaved work; a session must not eat it. Two rules:

Warn first, when the SPA can. Navigation away from a dirty form — by link, by the logout button, by the browser back button — opens a confirm modal (“You have unsaved changes”). Logout is behind the same modal plus an explicit confirm (§8.1).

Keep the draft in memory, when it cannot. A hard session end (refresh failed) cannot ask permission. Before redirecting, the wrapper copies any dirty form's values into the same in-memory Zustand store — memory only, gone when the tab closes, never written to browser storage (FP-3). After the user signs in again and the returnTo route loads, the form restores its values and shows a notice: “Restored what you had typed. Nothing was saved.” Result-entry screens (§8.4) use the same mechanism; a half-typed batch of results is the most expensive thing to lose in a lab.

7.2 Zod schemas at the boundary

Every API response is parsed through a Zod schema that mirrors its contract (Doc 03 §6.1 conventions; endpoint shapes from Doc 03 §6, Doc 04 §15, Doc 05 §10). The schemas are types first: the TypeScript type of a screen's data is inferred from its schema, so the screen cannot drift from the contract without a compile error. A response that fails parsing is treated as a server error (§7.4, last row): the screen shows the error surface and Sentry receives the mismatch — a schema failure means the API and SPA have drifted, which is a bug to fix, not a state to render.

Request bodies are validated by the same schemas' input twins before sending, so a malformed request fails in the form, not at the API. The SPA never calls Doc 06 §10's endpoints — those are n8n's callbacks into Django (FP-10) — so no Zod schema exists for them.

7.3 Forms: React Hook Form + Zod

Create and edit flows use React Hook Form with the Zod resolver sharing the §7.2 schemas: one definition drives the form's client validation and the request body. Client validation is a courtesy layer (fast feedback, no round trip); the API re-validates everything, and its answer wins. Field rules come from the owning documents — for example patient fields follow Doc 03 PT-V1 (name 2–120 chars, phone normalised to 10–15 digits, sex M | F, date of birth not in the future) — the SPA mirrors them in the schema and shows the same messages the API would, in the user's language (§9).

Server field errors land back on the form (§7.4): the problem+json errors object maps field name to messages, and the form sets each one on its field. A form-level code (for example refund_exceeds_payments, Doc 03 BL-7) shows as a form-level alert above the submit button, in words, not as a toast behind the modal.

9. i18n and RTL

9.1 Setup

i18next with react-i18next, initialised once at startup. Two locales in v1: en and ur. More languages are §18 — the structure below is what a third language would plug into, but none is built.

Namespaces, one per feature: common (buttons, states, errors), auth, patients, billing, samples, results, reports, partners, settlements, settings. Files: one JSON file per namespace per locale — src/locales/en/patients.json, src/locales/ur/patients.json — bundled with the build (no runtime fetching of translations; the SPA must render offline-cached screens in the right language, §15). Fallback language is en: a missing Urdu key shows English, never a raw key, and the build's i18n check fails CI when a key exists in one locale and not the other.

Keys, not sentences. Code asks for results.approve.confirmTitle, never for an English string. Error surfaces come from §7.4: the code selects the key; the API's detail is never displayed untranslated to a user who chose Urdu — server detail is a developer aid, the SPA's catalogue is the user text.

9.2 The RTL switch

On languageChanged, the SPA sets document.documentElement.lang and document.documentElement.dir from i18n.dir() (F-4): Urdu → dir="rtl", English → dir="ltr". The switch is at <html> level only — no per-component direction flags.

CSS convention: logical properties only. Spacing and positioning use Tailwind's logical utilities — ms-* / me-* (margin-inline), ps-* / pe-* (padding-inline), start-* / end-* (inset-inline), text-start / text-end. Physical utilities (ml-, mr-, pl-, pr-, left-, right-, text-left, text-right) are banned in app code; an ESLint rule fails the build on them. With that one rule, the RTL layout is the LTR layout mirrored by the browser — sidebar, tables and forms flip for free, and a screen that does not flip has a banned class in it, which the lint output names.

What never flips. Numbers, money, dates, and every ID — MRN, accession ID, phone — stay LTR with Latin digits, even inside Urdu text (§10). They render inside dir="ltr" spans (§7.2 schemas guarantee their shape). The barcode label (§11) never flips: it is a physical object, printed the same in both languages, from stored data whose patient name prints as recorded.

Type. Urdu renders in a Nastaliq web font (Noto Nastaliq Urdu), loaded with the build; English in the system sans stack. Muted Urdu text steps one contrast darker (§3.1 rule 3). Line-height for Urdu body text is looser than English (Nastaliq stacks tall); the token is per-locale, set once in the theme, not per screen.

9.3 The switcher, and what is remembered

The language switcher lives in the header, on every authenticated screen and on the login screen (a staff member chooses their language before signing in). It is a two-option control — English / اردو — never a dropdown of flags.

The choice is remembered in localStorage under one key (labflow.lang), alongside the theme preference (labflow.theme) and nothing else. This is a UI preference, not auth and not patient data (FP-3): it holds no token, no tenant, no record. The API is never told the staff UI language — it is irrelevant to the server. The language patients receive messages in is a different thing entirely: the tenant's report_default_language setting (Doc 04 §10.2, A-16), chosen by the Owner in settings, applied by Django when it renders messages (Doc 06 AS-5). The SPA does not confuse the two, and neither may a developer: the switcher changes the staff member's screen; the setting changes the patient's message.

9.4 Testing both languages

Every screen is tested in English and in Urdu before it is done — not sampled, every screen: the §15 suite runs FE-06 for the switch itself, and each screen's own review includes an Urdu screenshot. Truncation is the expected failure: Urdu strings run longer and taller, so buttons and table headers are sized by content, never by fixed pixel widths.

11. Barcode label printing

11.1 The rule the screen serves

Doc 03 SM-4 and Doc 01 Flow A: the label is printed client-side, from stored data, at collection and on reprint. The data comes from GET /api/v1/samples/{id}/label: accession ID, patient name, MRN, date of birth (nullable), collected_at, collector name, and symbology code128 over the accession ID. There is no free-text label endpoint, and this screen has no editable field: what is stored is what prints (FP-1). If the stored data is wrong, the fix is to correct the record and reprint — the audit log holds every print and reprint (Doc 03 §6.5).

11.2 The library: JsBarcode

R1 (§16): JsBarcode (MIT, F-2) renders the Code128 into an <svg> in a useEffect, called with the accession ID and format: "CODE128", displayValue: true so the human-readable accession prints under the bars. SVG, not canvas: the printed bars stay vector-sharp, and a cheap label printer cannot blur a raster it never receives. bwip-js (F-3) is the rejected alternative — broader, heavier, and pointless for one symbology; react-barcode-style wrappers were rejected with it, because a wrapper around an imperative one-call library adds a dependency whose only job is to go stale against React 18.

11.3 The label

One label per accession. The physical label is 100 mm × 50 mm label stock. Batch printing (from the sample list, §8.3) puts each label on its own page; where only A4 is available, the same markup flows two-across on an A4 sheet with each label kept whole. Layout, black on white only (§3.1):

Label layout — 100 × 50 mm

Line 1 (top): lab name, small, from tenant-status.
Centre: the Code128 barcode of the accession ID (SVG), with the accession ID itself printed beneath the bars in monospace.
Line under barcode: patient name, bold, as recorded.
Next line: MRN … · DOB … (or “DOB not recorded”).
Last line: collected DD MMM YYYY HH:mm · collector name.

Nothing else is on the label. No test names, no prices, no patient phone: a tube label is read at a bench and stuck on a tube, and every extra field is a chance to read the wrong one.

11.4 The print stylesheet

The label screen is a normal SPA screen — preview, sample summary, Print button — until print. A dedicated print stylesheet governs output:

@media print {
  /* everything that is not the label sheet disappears */
  body * { visibility: hidden; }
  #label-sheet, #label-sheet * { visibility: visible; }
  #label-sheet { position: absolute; inset: 0; }
  .label { page-break-after: always; page-break-inside: avoid; }

@page { size: 100mm 50mm; margin: 0; }   /* label stock; A4 fallback keeps the same .label box */

Header, sidebar, buttons and the toast container are inside body * and never reach paper. One label, one page-break: a batch of eight accessions is eight pages of one label each, in the order the API returned them. The screen's Print button calls window.print() — v1 has no silent or direct printing (§18).

11.5 Print failures

A label that renders wrong is a patient-safety surface (Doc 03 R-3). Two guards: the preview on screen is the print DOM itself, not a mock of it, so what staff check is what prints; and a barcode that JsBarcode refuses (invalid input — which stored accession IDs cannot be, by construction) fails the screen loudly with the §7.4 error panel instead of printing a label with no bars. Test FE-07 (§15) prints through a real print dialog against a mocked label response and asserts the accession text and the field lines are on the page.

12. PDF access

12.1 Staff download

Two buttons, one pattern. On a report: “Download PDF” calls GET /api/v1/reports/{id}/versions/{version}/pdf (Doc 03 §6.7). On a settlement: “Download statement PDF” calls GET /api/v1/settlements/{id}/statement.pdf (Doc 05 §10).

The call is an authenticated fetch through the §5.3 wrapper — not a bare link, because the endpoint requires the Bearer token and a plain navigation cannot send one. The API answers 302 to a pre-signed storage URL; fetch follows the redirect (the Authorization header is sent only to the API origin — browsers strip it on a cross-origin redirect), receives the PDF bytes, and the SPA opens them in a new tab via an object URL, revoking the URL once the tab has it. The SPA never stores the PDF, the pre-signed URL, or anything derived from them (FP-3, FP-10).

Not rendered yet. The endpoint answers 404 when the version's PDF does not exist yet. The SPA shows “The PDF is not ready yet — it is still being prepared” beside the button. There is no polling and no auto-retry: generation is fast (Doc 01 G1) and staff re-check with the button. A 404 that persists is a server problem and belongs in §15's failure handling, not in a spinner.

12.2 Patient access: two clicks, no session

The patient's link — from the delivery email or WhatsApp message, or the QR code on a printed report (Doc 03 §6.8) — opens the public page /report-access/:token on the lab's own host. The page holds no session and needs none. On load it navigates the browser, full-page, to GET /api/v1/report-access/{token}. That call sends no credentials: no Authorization header (there is no token in memory on a public page, by construction), no staff cookie involvement — the access token in the URL is the whole credential (Doc 03 §6.8).

The API verifies the token and answers 302 to a pre-signed URL for the current version's PDF. That is the whole flow, and it is G6 counted honestly: click 1 opens the link from the message; the page's automatic navigation is not a click; the PDF is on screen. If a browser blocks the automatic step, the page shows one button — “Open my report” — which performs the same navigation as a real click (click 2). There is no third step, no login, no app install, no “verify yourself” detour: the public verify endpoint (Doc 01 §14) is a separate, minimal surface and returns nothing sensitive, and v1's patient page does not build a flow on it.

Expired or revoked. The API answers 410 (Doc 03 RP-9). The public page routes to /link-expired (§8.7): lab name, lab phone number from the API's contact response, plain instructions. Unknown tokens answer 404 and land on the same page — the patient cannot learn anything from the difference, and neither can anyone who found the link. Staff reissue from the report screen (§8.4), which mints a fresh token; the old one stays revoked.

Suspended and read-only tenants. The flow above is exempt from both gates (Doc 04 TP-8, §11.2): a billing dispute must not strand a patient holding a clinical result. The SPA's tenant gate (§4.3) does not run on public routes, by design.

13. SPA notifications and empty states

13.1 The definition

Doc 06 §1.4 ruled that some notices exist only inside the SPA. This section defines what that means. An SPA notification is one of exactly two things:

  • A toast. A transient message in the toast container (§4.1). Confirmation and information toasts dismiss themselves after 5 seconds. Error toasts stay until dismissed — a failure a user must act on does not vanish on a timer. A toast is never the only record of anything: the underlying state is on its screen, from the API.
  • A nav badge. A count on a sidebar item, naming pending work. A badge persists while the work persists, and its number always comes from a real list query the SPA makes anyway (§7.1). Clicking the badge opens the list it counts.

Nothing else is an SPA notification. There is no browser Notification API, no push, no service worker, no sound, no email, no notification row (Doc 06 §1.4). If a future document wants one of those, it amends this definition first.

Delivery display is not a notification. The report screen's delivery panel (§8.4) shows report_delivery rows as state — word and colour per §3.1, hard_bounce: rendered as readable words (§8.4) — because staff open that screen to answer “did the patient get it”. It is data on a screen, not a toast, and it is read from the report GET, never pushed.

18. What is NOT built in v1

  • No browser push notifications, no Notification API, no service worker. SPA notification means toast + badge (§13). A service worker would also be a second cache of patient-adjacent state to reason about (FP-3).
  • No offline-first. TanStack Query's in-memory cache and the offline banner are the whole offline story (R3). No IndexedDB, no queued writes, no background sync.
  • No native mobile app. The SPA is the only client. Staff phones are not a v1 target; patient phones get the public report page, which is a web page.
  • No tablet-specific layout. One responsive layout; narrow widths must not break, but no screen is designed for a tablet.
  • No per-user theme customisation beyond following the OS light/dark setting with the §3.1 tokens. No brand-colour picker, no density setting.
  • No patient portal. The patient surface is the report link and the expired page (Doc 01 OQ-07) — no accounts, no history, no inbox.
  • No partner portal. Partners are record-only in v1 (Doc 05 §15): no login, no dashboard of their own; the statement PDF is their interface.
  • No languages beyond English and Urdu. The namespace structure (§9) admits more later; none ships.
  • No print server, no silent printing. Labels print through the browser's print dialog (§11). No direct-to-printer path, no print queue.
  • No CSV / Excel exports from the SPA. Data leaves through the Owner export path (Doc 04 §4.3, §15.2) — one audited door, with the secrets exclusion list — not through per-screen download buttons.
  • No optimistic updates on clinical or money writes. A payment, a result, an approval: the screen waits for the server's answer and shows that. Optimistic UI on a ledger or a clinical state machine would eventually show a state that never existed.
  • No data-fetching Suspense (F-8). Route code-splitting with React.lazy and skeleton fallbacks only.
  • No SPA-side PDF generation. PDFs are the server's documents (Doc 03 §9, Doc 05 §8); the SPA opens them (§12) and prints labels (§11), nothing more.

19. Interview talking points

JWT in memory, refresh in an httpOnly cookie — why not localStorage? Because XSS is the realistic threat to a lab counter PC, and a token in localStorage is a token any script bug hands to an attacker, valid until it expires, usable from anywhere. In memory, the access token dies with the tab and cannot be read out of storage; the refresh token is httpOnly, so script cannot read it at all, and it is scoped to /api/v1/auth/, so it rides only the calls that need it. The cost is one silent refresh on reload. We pay it gladly (ADR-005, §5).

One origin, no CORS — how much does it simplify? Almost everything annoying about browser auth disappears: no preflight, no origin allow-lists to keep in sync, cookies behave, the refresh flow needs no cross-origin credential gymnastics, and a whole class of “works on staging, fails in production” bugs cannot exist. One Caddy, one origin, API and SPA — chosen in Doc 01 §15, cashed in here.

Tenant from host — isolation that is structural. The SPA cannot send the wrong tenant ID because it never sends a tenant ID. There is no header to forge, no query param to tamper with, no “lab switcher” to abuse: the host picks the schema before the SPA's first API call, and everything after is that tenant's world. Client-side, tenant safety is not a check we remember to write; it is a field that does not exist (§6.1).

TanStack Query's cache is the offline mode — why no IndexedDB? Because offline-first for clinical and money data is not a cache, it is a second database with a sync protocol and a conflict policy, storing patient data in a browser store we promised never to touch (FP-3). The actual v1 problem is smaller: a connection drops for ten minutes and the bench should keep seeing the worklist. An in-memory cache plus an honest banner plus blocked writes solves the real problem and refuses the fake one (R3).

Money as strings, never recomputed — the class of bug it kills. Every “the screen said 1,249.99 but the invoice says 1,250.00” bug ever written comes from two pieces of code doing the same arithmetic slightly differently. If the browser does no money arithmetic, that bug class has one member left — the server's — and the server has Doc 03's derived-status rules and tests guarding it. A display surface that cannot compute cannot disagree (R2).

Barcode client-side, no label endpoint — the barcode is the record. A label endpoint that accepted text would let anyone print a tube label for anything — a sample that does not exist, a name typed from memory. By rendering only from GET /samples/{id}/label, the printed barcode is guaranteed to be the stored accession of a real sample, and every print is auditable against the record. The barcode is not a picture of the data; it is the data, encoded (§11).

Version conflict as a modal, not an auto-merge. Auto-merge is a promise that two people's edits to a clinical result can be woven together by software. They cannot — not safely. A modal that stops the work, shows the current version, and makes a human re-decide is friction in exactly the right place: stale writes to results and settlements fail loudly, once, in front of the person who can resolve them (R4).

SPA notification = toast + badge — why no push? Push needs a service worker, a permission prompt, a subscription store, and a delivery guarantee story — four systems to tell a pathologist something the approvals badge already tells her when she looks at the screen she works in all day. Drafts-ready as a badge (Doc 06 §1.4) is the pattern at its best: the signal lives where the work is done, costs no infrastructure, and cannot fire at 3 a.m. When a notice truly must leave the building, that is email — Doc 06's job, with rows and retries — not a browser API (§13).
