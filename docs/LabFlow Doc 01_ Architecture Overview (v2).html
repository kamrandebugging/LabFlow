2. System summary

LabFlow is a multi-tenant SaaS platform for diagnostic laboratories in Pakistan. A lab — or a chain with many branches and collection centres — runs its whole workflow on it: every sample is tracked from collection to final report, referral partner revenue share is calculated automatically, and reports are delivered to patients. The platform consists of:

  • Platform admin — the Super Admin surface on the apex domain: tenant registry, provisioning, plans and subscriptions (public schema).
  • Lab staff app — the React SPA on each tenant's subdomain, used by the Lab Owner, Branch Managers, reception and collection staff, technicians and pathologists.
  • Patient report access — no patient account: a signed link, valid 7 days, opens the report PDF in two clicks; staff can resend or revoke it.
  • Automation layer — self-hosted n8n receives signed webhooks from Django and handles email and WhatsApp click-to-send delivery, calling back on the tenant's own subdomain.

5. Constraints and assumptions

  • Solo developer, zero budget: free tiers and open source only. One unavoidable cost: a real domain name (labflow.app is a placeholder; roughly 10–20 USD per year, check prices).
  • Pakistan context: patchy connectivity at collection centres, English and Urdu (RTL), PKR.
  • Money rule: Decimal in Python, numeric(12,2) in Postgres, strings on the wire. Never float.
  • Assumptions: one VPS runs everything; up to 50,000 patient rows per tenant; finalised reports never change (corrections create a new version); tenants live on subdomains; no comprehensive data protection law in force in Pakistan as far as I know, but patient data is treated as sensitive.

7. Architecture pattern: modular monolith

One Django deployment, not microservices: a solo developer cannot carry the ops cost, one VPS is cheaper, and registration → bill → sample is naturally one DB transaction. Each app is a bounded module: it owns its models, other modules call only its service layer, events are the only push mechanism, and an import-linter rule in CI forbids cross-module model imports.

Where users live: Super Admins are PlatformUser rows in the public schema. Staff live in each tenant schema. Super Admins log in at the apex domain, staff at their subdomain.

8. Multi-tenancy design

A tenant is one lab or chain. Branches and collection centres are rows inside a tenant. The public schema holds Tenant, Domain, Plan, Subscription and PlatformUser. Each tenant has its own schema tenant_slug.

OptionVerdict
Database per tenant (NeuroScan)Rejected: N databases and migrations on one VPS
Shared tables with tenant_idRejected: one missed filter is a breach
Schema per tenant (django-tenants)Chosen: strong isolation, built-in per-tenant migrations

Resolution and TLS

Tenants resolve by subdomain (citylab.labflow.app; *.localhost in dev). DNS needs only a wildcard A record. Caddy uses on-demand TLS: before issuing a certificate it calls an internal ask endpoint (/internal/tls-check) that returns 200 only for hosts in the Domain table. No wildcard certificate and no DNS token. Let's Encrypt rate limits apply, so provisioning never loops.

Provisioning (Super Admin → POST /api/v1/platform/tenants/)

  1. Validate, create Tenant (status provisioning) and Domain.
  2. Create schema and run tenant migrations.
  3. REVOKE UPDATE and DELETE on audit tables for the app role, so audit is append-only at database level (repeat for every new schema).
  4. Seed roles, starter catalogue (CBC, LFT, RFT, HbA1c, Lipid Profile, Blood Sugar, Urine R/E, TSH), a 0% revenue-share rule, English and Urdu templates.
  5. Create the Lab Owner with a one-time activation token, set status active, emit TenantProvisioned.

Every step is idempotent; a failed run stays in provisioning and a Celery task retries it.

Migrations and isolation

  • No migration table or Celery task. The deploy script runs migrate_schemas --shared, then migrate_schemas --tenant; django-tenants already records applied migrations per schema. Migrations must be short and safe (no NOT NULL without default, no long locks).
  • Tenant models never carry a tenant column. Isolation comes from the schema; CI fails if a tenant-app model defines tenant or tenant_id.
  • Celery payloads carry tenant_slug and the worker enters tenant_context; a missing context raises an error. No request field selects a tenant.
  • A pytest suite creates two tenants and proves tenant A cannot see tenant B rows for every tenant model; Celery tasks, n8n callbacks and the TLS ask endpoint each have a tenant test.

10. Container diagram

The containers running on the single VPS, grouped in four layers. At the Edge, Caddy (:443, auto-HTTPS with on-demand TLS and the ask check) is the only public entry point: it serves the React SPA as static files and proxies API and admin traffic to Django. The Application layer is Django 5 + DRF (gunicorn, :8000), the Celery Worker — queues: default, reports, notifications, billing, referral_partners, maintenance — and Celery Beat on cron schedules, which hands its work to Redis. The Data layer is PostgreSQL 16 (public + tenant_* schemas), Redis 7 (broker + cache) and Cloudflare R2 / MinIO for reports and bills. In Ops, self-hosted n8n receives signed webhooks from Django, and Sentry receives errors from Django and the worker (dashed lines).

11. Request lifecycle

  1. Browser → Caddy (TLS, certificate on first visit after the ask check) → Django.
  2. Middleware: correlation ID (X-Request-ID), tenant from host (search_path), JWT auth.
  3. Expired access token → 401 token_expired → SPA calls /api/v1/auth/refresh (httpOnly cookie, rotated) → retry.
  4. View reads or writes the tenant schema. Slow work is queued with tenant_slug and an idempotency key (202).
  5. Worker enters tenant_context, does the job, records the result.

The access token lives only in memory; the refresh cookie is httpOnly, Secure, SameSite=Lax, scoped to /api/v1/auth/. SPA and API share one origin in production (no CORS).

Request lifecycle sequence diagram

The same lifecycle drawn as a sequence, steps numbered as in the diagram. Caddy terminates TLS — on a first visit it runs the on-demand TLS check against the ask endpoint — and proxies to Django, where CorrelationIdMiddleware assigns X-Request-ID, TenantMainMiddleware sets search_path = tenant_<slug>, and JWTAuthentication checks the Bearer access token. If the token has expired, Django answers 401 with code=token_expired; the SPA refreshes through POST /api/v1/auth/refresh (httpOnly cookie, validated and rotated by Django), then retries the original request. The view reads and writes the tenant schema in PostgreSQL; async work (PDF, notifications, revenue-share) is enqueued in Redis with the queue, tenant_slug and idempotency key, and the Celery Worker later delivers the task, enters tenant_context(tenant_slug), queries or updates PostgreSQL, and records the task result in Redis.

The clinical path, steps numbered as in the diagram. The technician enters results for a sample; the API stores the Result and ResultValue rows and validates them against the ReferenceRange. Flow C: Referral partner revenue-share and monthly settlement

The money path, steps numbered as in the diagram: payment on an invoice with a partner → RevenueShareRule resolved (partner + test category + branch) → share_ledger_entry row (Decimal amount; the ledger has no status and no settlement_id column) on the paid amount, reversed by a new negative row when a refund is recorded — a refund is itself a payment row with kind = refund (payment.kind: payment | refund, separate from payment.method) → on the 1st of the month at 01:00 Asia/Karachi Beat enqueues the monthly settlement task → the worker takes the ledger entries not yet in any settlement_line, groups them by partner, sums with Decimal, and drafts a Settlement with a settlement_line per ledger entry — an entry's status is derived from its settlement's status via settlement_line → settlement.status → Lab Owner reviews and approves in the SPA → the statement PDF is emailed to the referral partner (v1). Ledger is append-only.

13. Background jobs and n8n

QueuePurposeRetries
defaultGeneral tasks, small emails3, backoff 5 s to 125 s
reportsPDF generation (CPU heavy)5, 10 s to 5 min
notificationsDelivery through n8n5, 30 s to 30 min
billing / referral_partners / maintenanceReminders; monthly settlements; cleanup3 / 3 / 1

Every task is idempotent. There is no custom dead-letter queue: exhausted tasks leave a FAILED row, Sentry alerts, and a 15-minute Beat task retries failed deliveries. Beat (Asia/Karachi): daily 09:00 due reminders; every 15 min retry deliveries; 1st at 01:00 settlements; daily 03:00 token cleanup. Tenant migrations are not a Celery task.

n8n protocol

  1. Django emits an event; the payload is {event, tenant_slug, callback_url, idempotency_key, timestamp, data}, signed with HMAC-SHA256 (N8N_WEBHOOK_SECRET).
  2. n8n verifies the signature, rejects timestamps older than 5 minutes, de-duplicates on the idempotency key, and performs the side effect.
  3. Tenant context for callbacks: n8n calls callback_url on the tenant’s own subdomain, so normal tenant resolution applies. The endpoint also requires the body’s tenant_slug to match the resolved tenant (403 otherwise). The bearer key is a platform secret in env (N8N_CALLBACK_KEY, plus _NEXT for rotation), not a database table.

WhatsApp in v1: n8n builds a wa.me click-to-send link and staff click it (no receipts, not unattended). Upgrade path is the WhatsApp Cloud API; Meta moved to per-message pricing in 2025 as far as I know, so check pricing before relying on any free tier.

14. Security overview

  • JWT access 15 min (memory) + rotating refresh cookie 7 days; TOTP 2FA required for Lab Owner, Branch Manager, Pathologist, Super Admin; argon2; RBAC with object-level scoping.
  • Audit rows for every write touching money, results or reports, append-only via REVOKE per tenant schema.
  • HTTPS and HSTS everywhere; encrypted backups (age, Proposed); secrets only in env and GitHub Actions secrets.
  • Patient report access: random token in a link, stored hashed, valid 7 days, staff can resend or revoke. The backend checks it, then redirects to a pre-signed storage URL valid about 15 minutes.
  • Public verify endpoint returns only valid, report_id and issued_at. Sentry before_send strips patient fields.

15. Data, frontend, deployment

  • Storage: nightly encrypted pg_dump of public and every tenant schema to object storage (7 daily, 4 weekly), monthly restore rehearsal. Redis holds broker, short-TTL cache and rate limits, no patient data. Reports are not deleted in v1; as far as I know R2 free tier gives about 10 GB, which at roughly 150 KB per report is tens of thousands of reports.
  • Frontend: separate SPA, TanStack Query for server state, Zustand for UI only, tenant from host, English and Urdu with RTL, money formatted from API strings and never recomputed.
  • Compose services: caddy, backend (gunicorn :8000), worker, beat, frontend (built into Caddy in prod), postgres, redis, minio (dev only), n8n. Networks: edge and internal; n8n cannot reach postgres. Environments: local (*.localhost), staging, production, same Compose file with different .env.

16. Observability, performance, testing

  • Observability: JSON logs with request_id, tenant_slug and user_id; /healthz, /readyz; Sentry free tier with alerts on exhausted tasks.
  • Scaling order: reports worker on a second VPS → PgBouncer → split worker queues → managed Postgres. Cap about 200 items per report. First visit to a new subdomain pays one certificate issuance. No microservices on the path.
  • Testing: pytest unit and integration, mandatory cross-tenant suite on every PR, OpenAPI schema snapshot, Playwright E2E for the three flows, one manual k6 run before launch. CI: ruff, mypy, eslint, tsc, pytest, pip-audit, npm audit, bandit, trivy, docker build, deploy on tag.
