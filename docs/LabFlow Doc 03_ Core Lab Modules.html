1. Purpose, scope, inputs and assumptions

1.1 Purpose

Doc 01 fixed the architecture. Doc 02 fixed the data model. This document fixes the behaviour of the six core lab modules: what each module does, which rules it enforces, which API it exposes, which states it moves through, and what happens when something goes wrong. After reading it, a developer should be able to build these modules without inventing rules, and defend every rule in review.

1.5 Assumptions

  • AS-1. One tenant is one lab organisation; a branch is a physical site of that lab, including collection centres. A collection centre is a branch row with is_collection_centre = true that can collect and transfer, and cannot enter results unless the owner enables it (OQ-27 resolved, §13).
  • AS-2 (Assumption). A bilingual (English + Urdu) report is a product differentiator, not a verified legal requirement. No source found requires Urdu lab reports in Pakistan (§2, R-17). v1 ships English reports with an Urdu patient-summary block (§9); the legal position is Unverified.
  • AS-3 (Unverified). Punjab Healthcare Commission (PHC) MSDS wording: the MSDS text available to this project is the Khyber Pakhtunkhwa HCC edition, which states it adopts the PHC standards. It is used as a strong proxy. Verbatim Punjab wording must be confirmed from PHC before any compliance claim.
  • AS-4. CAP checklist item numbers cited in §2 come from 2019 CAP training material. They show the expected practice; they are not re-verified against the current CAP checklists.
  • AS-5. ISO 15189 report-content detail in §2 and §9 derives from an accreditation checklist based on the 2012 edition. ISO 15189:2022 is the current edition; its full text is paid and was not read. LabFlow does not claim ISO 15189 compliance.
  • AS-6. Healthwire's lab software feature set could not be verified beyond one marketing sentence (§2, R-16). It is treated as a marketplace channel, not a documented LIS competitor.
  • AS-7. Staff authenticate as staff_user rows; how login works is Doc 08. This document only states which roles may call which endpoints.

3. Design principles for these modules

Every rule in §5 and §6 traces back to one of these principles. When a new case is not covered by a rule, decide by the principles in this order — P-1 outranks all others.

#PrincipleWhat it means in these modules
P-1Patient safety first.A wrong result on the wrong patient is the worst failure this system can produce. Two identifiers on labels (R-3), no sample without a patient, no flag ever guessed (§8.1), no silent merge of duplicate patients (§5.1). When safety and convenience conflict, safety wins and the friction is documented, not hidden.
P-2Nothing clinical is edited in place.Results, approvals, payments, sample events and report versions are append-only or superseded by new rows. A correction creates a new row and moves the old row to a terminal state (amended). The database enforces this where Doc 02 says so (REVOKE UPDATE/DELETE); the API never exposes an update path for these rows.
P-3Every write is audited.Every create, state change and sensitive read writes an audit_log row in the same transaction: actor, role, branch, action, object, before/after for state fields, timestamp. PHC-origin MSDS expects entries to be dated, timed and attributable (R-17); the audit log is how LabFlow answers "who did this, when".
P-4Every retryable action is idempotent.Invoice creation and payment recording take an Idempotency-Key. Celery tasks are safe to run twice (§10). A retried request returns the original result; it never creates a second invoice, a second payment or a second PDF version.
P-5Money is Decimal, end to end.Decimal in Python, numeric(12,2) in PostgreSQL, strings on the wire ("1250.00"). Never float, anywhere. Invoice totals are recomputed on the server from stored rows, never trusted from the client.
P-6The server owns state transitions.Clients request actions (receive, reject, approve); they never PATCH a status field directly. Each action checks the current state and returns 409 invalid_state_transition when the move is not legal. State machines in §5 are the contract.
P-7Branch scope is enforced in the query, not the UI.Every list and detail query for branch-scoped roles is filtered by the caller's staff_branch rows on the server. Hiding a button is not access control. A cross-branch object is indistinguishable from a missing one (404), except where §4 explicitly grants visibility.
P-8Snapshots over live references for anything printed or charged.Invoice items snapshot description and unit_price at billing time. The PDF prints the reference range selected at approval time. Later catalog edits never change what a patient was charged or what a report said.
P-9Fail loud, recover by retry, never guess.Unparseable result value → flag NULL + mandatory pathologist review, not a guessed flag (§8.1). PDF failure → visible failed state + retry, not a silent missing report (§10). Unknown reference range → flag NULL, not the nearest range.
P-10Boring technology, explicit trade-offs.One PostgreSQL database, one Celery setup, server-rendered PDF. Each "NOT built" item in §15 names what was given up and why. If a rule cannot be explained in two sentences, it does not ship.

4.2 Branch scoping rules

  • BS-1. owner and pathologist are tenant-wide (Doc 02 §5.1): branch_id is NULL on their staff_user row and they need no staff_branch rows. They can read and act in every branch of the tenant.
  • BS-2. manager, reception and technician act only in branches where a staff_branch row exists for them. An account with zero staff_branch rows can log in but every branch query returns empty and every branch write returns 403 branch_scope_denied.
  • BS-3. Object scope follows the object, not the caller: a patient is scoped by patient.branch_id (registering branch), an invoice by invoice.branch_id, a sample by its current holding branch (sample.branch_id, updated on transfer receipt). Results and reports inherit the scope of their sample.
  • BS-4. Patient search is the one deliberate exception: a receptionist may search patients across the tenant by exact phone or MRN to prevent duplicate registration, but the response shows only name, MRN, sex and year of birth for out-of-branch matches — no clinical or billing history. Full detail requires branch scope. (Duplicate prevention is a patient-safety feature, R-16; the data exposure is minimised to identifiers.) Managers get the same identifiers-only exception (OQ-26 resolved, §13).
  • BS-5. Catalog (tests, panels, prices, ranges) is tenant-wide reference data: readable per the matrix in §4.3, writable only by Owner, plus Pathologist for reference ranges. Prices live in test_price (Doc 02 v1.3) and are tenant-wide, so there is no per-branch price editing in v1.
  • BS-6. A transfer moves scope: after TRANSFERRED_IN, the sending branch keeps read access to the sample's history via sample_event, but only the receiving branch can act on it.

Rule IDs (for example BL-3) are stable references for code reviews and tests.

5.1 Patients

Responsibility. One durable identity per real person per tenant: registration, identity fields, search, duplicate prevention, contact and consent records, soft delete. Every other module points at this identity; nothing else in the system stores patient name or phone.

Tables used. patient; patient_contact (Doc 02 v1.3); patient_consent (Doc 02 v1.3); reads branch for branch_code (MRN format, Doc 02 §9).

Business rules

  • PT-1. MRN is assigned by the server at registration: MRN-{branch_code:3}-{seq:06d} (Doc 02 §9), unique per tenant, never reused, never editable. The registering branch is stored in patient.branch_id.
  • PT-2. A patient is identified by two identifiers wherever a human confirms identity: name + MRN, or name + date of birth (R-3). Phone alone is a search key, never proof of identity.
  • PT-3. Registration checks for duplicates before insert: exact phone match, or pg_trgm name similarity plus same date of birth. A possible duplicate returns 409 possible_duplicate with the candidate list (identifiers only, per BS-4); the receptionist must explicitly confirm "register anyway" to proceed. The system never merges two patients automatically — a wrong merge is a patient-safety incident (P-1).
  • PT-4. Name, phone, sex and date of birth are editable while the patient has no finalised report. After the first finalised report, identity edits (name, sex, date of birth) require Owner or Manager and are written to audit_log with before/after values; already-issued PDFs are never regenerated to match — a wrong identity on an issued report is fixed by voiding and reissuing (§5.6).
  • PT-5. Delete is soft only: deleted_at is set. Soft-deleted patients disappear from search but their invoices, samples, results and reports remain readable by ID for audit. Hard delete does not exist in v1.
  • PT-6. date_of_birth may be NULL (patient does not know it). Age-dependent behaviour degrades explicitly: reference-range selection falls back per §8.2 and the report prints "Age: not recorded" instead of an age.
  • PT-7. Contacts and consents (WhatsApp number, report-delivery consent) live in patient_contact / patient_consent (both in Doc 02 v1.3). Delivery to a contact with no consent row is refused by the reports module (§5.6, RP-6).

Validation rules

  • PT-V1. name: required, 2–120 characters after trim. phone: required, normalised to digits with country code stripped of spaces and dashes; must be 10–15 digits. sex: M | F only (Doc 02). date_of_birth: a valid date, not in the future, not more than 120 years ago.
  • PT-V2. A second patient with the same phone is allowed only through the PT-3 confirm path (families share phones).

State machine. None — a patient has no lifecycle states, only the deleted_at soft-delete marker.

Events emitted. patient.registered, patient.updated, patient.soft_deleted.

Celery tasks. None.

Audit points. Registration, every update (field-level before/after), duplicate-confirm override (with the candidate MRN shown), soft delete, and every cross-branch detail view under BS-4.

Edge cases

  • Same phone, different people (family). PT-3 confirm path; both records keep the shared phone. Search by phone returns both.
  • Patient registered at branch A presents at branch B. BS-4 search finds the record; branch B can bill against it (the invoice carries branch B), but the patient row keeps branch_id = A. Patient detail history remains scoped per BS-3; managers get the same identifiers-only cross-branch search as BS-4 (OQ-26 resolved, §13).
  • Newborn with no name yet. Register under the mother's name plus "baby of" convention is a lab SOP matter, not a schema feature; the system requires a non-empty name (PT-V1). No special-case code in v1.
  • Typo in MRN on a printed label. MRN is server-generated (PT-1) and labels are printed from stored data (§7 workflow 2), so this cannot occur from manual typing.

5.2 Catalog

Responsibility. What the lab sells and how results are judged: tests, panels and their component tests, per-branch-effective prices, and reference ranges. The catalog is configuration, not clinical data — but it is snapshotted into billing and reports (P-8) so history never moves.

Tables used. test, panel, panel_test, test_price (Doc 02 v1.3), reference_range. Seeded per Doc 02 §16.

Business rules

  • CT-1. A panel is a priced bundle of component tests (panel_test). Ordering a panel creates one invoice_item for the panel and, at sample creation, one sample_test row per component test. Panels never nest.
  • CT-2. Prices are effective-dated rows in test_price. The price charged is the row effective on the invoice date. Changing a price closes the old row and opens a new one; existing invoices are unaffected because invoice_item.unit_price is a snapshot (P-8).
  • CT-3. A test with no effective price cannot be added to an invoice: 422 test_not_priced. The lab fixes its price list instead of billing 0.00 by accident.
  • CT-4. Reference ranges are effective-dated (effective_from / effective_to) and keyed by test, sex (M | F | B) and age band in days (age_min_days / age_max_days), per Doc 02 §10. Editing a range closes the current row and opens a new one; overlapping bands for the same test + sex are rejected (422 overlapping_range) so selection in §8.2 is deterministic.
  • CT-5. A test may be deactivated (not orderable) but never deleted once it appears on any invoice_item or result. Deactivation does not affect samples already in flight.
  • CT-6. Each test declares its result kind implicitly: a test is numeric if any effective reference_range row has low or high NOT NULL; otherwise it is qualitative (§8.4). There is no separate type flag to drift out of sync.

Validation rules

  • CT-V1. Prices: Decimal string, ≥ 0, at most 2 decimal places; a price of exactly 0 is allowed only with the test flagged free by Owner action and is still an explicit row (CT-3 still applies — the row must exist).
  • CT-V2. Ranges: low < high when both are present; unit is required on every range row (Doc 02: unit NOT NULL); age_min_days ≥ 0; age_max_days NULL means "no upper bound". Adult bands start at 6570 days (18 years).
  • CT-V3. A panel must contain at least one component test and cannot contain a deactivated test at save time.

State machine. None. Tests and panels have an active/inactive flag only.

Events emitted. catalog.test_created, catalog.price_changed, catalog.range_changed, catalog.panel_changed.

Celery tasks. None.

Audit points. Every catalog write, with before/after for price and range rows (who changed a range, and when, is a clinical-governance question — R-10).

Edge cases

  • Price changes between billing and payment. Irrelevant by design: the invoice holds snapshots (CT-2).
  • Panel price vs sum of components. The panel's own price is charged; component prices are not summed. If the panel price is missing, CT-3 blocks the panel too.
  • A range row effective in the future. Allowed (scheduled change). Selection in §8.2 uses the sample's collection date, so a future range never rewrites a past result's flag.
  • Test in two panels. Allowed. sample_test uniqueness is per sample + test, so ordering both panels for one sample produces one sample_test row per distinct test, linked to the first invoice item that introduced it; the second panel's overlapping component is billed (it was ordered) but tested once. This is stated behaviour, tested in §12 (T-14).

5.3 Billing

Responsibility. The money record of a visit: invoice creation with price snapshots, discounts, payments, refunds, cancellation, and the derived invoice status. Billing never touches clinical data; samples module reads the invoice to know what was ordered.

Tables used. invoice, invoice_item, payment (append-only); reads patient, test, panel, test_price, referral_partner (partner attribution only — share calculation is Doc 05).

Business rules

  • BL-1. An invoice belongs to one patient and one branch. referral_partner_id is NULL for walk-ins. Items reference a test_id XOR a panel_id; description and unit_price are snapshots taken at creation (Doc 02, P-8).
  • BL-2. Totals are server-computed: subtotal = Σ unit_price × qty; total = subtotal − discount_amount (Doc 02). The client sends items and a discount, never totals. Any client-sent total is ignored.
  • BL-3. discount_amount > 0 requires discount_reason (Doc 02) and a Manager or Owner role. Receptionists cannot discount (403 discount_not_permitted).
  • BL-4. Invoice creation requires an Idempotency-Key header. The key is stored in invoice.idempotency_key (UNIQUE, partial — Doc 02). A replay with the same key and the same payload returns the original invoice with 200; the same key with a different payload returns 409 idempotency_key_reused (§10).
  • BL-5. Payments are append-only rows in payment. kind says whether money moved in (payment) or out (refund); amount is always positive; kind supplies the sign (Doc 02 §5.4, OQ-23 resolved). A payment row is never updated or deleted — a mistake is corrected by a compensating refund row.
  • BL-6. Invoice status is derived, never set directly: let net = Σ payments − Σ refunds. net = 0 and no payment ever recorded → unpaid; 0 < net < total → partial; net = total → paid; net = 0 and at least one payment and one refund exist → refunded; cancelled is the only status set by an explicit action (BL-8). The stored invoice.status is updated in the same transaction as each payment insert, from this formula, so the two can never disagree.
  • BL-7. A payment is rejected when it would make net > total (422 overpayment), and a refund is rejected when cumulative refunds would exceed cumulative payments (422 refund_exceeds_payments). Refunds also require reference or a reason note for non-cash methods, and Manager or Owner role (§4.3). A refund fires the revenue-share reversal hook for Doc 05 (an event, §7 workflow 8 — the ledger write itself is Doc 05's).
  • BL-8. Cancellation: an invoice may be cancelled only while status = unpaid and no sample has been collected against it. Cancelling is a status change with an audit row, not a delete. A paid or partial invoice is never cancelled — it is refunded (BL-7), which keeps the money trail complete.
  • BL-9. Sample collection is blocked while the invoice is cancelled. Collection against unpaid or partial invoices is allowed — labs routinely collect before full payment; the report release is what billing can hold (RP-7, §5.6). The hold is the tenant_setting key billing_hold_enabled (Doc 04 §10.2), default false (OQ-33 resolved, §13).
  • BL-10. Payment method is one of cash | card | bank_transfer | easypaisa | jazzcash | other (Doc 02). Raast transfers are recorded as bank_transfer with the Raast ID (sender mobile number) in reference (R-18). Easypaisa / JazzCash payments record the wallet transaction ID in reference; reference is required for every non-cash method (422 reference_required).

Validation rules

  • BL-V1. Money fields are Decimal strings with at most 2 decimal places, ≥ "0.01" for payments and refunds, ≥ "0.00" for discounts. Floats in JSON are rejected by the serializer (422 money_must_be_string) — a JSON number for money is a bug, not input.
  • BL-V2. qty is an integer ≥ 1. Duplicate test or panel lines on one invoice are merged by summing qty only when they are the same item kind; a test and a panel containing that test may coexist (CT edge case, §5.2).
  • BL-V3. received_by is the authenticated staff user; it is never taken from the request body.

State machine — invoice

stateDiagram-v2
  [*] --> unpaid: invoice created
  unpaid --> partial: part payment recorded
  unpaid --> paid: full payment recorded
  partial --> paid: balance recorded
  unpaid --> cancelled: cancelled before any payment
  partial --> refunded: refunds equal amount paid and total not reached
  paid --> refunded: refunds equal amount paid
  paid --> partial: partial refund recorded
  partial --> partial: partial refund recorded

Invoice states (Doc 02 CHECK: unpaid, partial, paid, refunded, cancelled). All transitions except cancel are derived from payment rows by rule BL-6.

Events emitted. invoice.created, invoice.cancelled, payment.recorded, payment.refunded, invoice.status_changed (with from/to).

Celery tasks. None in this module. The refund event is consumed by Doc 05's share-reversal logic; the notification of a refund receipt, if the tenant enables it, is a Doc 06 workflow.

Audit points. Invoice create (including idempotency key), discount (with reason), every payment and refund row, cancellation, and every derived status change.

Edge cases

  • Double-tap "Pay" on a slow connection. Same Idempotency-Key → the original payment is returned; no double charge (BL-4 pattern applied to payments, §6.4).
  • Refund after the report was delivered. Allowed. Money and clinical records are independent; the refund does not void the report. Doc 05 reverses the share.
  • Partial refund then another partial refund. Each is a new payment row with kind = refund; status recomputed by BL-6 after each.
  • Invoice with a panel whose price changed after creation. Snapshot wins (CT-2). The patient pays what was quoted.
  • Zero-total invoice (full discount). total = "0.00" with discount_amount = subtotal and a reason (BL-3). Status derivation: net = 0 = total and no payments — BL-6 is applied with the special case that a zero-total invoice is created directly in paid status, because there is nothing to collect. This exception is deliberate and tested (T-09, §12).

5.4 Samples

Responsibility. The physical specimen's digital twin: collection, accessioning, labelling, movement between branches, bench receipt, processing, rejection and recollection. If it happened to the tube, it is an event here.

Tables used. sample, sample_test (Doc 02 v1.3), sample_event (append-only), sample_transfer (Doc 02 v1.3); reads invoice / invoice_item (what was ordered), patient (label identity).

Business rules

  • SM-1. One sample is created per collection event against one invoice. Creating the sample generates the accession ID server-side: {tenant_prefix:3}{YYYYMMDD}{seq:06d}, for example CIT20261019000042 (Doc 02 §9). The client never supplies it.
  • SM-2. At creation, one sample_test row is inserted per distinct ordered test (panels expanded via panel_test, §5.2). sample_test is the worklist contract: a result is expected exactly when a row exists (Doc 02 §5.5).
  • SM-3. Collection records collected_at (server time, Asia/Karachi) and collected_by (authenticated user), sets status = collected, branch_id = collecting branch, and writes the first sample_event (COLLECTED) in the same transaction.
  • SM-4. The label is printed from stored data only: accession ID as Code128 barcode payload, patient name, MRN, date of birth if recorded, collection date-time, collector (R-4). Two identifiers are always on the label (R-3). There is no free-text label endpoint — a hand-typed label defeats the barcode.
  • SM-5. Every status change writes a sample_event row in the same transaction as the status update. sample_event is append-only; the pair (status, event) can never disagree. The timeline endpoint (§6.5) reads events only.
  • SM-6. Receipt at the bench (collected → received) is a deliberate scan or confirm action by Technician or Manager at the holding branch. Receipt checks are the rejection gate: identity matches the label, tube type correct, volume sufficient (R-1, R-2).
  • SM-7. Transfer: a sample may be transferred only while its status is collected or received. An in_process sample cannot be transferred — bench work has started on it, and receipt at the other branch would move it backwards to received. Transfer out creates a sample_transfer row (Doc 02 v1.3) with status = open and dispatched_at set — dispatched_at is the moment the sending branch hands the sample to the courier, and it is set when the transfer is created — plus a TRANSFERRED_OUT event; the sample's own status does not change while the transfer is open. Receipt at branch B sets the transfer's status = received and received_at, writes TRANSFERRED_IN, moves sample.branch_id to B, and sets the sample status to received. sample_transfer.status is one of open | received | cancelled | lost, enforced by the application (Doc 02 v1.3, A-9). A lost transfer does not change sample.status: marking a transfer lost closes the transfer only, and the sample is then resolved through reject-sample (SM-8) and recollect (SM-9) — a developer must not assume that lost auto-closes the sample. Cancellation and loss are Doc 04 §9.2 behaviour, exposed by the endpoints in §6.5. A sample with an open transfer cannot be transferred again, rejected, or resulted until the transfer is received or cancelled by the sender (§10). Custody is never ambiguous: exactly one branch holds the sample at any time (R-5).
  • SM-8. Rejection requires a reason code from the v1 list: unlabelled, mislabelled, hemolyzed, insufficient_volume, wrong_tube, clotted, lipemic, damaged_transport, barcode_issue, other (with a mandatory note). The code list follows R-1. The code is stored in sample.rejection_reason_code and the note in sample.rejection_note (Doc 02 v1.2, amendment A-2 accepted, §14), and is also carried in the REJECTED event payload and the audit row.
  • SM-9. Rejection is terminal for that sample but not for the order: a recollect action creates a new sample against the same invoice, copies the still-untested sample_test rows, and links the two samples in audit_log (old accession → new accession). The patient is not billed again for a lab-caused rejection; a patient-caused recollection (for example non-fasting for a fasting test) is a new invoice — that distinction is a Manager decision recorded in the audit note, not an automatic rule.
  • SM-10. A sample becomes ready automatically when every sample_test row has an approved result (§5.5). No user sets ready by hand. ready is the trigger for report generation (§5.6).
  • SM-11. Cancellation of a sample is allowed only from collected or received, by Manager or Owner, with a reason. Once any result exists (even entered), the sample cannot be cancelled — the clinical trail must be resolved through result rejection instead.

Validation rules

  • SM-V1. The invoice must exist, belong to the caller's branch scope (or be tenant-visible to Owner), and not be cancelled (BL-9).
  • SM-V2. collected_at is server time. A client-supplied collection time (home sampling) is accepted only as a separate note field and never overwrites the server timestamp in v1 — backdating a collection time corrupts TAT (§11) and range ageing (§8.2). No backdating is allowed, and home collection is not built in v1 (OQ-34 resolved, §13).
  • SM-V3. Reject and cancel actions require a non-empty reason; reject requires a code from SM-8.

State machine — sample

stateDiagram-v2
  [*] --> collected: sample collected and labelled
  collected --> received: received at bench
  collected --> rejected: rejected at collection point
  received --> in_process: analysis started
  received --> rejected: rejected on receipt checks
  in_process --> ready: all results approved
  in_process --> rejected: rejected during processing
  collected --> cancelled: order cancelled
  received --> cancelled: order cancelled

Sample states (Doc 02 CHECK: collected, received, in_process, ready, rejected, cancelled). A transfer does not change the sample's status while it is open, and transfer is allowed only from collected or received — an in_process sample cannot transfer (SM-7). On receipt the sample becomes received at the destination branch.

Events emitted. sample.collected, sample.received, sample.in_process, sample.transferred_out, sample.transferred_in, sample.rejected, sample.ready, sample.cancelled, sample.recollected. Domain events mirror sample_event types one-to-one.

Celery tasks. samples.notify_rejection (notifications queue, Doc 01 §13) — tells the patient and the collecting branch that a recollection is needed, using notification_template in the tenant default language — the tenant_setting key report_default_language (Doc 04 §10.2). Doc 02 has no per-patient language column, so the tenant default is used until a per-patient language exists (OQ-30, Doc 07). No other tasks; state changes are synchronous.

Audit points. Collection, every event (the event row itself is the audit), transfer create and receive, rejection (actor, code, note), recollection link, cancellation.

Edge cases

  • Two samples for one invoice (split tubes). Allowed: CBC and LFT drawn into two tubes is two sample rows, two accession IDs, each with its own sample_test subset. The create endpoint accepts an explicit list of invoice items per sample; without a list it takes all untested items.
  • Sample scanned at the wrong branch. Receipt by a branch that does not hold the sample returns 409 sample_not_here with the holding branch named — a custody error is surfaced, not silently accepted (SM-7).
  • Transfer never received (lost in transit). The transfer stays open; the sample appears on the sender's "in transit over 24 h" exception list (§11). There is no auto-receive and no auto-loss state in v1 — a human resolves it, and the resolution is audited.
  • Rejection after a result was entered. Refused (409 sample_has_results). The entered result must be rejected through the results flow first; the sample record must not strand a live result (SM-11 logic).
  • Barcode will not scan (damaged label). Reprint from stored data (SM-4) — same accession ID, event barcode_issue noted in audit. A sample never gets a second accession ID for the same tube.

5.5 Results

Responsibility. The clinical record: entry of values against sample_test rows, flag computation, two-person verification, approval, rejection, and amendment. This module is where patient safety is won or lost, so its rules are the strictest in the document.

Tables used. result, result_approval (append-only), critical_notification (append-only, Doc 02 v1.2); reads sample_test (what is expected), reference_range (flag computation), sample and patient (age/sex at collection).

Business rules

  • RS-1. A result can be created only for an existing sample_test row (sample + test). Entering a result for a test that was not ordered returns 422 test_not_ordered. This is the guard against results appearing for work nobody billed or consented to.
  • RS-2. result.value is stored exactly as entered (text, Doc 02). The engine computes flag and stores the parsed form separately in the response, never by rewriting value (§8.1). unit defaults to the matched range's unit and is stored on the result.
  • RS-3. Entry requires the sample in received or in_process. The first entry moves received to in_process (with the IN_PROCESS event) — bench reality is that entry is the start of processing. One branch-level rule applies on top of this state rule: at a branch where branch.is_collection_centre = true and branch.result_entry_enabled = false (Doc 02 v1.3, A-8), result entry is refused with 403 result_entry_disabled_at_branch, regardless of the sample state.
  • RS-4. A result in entered state may be corrected by its author only by superseding: the old row is marked rejected by a pathologist decision, or withdrawn by the author before any approval decision exists. Author withdrawal sets result.status = withdrawn, writes no result_approval row, and is recorded in audit_log only. There is no UPDATE of value on a saved result row (P-2).
  • RS-5. Approval is a separate act by a Pathologist, recorded as a result_approval row: decision (approved | rejected), note, range_override flag, pathologist, timestamp. Approval and rejection are the only ways out of entered besides RS-4 withdrawal. A rejected result returns the sample_test row to the pending worklist; the rejected result row is kept read-only.
  • RS-6. Self-approval: a Pathologist who entered a result may not approve it, unless the tenant has exactly one active pathologist account, in which case self-approval is permitted and the result_approval row records range_override = false plus the audit note single_pathologist_self_approval. Small labs are the market (R-7's two-person pattern assumes staff LabFlow's customers may not have). The exception is visible in audit, never silent.
  • RS-7. Range override: a Pathologist may approve a result whose computed flag they judge clinically misleading (for example a haemolysed sample known to skew potassium). That approval must set range_override = true and a non-empty note (422 override_note_required otherwise). The computed flag stays on the result; the override is shown on the internal view, and the report prints the flag with the pathologist's comment (§9).
  • RS-8. When every sample_test row of a sample has an approved result, the sample moves to ready (SM-10) and the reports module is triggered. Partial approval is a normal, stable state — the sample waits in in_process (§10).
  • RS-9. Amendment: an approved result is never changed. A correction creates a new result row for the same sample_test (status entered), and when the new row is approved, the old row's status becomes amended in the same transaction. If the sample already has a final report, the amendment triggers a new report version (§5.6, RP-4). The amendment requires a reason note on the new row's approval.
  • RS-10. Results with flag NULL (unparseable value, no matching range, qualitative) can be approved, but the approval screen marks them "no auto flag" and — for numeric tests with unparseable values — approval requires a note (P-9, §8.1).

Validation rules

  • RS-V1. value: required, non-empty after trim, max 500 characters. Stored verbatim (only leading/trailing whitespace trimmed).
  • RS-V2. Batch entry (§6.6) is all-or-nothing per sample: if any row fails validation, no rows are saved and the error lists every failing test. A bench batch half-saved is a wrong-results incident waiting to happen.
  • RS-V3. entered_by is the authenticated user. A Technician entering results must have branch scope on the sample's holding branch (BS-3).

State machine — result

stateDiagram-v2
  [*] --> entered: value saved by technician or pathologist
  entered --> approved: pathologist approves
  entered --> rejected: pathologist rejects
  entered --> withdrawn: author withdraws before any approval decision
  approved --> amended: superseded by an approved correction
  rejected --> [*]: kept read only, sample test returns to worklist
  withdrawn --> [*]: kept read only, no approval row, audit only

Result states (Doc 02 v1.2 CHECK: entered, approved, rejected, amended, withdrawn). Withdrawal writes no result_approval row — audit only. A correction is always a new row; no state moves backwards.

Events emitted. result.entered, result.approved, result.rejected, result.amended, result.withdrawn, result.critical_flagged (fires when a result is flagged critical, §8.5), sample.ready (via samples module).

Celery tasks. reports.generate_pdf is enqueued when a sample becomes ready and when an amendment completes (§5.6). results.notify_critical (notifications queue) fires on approval of a critical-flagged result and prompts for the notification to be recorded in critical_notification (Doc 02 v1.2, §8.5); a Pathologist or a Branch Manager records it.

Audit points. Entry (author, value), every approval decision (pathologist, decision, note, override), withdrawal, amendment chain (old result ID → new result ID), and every approval of a flag-NULL result.

Edge cases

  • Two technicians enter the same test. The second save finds an existing entered result for that sample_test and returns 409 result_already_entered with the existing result ID and author. No silent overwrite (§10).
  • Pathologist rejects a result the patient is waiting for. Normal flow: the test returns to the worklist with the rejection note visible to technicians. The sample stays in_process; no patient-facing message is sent for an internal rejection.
  • Result entered against the wrong sample. Caught by RS-4/RS-5 (withdraw or reject before approval). If already approved, only the amendment path (RS-9) fixes it, and if a report was issued, RP-4's amended-report notice applies. There is no "move result to another sample" operation — that is exactly how wrong-patient results happen (P-1).
  • Value with a comparator, for example "<0.1". Parsed per §8.1: the comparator is kept as a qualifier, the numeric part drives the flag.
  • All results approved but one test was cancelled by the lab. There is no per-test cancel in v1; the pathologist rejects the entered placeholder is not allowed either. Chosen behaviour: a sample_test row can only leave the pending set via an approved result or sample rejection. A test the lab cannot perform means the sample (or that tube) is rejected with reason other and a note, and billing issues a refund for the untested item (Manager action, BL-7). Resolved in OQ-35 (§13): v1 uses reject-sample plus refund; per-test cancel is post-v1.

5.6 Reports

Responsibility. The patient-facing artefact: turning approved results into a versioned PDF, delivering it, and controlling patient access to it. One report per sample in v1 (Doc 02 §11, known limitation).

Tables used. report, report_version (append-only), report_delivery, report_access_token; reads sample, result, reference_range, patient, patient_contact / patient_consent (Doc 02 v1.3), notification_template.

Business rules

  • RP-1. A report row is created when a sample first becomes ready: status = draft, current_version = 0. PDF generation is a Celery task (reports.generate_pdf, reports queue — Doc 01 §13), never a synchronous request: G1 allows 60 s at p95 and the request must not wait for WeasyPrint.
  • RP-2. Successful generation inserts a report_version row (version = current_version + 1, pdf_key = reports/{report_id}/{version}.pdf), sets report.current_version, status = final (first version) and finalised_at. The PDF bytes are immutable once written; object storage versioning is not relied on — the key itself is versioned.
  • RP-3. The PDF content is frozen at generation time from approved results and the ranges selected for them (P-8). Later catalog or range edits never change an existing version.
  • RP-4. Amendment: when an approved result is amended (RS-9) on a sample whose report is final, a new version is generated; report.status becomes amended and the new PDF carries the amended notice (§9.4) listing each changed test with old and new values (R-12). The old version stays downloadable by staff; patient links always resolve to the current version (§5.6 RP-8), so a patient who reopens an old link sees the corrected report, with the notice explaining why it changed.
  • RP-5. Voiding (status = void) is Owner or Pathologist only, with a reason, and only makes sense before delivery or when the wrong patient was reported. Voiding revokes all access tokens immediately (RP-8) and blocks delivery. A voided report is never deleted; reissue means a new sample/report flow, not un-voiding.
  • RP-6. Delivery creates report_delivery rows per channel (email | whatsapp) with status PENDING → SENT | FAILED | BOUNCED, and OPENED when the patient link is first used. Sending is a Celery task (reports.deliver, notifications queue); failed deliveries retry via the Beat sweep every 15 minutes using attempts / next_attempt_at (Doc 02). WhatsApp delivery stores the whatsapp_url hand-off; the message body comes from notification_template in the tenant default language — the tenant_setting key report_default_language (Doc 04 §10.2). Doc 02 has no per-patient language column, so the tenant default is used until a per-patient language exists (OQ-30, Doc 07). No delivery without a consent row (PT-7).
  • RP-7. Billing hold (tenant setting, default off in v1): if enabled, delivery is blocked while the sample's invoice is not paid; the report still generates and staff can view it. The hold never blocks the pathologist or the PDF — only patient delivery. The setting is the tenant_setting key billing_hold_enabled (Doc 04 §10.2), default false (OQ-33 resolved, §13).
  • RP-8. Patient access: issuing a link creates a report_access_token row storing only token_hash (argon2 hash of 32 random bytes); the plain token exists once, inside the delivery message. For a new token, expires_at is counted from issue using the tenant_setting key report_link_validity_days (Doc 04 §10.2); when the tenant has no row for that key, the platform default of 7 days applies. expires_at is stored on each report_access_token row (Doc 02 §5.7), so changing the setting later never changes tokens already issued. Opening the link validates hash, expiry and revoked_at, sets last_accessed_at, marks delivery OPENED, and redirects (302) to a pre-signed storage URL for the current version's pdf_key, valid about 15 minutes (Doc 01 §14). The token is reusable inside its validity period (patients reopen reports; a one-time token would fail G6's two-click goal on the second open). Revocation is instant and per report.
  • RP-9. An expired or revoked token returns a plain "link expired" page (410) with the lab's phone number — never a login wall and never the PDF. Staff reissue from the report screen, which mints a fresh token row; old rows remain for audit.

Validation rules

  • RP-V1. Generation requires at least one approved result and report.status in draft | final | amended. Generating against a void report returns 409 report_void.
  • RP-V2. Delivery requires report.status in final | amended and current_version ≥ 1: no patient ever receives a draft (409 report_not_final).
  • RP-V3. The public access endpoint takes only the token. No patient ID, MRN or report ID is accepted as an alternative credential.

Report states (Doc 02: draft, final, amended, void). Versions only ever increase; a version number is never reused.

Events emitted. report.created, report.version_generated, report.finalised, report.amended, report.voided, report.delivery_sent, report.delivery_failed, report.accessed, report.token_revoked.

Celery tasks. reports.generate_pdf (reports queue: 5 retries, backoff 10 s–5 min, Doc 01 §13); reports.deliver (notifications queue: 5 retries, 30 s–30 min); reports.retry_deliveries Beat sweep every 15 minutes picking up report_delivery rows with status = FAILED and next_attempt_at ≤ now (Doc 02).

Audit points. Generation (trigger: automatic or named user for manual regenerate), every version, delivery attempts and outcomes, token issue/revoke, every patient access (token ID, time, IP — security detail in Doc 08), void with reason.

Edge cases

  • PDF generation keeps failing (bad template data). After the queue's retries the report stays draft (or keeps its previous version) with a visible failure state on the report screen and an alert event; staff can retry manually. A failed generation never produces a partial report_version row (§10).
  • Patient opens the link after an amendment. They get the current (amended) version with the amended notice (RP-4). The token does not pin a version — pinning would let a patient keep acting on a wrong result (P-1).
  • Two deliveries race (email + WhatsApp). Independent report_delivery rows; OPENED is set by whichever link is used first; the second channel is not cancelled (patients lose messages).
  • Report for a sample whose invoice was refunded. The report stands (BL edge case). Delivery rules unchanged.
  • Storage upload succeeds but the DB write fails. The orphaned object is harmless: its key is deterministic and the retry overwrites the same key before inserting the version row (§10).

6. API reference

6.1 Conventions

  • Base path and tenancy. All endpoints are under /api/v1. The tenant is resolved from the request host by django-tenants (Doc 01); no endpoint accepts a tenant identifier in the path or body. A request to the wrong tenant's host simply sees that tenant's data — schema isolation does the work (tested in §12).
  • Authentication. Staff endpoints require an authenticated staff_user (mechanism: Doc 08). Unauthenticated → 401. The only unauthenticated endpoint is the patient report link (§6.8), which is authorised by the token itself.
  • Role codes. O, M, R, T, P as defined in §4.1. Branch scoping (BS-1 to BS-6) applies to every endpoint.
  • Pagination. Cursor pagination on every list: query params cursor (opaque, from the previous response) and limit (default 50, max 200). Response: { "results": [...], "next_cursor": "..." | null }. Ordering is stable: created_at DESC, id DESC unless an endpoint says otherwise. Offset pagination is not offered — worklists change while staff page through them, and a cursor does not skip or repeat rows.
  • Filtering. Query parameters only, named after fields: status, branch_id, patient_id, q (search text where defined), created_after / created_before (ISO 8601). Unknown filter parameters are ignored; unknown values for enum filters return 422.
  • Errors. All errors are application/problem+json (RFC 9457 shape): 
    {
  "type": "https://labflow.example/problems/invalid-state-transition",
  "title": "Invalid state transition",
  "status": 409,
  "detail": "Sample is already received; it cannot be received again.",
  "code": "invalid_state_transition",
  "errors": { "status": ["already received"] }
}
    code is the machine-stable field; clients branch on code, never on detail. Standard codes: validation_error (422), not_found (404), forbidden (403), branch_scope_denied (403), invalid_state_transition (409), version_conflict (409), idempotency_key_reused (409), plus the endpoint-specific codes named in the tables.
  • Money. Always strings with 2 decimal places: "1250.00". Currency is PKR for every tenant in v1 (Doc 01) and is not repeated per field. JSON numbers for money are rejected (422 money_must_be_string, BL-V1).
  • Times. ISO 8601 with offset, Asia/Karachi: "2026-10-20T11:46:59+05:00". Dates (date of birth, effective dates) are plain YYYY-MM-DD. The server stores UTC; the offset shown is always +05:00 in v1.
  • Idempotency. POST /invoices and POST /invoices/{id}/payments require an Idempotency-Key header (a client-generated UUID). All other action endpoints are naturally idempotent or state-guarded: repeating them returns the current state or 409 invalid_state_transition, never a duplicate effect. Celery-triggering actions deduplicate per §10.
  • Optimistic concurrency. Detail responses carry updated_at. PATCH endpoints and action endpoints accept If-Match: <updated_at value>; if the row changed since, the response is 409 version_conflict and nothing is written. This is how two staff editing one patient or one sample is resolved (§10) without locking anyone out of reads.
  • Audit. Every non-GET endpoint writes an audit_log row (P-3); the tables below name the audit action. Sensitive GETs (patient detail, report PDF download by staff) are audited too and say so.

8. Result engine rules

The result engine is the small pure function set that turns an entered value into a flag. It runs at entry time (§6.6) and its inputs are only: the value text, the patient, the sample, and the reference_range rows. It has no side effects. This section resolves Doc 02's OQ-25; the resolution is also recorded in §13.

8.1 Parsing result.value (OQ-25 resolution)

Decision: result.value stays text, stored exactly as entered. Labs receive comparators ("< 0.1"), semi-quantitative grades ("2+") and words ("Positive") from real benches; a numeric column would reject real results or force staff to lie to the form. Parsing happens at flag-computation time, by these rules, in this order:

  1. Trim leading and trailing whitespace. The trimmed text is what is stored.
  2. Comparator: if the text starts with <=, >=, < or >, that prefix is the qualifier and the rest is the body. The qualifier is not stored separately — it is part of value and is re-derived on every read, so display and flag logic can never disagree about it.
  3. Test kind: find the matched range row (§8.2). If it has low or high NOT NULL, the result is treated as numeric. Otherwise it is qualitative (§8.4).
  4. Numeric parse: for a numeric result, remove spaces and comma thousands separators from the body, then parse with Decimal. Scientific notation is not accepted. Success gives the numeric value n. Failure — empty body (a bare "<"), letters, "trace", multiple decimal points — gives no number.
  5. Flag from a number: n < low → low; n > high → high; otherwise normal. If the matched row defines critical_low / critical_high and n is beyond them, the flag is critical instead (§8.3, §8.5). Bounds are inclusive: a value exactly on low or high is normal. A missing bound is not checked (a range may define only high). The flag is computed from the numeric part; the qualifier is displayed beside the value ("< 5.0") and the pathologist sees both at approval.
  6. No number: if parsing fails for a numeric test, flag = NULL and the result is marked needs_review in API responses. It can still be approved, but only with a pathologist note (RS-10). The engine never guesses a flag (P-9): a guessed "normal" on an unparseable critical value is the exact failure this rule exists to prevent.
  7. No matched range: if §8.2 selects no row, flag = NULL. The value, unit (as entered, may be NULL) and the absence of a flag are shown plainly; approval proceeds under RS-10.

8.2 Picking the reference range

Exactly the selection Doc 02 §10 specifies, made deterministic:

  1. Candidate rows: reference_range.test_id = the result's test, and the row is effective on the sample's collection date: effective_from ≤ date(collected_at) and (effective_to IS NULL or effective_to ≥ date(collected_at)). Collection date — not entry date, not today — so a range edited later never re-flags yesterday's sample.
  2. Sex: the row's sex equals the patient's sex, or the row's sex = B (both).
  3. Age: patient age in days at collection, from patient.date_of_birth and sample.collected_at (Doc 02 v1.2). The row matches when age_min_days ≤ age_in_days and (age_max_days IS NULL or age_in_days ≤ age_max_days). Adult bands start at 6570 days (18 years), so newborn and infant bands work. Age is shown to users in years, months or days, whichever fits the age — the stored and matched unit is always days.
  4. If date_of_birth is NULL, age is unknown: a row can be selected only if it is a catch-all band (age_min_days = 0 and age_max_days IS NULL). If only age-banded rows exist, no row is selected and the flag is NULL (§8.1 step 7). The report prints "Age: not recorded" (PT-6).
  5. Tie-break: CT-4 forbids overlapping bands for the same test + sex, so at most one sex-specific row and one B row can match. The sex-specific row wins. The selection is a pure function of stored data, so the approval screen and the PDF always compute the same range (RP-3).
  6. Governance guard: the API rejects a range row whose effective_from is in the past (422 effective_from_in_past), except on the seed path. Retroactive ranges would silently re-flag history; ranges take effect today or later.

8.4 Qualitative results

  • A qualitative result always has flag = NULL. The engine does not map "Positive" to "high" or any other flag — words are not severities.
  • If the test defines an expected value set (Proposed column test.qualitative_values, amendment A-4), the entered value is matched case-insensitively after trim ("positive", "POSITIVE" and " Positive " are the same value). A value outside the set is still saved (the bench may have a real, unusual finding) but is marked needs_review and needs a pathologist note at approval.
  • If the test defines no set, the value is free text with no flag and no review mark. This is the v1 behaviour for every qualitative test until A-4 lands; the seeded Urine R/E components are the first candidates for defined sets (OQ-29, §13).
  • Semi-quantitative values ("trace", "1+", "2+", a titre like "1:160") are qualitative text in v1 (R-11). They are never parsed as numbers, even when they start with a digit — §8.1 step 3 decides kind from the range row, not from the value's shape, so a "1+" on a qualitative test cannot be misread as the number 1.

8.5 Critical values

Research is unambiguous that critical values need immediate, recorded notification with read-back (R-8). Doc 02 v1.2 carries the schema for it — amendments A-1 and A-3 accepted (§14): reference_range.critical_low / critical_high, result.flag including critical, and the append-only critical_notification table. The behaviour is:

  • At entry, a value beyond the matched row's critical bounds gets flag = critical (it replaces low/high for display; the direction is derivable from the value and bounds).
  • At approval of a critical result, results.notify_critical fires immediately (notifications queue). The report is generated in parallel — notification never waits for the PDF, and the PDF never waits for the notification.
  • A Pathologist or a Branch Manager records the notification — no other role may (§4.3, §6.6): full name of the person notified (notified_name), time (notified_at), result read back (read_back, yes/no), with the caller stored as recorded_by, into critical_notification. A critical result with no notification record after 30 minutes appears on the exceptions list (§11) until it is recorded. Read-back is required for phone notification; confirmed electronic receipt does not need it (R-8).

A critical result is not complete at approval: it is complete when the notification is recorded. Until then it stays on the exceptions list (§11).

8.6 Delta check (display only in v1)

At approval time the API returns, beside each numeric result, the patient's most recent previous approved result for the same test (any earlier sample): its value, collection date, and the change (absolute and percentage) when both values parse as numbers. Rules: no previous result → nothing shown; either value unparseable or qualitative → no delta shown; the delta never blocks approval and never changes the flag in v1. Threshold-based holds and autoverification are post-v1 (R-9, §15): thresholds must be validated on a lab's own data before they may hold a result, and v1 has no such data yet.

8.7 Pathologist override

The computed flag is data, not a verdict. A pathologist may approve against it only via range_override = true with a note (RS-7). The stored flag is not rewritten — the override lives on the result_approval row, so a reviewer can always see what the engine said and what the pathologist decided. On the PDF, an overridden result prints its computed flag plus the pathologist's comment in the comments column (§9.1). Overrides are counted as a quality metric (§11): a test whose results are overridden often has a wrong range, and the catalog should be fixed, not the results.

9. Report PDF specification

9.1 Layout and sections

One PDF per report version, A4, generated by WeasyPrint from a fixed HTML template. Sections, in order:

  1. Header: lab (tenant) name, branch name and address, lab phone. (CAP GEN.41096 lab identity, R-14.)
  2. Report meta line: report ID, version ("Version 1" / "Version 2 — Amended report"), report status (Final / Amended), finalised date-time (Asia/Karachi).
  3. Patient block: full name, MRN, age shown in years, months or days as fits the age (or "Age: not recorded", PT-6) and sex, date of birth when recorded. Two identifiers minimum (R-3, R-13).
  4. Order block: referring partner / ordering clinician name when invoice.referral_partner_id is set (walk-in otherwise), invoice number.
  5. Sample block: accession ID, collection date-time, receipt date-time (from sample_event), sample status notes — including any specimen-condition caveat recorded at receipt (R-14).
  6. Amended notice (amended versions only — §9.4).
  7. Results table: test name; result value exactly as entered, with unit; flag shown as L / H / CRITICAL beside abnormal values and blank for normal; the reference interval actually used, with its unit (§8.2); comments column carrying pathologist notes and override comments (§8.7). Panel components are grouped under the panel name.
  8. Signatory block: "Verified and authorised by" — each approving pathologist's name once, with role and their approval date-time (from result_approval). A report with results approved by two pathologists names both (R-13: the person authorising release must be identifiable).
  9. Urdu patient summary (§9.2).
  10. Footer on every page: patient name + MRN, accession ID, "Page X of Y", report ID + version, and the verification QR (§9.3). Patient identification on every page is an ISO-checklist expectation (R-13), not decoration.

9.2 Bilingual layout and Urdu rules

  • English is the primary, clinical language of the report (AS-2: no verified rule requires Urdu reports; the Urdu block is a patient-usability feature).
  • The Urdu block is a short patient summary only: lab name, patient name, accession ID, a fixed sentence that the report is ready, and the lab phone for questions. Strings come from the tenant's notification_template-style fixed texts (ur), never from free-typed clinical content.
  • Typography: Noto Nastaliq Urdu (Doc 01), the block is a single dir="rtl" container, isolated so RTL cannot leak into the English layout. Accession IDs, MRN and phone numbers inside the Urdu block stay in Latin digits, wrapped so the bidi algorithm cannot reorder them into the Urdu text.
  • No Urdu in the results table in v1: test names, values, units and ranges are English. Translating clinical terms without a verified glossary would risk patient harm, the opposite of P-1.

9.3 QR verification payload

The QR code encodes the report's patient access URL — the same /api/v1/report-access/{token} link that delivery sends (§6.8). One mechanism, not two. Scanning the printed report opens the current version's PDF. Consequences, chosen deliberately: the paper already contains the full results, so the QR grants no new exposure; and if the token is revoked (RP-5, RP-8), the printed QR stops working and returns the 410 page — a voided report's QR must not keep serving the PDF. The token printed is the token current at generation time; an amended version's PDF carries the then-current token.

9.4 Versioning and the amended-report notice

  • Every version is a separate immutable PDF at reports/{report_id}/{version}.pdf (RP-2). A reprint is the stored bytes, never a re-render (P-8) — a reprint of version 1 after version 2 exists still shows version 1, labelled as such.
  • An amended version's notice box (before the results table) states: "Amended report — this version corrects version N." Then one line per changed test: test name, previous value with unit, corrected value with unit, amendment date, approving pathologist. Then a compact version history: every version with its status and finalised time, in order (R-12: original and corrected data identifiable, corrections referenced in sequence).
  • The changed rows in the results table are marked with a dagger (†) pointing at the notice, so a reader who skips the box still sees which values moved.

9.5 WeasyPrint constraints

  • The template uses only what WeasyPrint renders deterministically: block layout and tables for structure, @page rules with margin boxes for the running footer, CSS counters for "Page X of Y". No JavaScript, no web fonts loaded at render time (fonts are installed with the app), no external images — the logo and QR are local assets, the QR generated server-side as a PNG.
  • The results table header row repeats on every page (thead), and a result row never splits across pages (break-inside: avoid).
  • Generation runs in the reports queue with the Doc 01 §13 retry policy and a task time limit sized to G1 (p95 ≤ 60 s). A render exception fails the task cleanly — no partial PDF object is kept (§10).

9.6 Page limits

Design target: a single-panel report fits 1 page; the full starter catalogue on one sample fits ≤ 3 pages. This is a layout budget verified by fixture tests (§12, T-38), not a runtime rule — a legitimately long report renders as many pages as it needs, with footer and repeated headers keeping every page identifiable.

11.2 TAT calculation

  • Definition (v1, stated wherever TAT is shown): sample TAT = report.finalised_at − sample.collected_at for samples that reached a final report. Research shows labs and physicians define TAT differently (R-15), so LabFlow prints its definition next to every TAT figure instead of pretending there is one true number.
  • Stage durations (from sample_event timestamps): collection → receipt (transport and bench wait), receipt → in-process, in-process → ready (analysis plus verification wait), ready → finalised (PDF wait; the G1 window). The stage split exists because the fix for a slow stage depends on which stage is slow — pre-analytical delay is the largest contributor in the literature (R-15), and LabFlow's own data should confirm or refute that per tenant.
  • Aggregates: median and p90 per branch per week, and per sample overall. Per-test TAT targets and breach alerts need a target to breach against — that is Proposed amendment A-5 (test.tat_target_minutes, matching the MSDS expectation of a documented minimum reporting time per test, R-17). Until A-5 lands, LabFlow shows durations and ageing, and claims no breaches.
  • Exclusions, stated on the report: rejected and cancelled samples are excluded from TAT and counted separately. A recollected sample's TAT runs from the replacement sample's collection; the patient's full journey (first collection → final report, including the rejection delay) is reported as a second figure, so recollection cannot be used to launder a slow lab.
  • Samples still in flight are not in TAT at all — they appear as ageing work-in-progress, oldest first, which is the operationally honest view.

16. Interview talking points

The ten decisions in this document worth being able to defend out loud. Each states the decision, the defence, and the alternative that was rejected.

  1. Result values are stored as text, with strict parse rules (§8.1). Real benches produce "< 0.1", "2+" and "Positive"; a numeric column would reject true results or teach staff to falsify entries. So the value is stored verbatim and the flag is computed by explicit rules, with NULL — never a guess — when parsing fails. Rejected: a numeric value column with separate text column (two sources of truth), and free-text-with-no-parsing (no flags at all).
  2. Two-person verification, with an honest single-pathologist exception (RS-5, RS-6). Entry and approval are different endpoints and different roles, matching OpenELIS and SENAITE practice, because the second pair of eyes is the cheapest error-catcher in the system. But the target customer may employ exactly one pathologist, so the exception exists — recorded in the approval row and audit, not smuggled in. Rejected: hard two-person rule (unusable for the smallest labs) and silent self-approval (destroys the audit story).
  3. Nothing clinical or financial is ever edited in place (P-2). Corrections are new rows; the old row moves to amended or stays as the compensated payment. That is what makes "what did the report say on Tuesday?" answerable, and it is how CAP expects corrected reports to work. Rejected: in-place edits with an audit log of changes — the audit says a value changed, but no artefact can reproduce the old report.
  4. Idempotency is enforced by database unique indexes, not by careful code (BL-4, §10). A double-clicked payment is a when, not an if. Storing the key on the invoice/payment row under a UNIQUE partial index means even racing requests cannot both succeed — the guarantee survives framework bugs. Rejected: client-side button disabling (theatrical) and a Redis dedupe cache (a second system that can be flushed).
  5. Invoice status is derived from payment rows, never set (BL-6). Status is a pure function of the append-only money rows, recomputed in the same transaction as each insert, so the status can never disagree with the money. Refunds and partial refunds follow from that formula. The zero-total invoice does not: it is a deliberate exception to BL-6, created directly in paid status because there is nothing to collect (§5.3). Rejected: status set by endpoint handlers (five code paths, five chances to drift).
  6. Prices and ranges are snapshotted into anything charged or printed (P-8, CT-2, RP-3). A price change next month must not alter last month's invoice, and a range change must not re-flag a reported result. Snapshots cost a few columns and buy total historical stability. Rejected: joining live catalog data at read time — the classic bug where old reports silently change.
  7. Reports are versioned PDFs; the patient link always serves the current version (RP-2, RP-4). Amending a result mints a new immutable PDF with a notice showing old and new values, and old links upgrade automatically — a patient must never keep acting on a corrected result. Rejected: regenerating the same PDF in place (destroys the original) and pinning links to a version (strands the patient on wrong data).
  8. Patient access is a two-layer token design (RP-8). A 7-day token that is stored only as an argon2 hash opens the door; a 15-minute pre-signed URL serves the file. Each layer's lifetime matches its exposure: links get forwarded and screenshotted, storage URLs should not outlive the tap. Rejected: a long-lived direct file URL (unrevocable) and patient accounts with passwords (fails the two-click goal and the support desk).
  9. Branch scope lives in the query layer, with one deliberate exception (BS-1 to BS-6). Every query for a branch-scoped role is filtered by staff_branch on the server, and out-of-scope objects answer 404, so the API cannot leak existence. The single exception — identifiers-only cross-branch patient search — exists to stop duplicate registrations, a safety feature, and its narrowness is the point. Rejected: UI-level hiding (not access control) and tenant-wide patient visibility (convenient, and a privacy incident waiting for a date).
  10. Rejection is a coded, terminal, auditable state — never a delete (SM-8, SM-9). WHO practice and the MSDS both treat rejection as a recorded event with a reason and a recollection path. Coding the reason turns a daily frustration into a quality metric that can show a branch its haemolysis rate. Rejected: deleting rejected samples (destroys the custody chain) and free-text reasons (unmeasurable).
