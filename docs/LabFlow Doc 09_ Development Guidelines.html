How LabFlow is written, reviewed, tested and shipped: repository layout, coding standards for the Django backend and the React frontend, migration discipline, the testing strategy that hosts every earlier doc's test plan, version control, the CI pipeline, dependency rules, n8n workflow development, and documentation discipline.
Audience: the developer building LabFlow v1. What the system does comes from Docs 01–08 — none of it is re-decided here. Doc 02 remains the only source of truth for tables, columns and status values.

How this document treats earlier docs. Docs 01–08 are ground truth. This document fixes how the code that implements them is produced: the standards, the checks, and the pipeline that keep the code equal to the documents. It answers the one question earlier docs left to it — OQ-49, Playwright test-ID naming and UI copy ownership, resolved in §10. Anything a guideline needs that contradicts an earlier doc would be a Proposed amendment in §20, never a silent override; §20 in fact proposes none, and §1.4 records why. Where an earlier doc already set a rule (money as server strings, no patient data in browser storage, audit on every non-GET), this document turns it into a checkable coding standard and a CI gate — it does not restate the decision as its own.

1. Purpose, scope, inputs, consistency check

1.1 Purpose

Docs 01–08 say what LabFlow is: the architecture, the schema, the module behaviour, the tenancy rules, the money rules, the automation protocol, the frontend, and the security layer. None of them says how the code is to be written and kept honest over time. That gap is where real projects drift: a service function that skips the audit row, a migration edited after it shipped, a UI string hard-coded in English only, a test suite nobody trusts. This document closes the gap. It fixes the repository shape, the coding standards for both codebases, the migration discipline that protects Doc 02's schema, the testing strategy that gives the six existing test plans (T, TN, RS, AU, FE, SE) one home, and the pipeline that runs all of it on every change.

1.5 Assumptions

  • AS-1. The developer is one person — the same solo developer and platform operator Docs 01–08 assume. Every process rule here (review, CI, release) is written to work for a team of one today and a small team later, without a rewrite. Where a rule normally needs a second person (code review), §11.4 states the solo form honestly.
  • AS-2. Code lives in one Git repository (a monorepo) hosted on GitHub, following the GitHub connection already in use for this project. CI is GitHub Actions. If the host changes, §11 and §12 port directly — the rules are host-shaped, not host-owned. The hosting-cost question is Doc 10's (OQ-54, §19.2).
  • AS-3. Local development runs the same Docker Compose stack as production (Doc 01 §15), with test tenants and synthetic data only. No developer machine ever holds a copy of a real tenant schema (§16.3).
  • AS-4. Tool versions named in §5, §6 and §12 (Ruff, mypy, ESLint, Prettier, pytest, Vitest, Playwright) are the current stable releases at build time; §13's update cadence, not this document, keeps them current.

2. Research findings

Eight findings, each from a real source checked on 2026-10-20. Anything that could not be sourced is marked Unverified where it is used.

#FindingSourceWhere used
F-1Conventional Commits 1.0.0 is a lightweight convention on top of commit messages: <type>[optional scope]: <description>, where feat correlates with a SemVer MINOR and fix with a PATCH, and a BREAKING CHANGE footer (or !) with a MAJOR. Because the format is machine-readable, changelogs and version bumps can be derived from history instead of reconstructed from memory.Conventional Commits 1.0.0§11.2, §15.2
F-2The Twelve-Factor App methodology: one codebase tracked in version control with many deploys; dependencies explicitly declared and isolated; config stored in the environment; strict separation of build, release and run; dev/prod parity; logs as event streams; admin processes run as one-off processes in the same environment. Doc 01's architecture already follows most of it; this document codes the rest as rules.Twelve-Factor App methodology (summary of the twelve factors)§3 GP-2, §4.4, §16
F-3PEP 8 is Python's style guide: 4-space indentation, snake_case for functions and variables, CapWords for classes, ALL_CAPS for constants, two blank lines around top-level definitions, imports grouped and ordered. Its own framing is the one §5 adopts: consistency within a project matters more than any single rule, and a style guide is about making code readable for the next reader.PEP 8 — Style Guide for Python Code (full text)§5.1
F-4Ruff is a single fast tool that replaces Flake8 (plus dozens of plugins), Black, isort, pydocstyle and pyupgrade: ruff check lints with 900+ rules mirroring the Flake8 rule-code system, and ruff format formats with near-identical output to Black (>99.9% of lines on codebases like Django itself). One tool in pyproject.toml means one config file and one CI step for all Python style enforcement.Ruff documentation (Astral)§5.1, §12
F-5Trunk-based development: all work lands on one shared trunk (main); feature branches, when used at all, live hours to at most a couple of days; CI runs on every integration; the trunk is always in a releasable state; incomplete work is hidden in the product (here: behind tenant settings and role checks that already exist), not parked on long-lived branches. It minimises merge divergence — the main cost centre of branching for a small team.Trunk-based development: process, examples, strategy (Unleash)§11.1
F-6Semantic Versioning 2.0.0: a version is MAJOR.MINOR.PATCH; MAJOR for incompatible API changes, MINOR for backwards-compatible functionality, PATCH for backwards-compatible fixes; once released, a version's contents never change — any modification is a new version. For LabFlow the "public API" the version speaks about is the deployed platform release: what tenants' staff and the n8n callbacks depend on.Semantic Versioning 2.0.0 (semver.org)§11.5, §15.2
F-7Keep a Changelog: a changelog is for humans, not machines — a curated, versioned list of notable changes (Added, Changed, Deprecated, Removed, Fixed, Security), latest first, with an Unreleased section maintained continuously. A git log cannot substitute: commits document atomic steps of how the code evolved; a changelog documents the noteworthy differences between releases, and why.Keep a Changelog (keepachangelog.com)§15.2

3. Guiding principles

#PrincipleWhat it means here
GP-1The documents are the specification; the code is the implementation.If code and a doc disagree, one of them is wrong and the PR must say which. Behaviour changes land as a doc amendment first or in the same PR (§15.3) — never as code that quietly re-decides a module.
GP-2One codebase, many deploys.Twelve-factor factor I (F-2). One monorepo builds every deploy: local, CI, the VPS. There is no "production branch" and no code that exists only on the server.
GP-3Automate every rule that can be automated.A rule a machine can check (format, lint, types, migration-vs-Doc 02 drift, hard-coded UI strings, secrets) is a CI gate, not a review comment. Human review is spent on behaviour, not on commas (§12).
GP-4Small changes, merged fast.Trunk-based development (F-5): branches live at most two days, PRs stay reviewable in one sitting, main is always deployable. A change too big to review is split, not waved through.
GP-5Tests are part of the change, not a phase after it.Every behaviour in Docs 03–08 has a scenario ID; the PR that implements it names the IDs it covers. A bug fix lands with the regression test that would have caught it (§9.5).
GP-6Synthetic data only, everywhere outside production.Fixtures, seeds, screenshots and CI databases use invented patients with obviously fake identifiers. Real patient data never enters a dev, test or CI environment (Doc 08 §11's scrubbing rule applied to data, not just errors).
GP-7Boring tooling, pinned versions.Mainstream tools, committed lockfiles, no unpinned installs. Exotic tooling is a cost the solo operator pays forever; §13's cadence keeps the boring tools current instead.
GP-8Leave the codebase tidier than you found it — inside the change's scope.Fix the lint warning you touch; do not refactor the neighbouring module in the same PR. Opportunistic cleanup rides its own commit, so review and rollback stay clean.

4. Repository layout and environments

4.1 One repository

LabFlow is one Git repository. The backend, the frontend, the n8n workflow exports, the Compose files and these documents' sources live together, because every meaningful change crosses at least two of them (an endpoint and its screen; a schema migration and its Doc 02 update) and GP-2 wants those changes atomic and reviewable as one PR.

App boundaries mirror module boundaries. A Django app maps to one doc module. Code reaches across apps only through the owning app's service layer (§5.2), never by importing another app's models into a view. This is what keeps a change to settlements (Doc 05) from silently becoming a change to billing (Doc 03).

4.2 What never enters the repository

  • No secrets. No .env with real values, no keys, no tokens — a committed example file (.env.example) lists names only, matching Doc 08 §6's inventory. CI scans for secrets on every PR (§12.2).
  • No real data. No production dump, no real patient row, no screenshot of a real tenant — in code, fixtures, docs or screenshots (GP-6).
  • No generated output. No built frontend bundles, no __pycache__, no exported PDFs, no n8n exports containing credentials (§14.2).

4.4 Configuration and parity

Config comes from environment variables only (twelve-factor factor III, F-2), using exactly Doc 08 §6's inventory — code reads no config file that is not in the repo, and no setting has a hard-coded production default for a secret. The same container images run locally, in CI and in production; the Compose file differs per environment only in env values and published ports. Python and Node versions are pinned in the repo (.python-version, .nvmrc, and the Dockerfiles) so "works on my machine" is a version mismatch, not a mystery.

5. Backend standards (Django / DRF)

5.1 Style, lint, types

  • PEP 8 (F-3) as enforced by Ruff (F-4). One pyproject.toml holds the Ruff configuration: ruff format (line length 88, double quotes) and ruff check with the rule families E, F, I, UP, B, SIM, DJ (pycodestyle, pyflakes, import order, pyupgrade, bugbear, simplify, Django). A rule is disabled per-line with a reason comment, or per-project in the config with a comment — never by lowering the gate for a whole file silently.
  • Type annotations are required on service functions and Celery tasks (parameters and return), and on view code where DRF does not already fix the shape. mypy runs in CI (§12) over apps/; models may rely on Django's typing without stubs gymnastics, but a service signature like def record_payment(invoice, amount: Decimal, ...) -> Payment is the norm, not the exception.
  • Naming. Modules and functions snake_case, classes CapWords, constants ALL_CAPS (F-3). Names use Doc 02's vocabulary: a function that records a share entry is partners.services.record_share_entry() — the exact callable Doc 05 names — not a synonym invented in code.

5.2 Where logic lives: the service layer

The point of the split is testability and reuse: Doc 05's ledger entry is created synchronously inside the payment transaction by partners.services.record_share_entry(), and the hourly reconciliation sweep calls the same function from Celery. If the logic lived in the view, the sweep would need a second copy — and the two copies would drift.

5.3 State, status values, and Doc 02's vocabulary

Status values are Python TextChoices classes generated from Doc 02's definitions, one per status column, living with the model. Code never compares against a raw string literal (status == "collected" is a review defect; status == Sample.Status.COLLECTED is the standard). Ruff's rule set does not catch string literals, so this is one of the few style rules enforced by review (§11.4) — it exists because a typo'd status string fails silently in Python and loudly nowhere.

5.4 Money and numbers

  • Money is Decimal end to end (Doc 02 column types). A float touching a money value is a defect, in code or in a test.
  • result.value stays text, per OQ-25 as resolved in Doc 03 §8: parse to Decimal only for numeric range checks, and never guess a flag when parsing fails — the flag stays NULL.
  • Rounding happens only where Doc 05 specifies it (share calculation). No other rounding is introduced by code; if a screen needs a formatted amount, the API sends the string (§6.3).

5.5 The audit rule, as code

Doc 08 §9 fixes the audit write contract: every non-GET writes one audit_log row in the same transaction, and an audit failure rolls the write back. The coding standard that makes this structural rather than remembered: a service function that mutates state takes the actor and writes its audit row before returning, inside the caller's transaction.atomic(). Views never write audit rows directly. The DG test suite (§18) includes a contract test that walks every registered non-GET route and asserts an audit row exists after a successful call — a new endpoint that forgets its audit row fails CI, not a code review months later.

5.6 Celery tasks

  • Idempotent or not shipped. Every task carries or derives an idempotency key, following Doc 05's pattern (share-ledger:{payment_id}); a task that runs twice must produce the same end state as a task that runs once. Doc 06's 15-minute Beat sweep and retry rules assume this.
  • Thin tasks. A task parses its arguments, loads the tenant context (schema switch per Doc 04), and calls a service function. No business logic in the task body.
  • No patient payloads in task arguments beyond identifiers. Tasks pass IDs, never names, phone numbers or result values — Redis is not a patient-data store (Doc 01 §15, Doc 08 AS-3), and task arguments sit in Redis.
  • Failures are loud. A task that exhausts retries raises; the Sentry scrubber (Doc 08 §11) governs what the error report may contain.

5.7 Errors and logging

API errors use the error envelope and codes the module docs define (invalid_state_transition, rule_overlap, owner_approval_required, and the rest); §8.2 governs how new codes are added. Code raises the module's typed exceptions; one exception handler renders them — views do not hand-build error responses. Logging is structured JSON with request_id (Doc 01 §11); log lines carry identifiers, never patient values, for the same reason Sentry events do not (Doc 08 SP-6).

5.8 PDF generation (WeasyPrint)

Report, statement and label PDFs render from the templates in backend/templates/pdf/ (Doc 03 owns the report, Doc 05 the statement, Doc 07 §11 the 100×50 mm label). Templates receive a prepared context dict from a service function — no queries in templates. A template change ships with a golden-file test: the rendered PDF for the synthetic fixture patient is compared page-for-page in CI, so a CSS change that breaks a lab's report layout fails a test, not a tenant.

6. Frontend standards (React / TypeScript)

6.1 Style, lint, types

  • TypeScript in strict mode, with noUncheckedIndexedAccess on. any requires a comment saying why; @ts-ignore is banned — @ts-expect-error with a reason is the only suppression, and it fails the build when the error disappears.
  • ESLint + Prettier, configured in the repo, run in CI (§12). Formatting is Prettier's decision alone — no PR discussion about quotes or semicolons (GP-3).
  • API types come from the API. Response types are generated from the backend's OpenAPI schema (§8.3) into src/api/types.ts and committed; a backend shape change that is not regenerated fails CI. Hand-written duplicate types for API payloads are a review defect — they are how the SPA and the API silently disagree.

6.2 Components and state

  • Server state lives in TanStack Query with Doc 07 R3's settings (staleTime 30s default, 15s queues, 5 min catalog, gcTime 5 min, mutation retry 0). Component-local state is useState; there is no second global store in v1.
  • Screens sit behind Doc 07 D-1's route-level ScreenBoundary; a new screen that is not wrapped is incomplete by definition.
  • Forms use the validation shape Doc 07 specifies; server validation errors render from the API's error codes (§8.2), mapped to i18n strings (§10.3) — never from raw server message text.

6.3 Money, dates, and patient data

  • Money is displayed as the server string, verbatim (Doc 07 R2). The SPA does no money arithmetic, holds no Decimal library, and never reformats an amount. A total the screen needs is a field the API adds — requested via the module doc, not computed in the browser.
  • Patient data is never written to browser storage (Doc 07 R3): no patient names, results or identifiers in localStorage, sessionStorage or IndexedDB. The access token lives in memory only (Doc 08 §4.1). A PR that adds a storage write is reviewed against this rule first.
  • Dates and times render in the tenant's timezone from server-supplied ISO values; the SPA never invents a timezone conversion the API did not imply.

6.4 The component library boundary

Doc 07 D-3 fixed the shadcn/ui list at 19 components. Code uses those 19. Needing a 20th is legitimate — but it is a Doc 07 change: the PR names the component, amends Doc 07's list (or files the amendment per §20's convention), and only then adds it. What this rule prevents is the slow drift where five PRs each add "just one small component" and the design system stops existing.

6.5 Strings and languages

Every user-visible string is an i18n key with both an English and an Urdu value, added in the same PR as the UI that uses it (§10.3 owns the naming and ownership). Hard-coded JSX text is a CI failure (§12.2), not a style preference: a hard-coded string is an Urdu screen that silently shows English. Urdu renders RTL where Doc 07 requires it; tests cover one RTL screen in the FE suite so a layout that breaks under RTL fails before a user sees it.

7. Database and migration discipline

7.1 The one rule

A migration implements Doc 02; it never invents schema. If the schema a change needs is not in Doc 02 v1.3 (as amended), the work splits: first the Doc 02 amendment (reviewed, versioned, per the series' convention), then the migration. A PR whose migration adds a column Doc 02 does not name is not merged, however small the column. This is the enforcement half of "Doc 02 is the only source of truth" — the other half is §7.5's drift check.

7.2 Shared schema vs tenant schemas

django-tenants splits migrations exactly as Doc 04 fixes: SHARED_APPS migrations run once on the public schema (platform tables, Doc 02 §4); TENANT_APPS migrations run on every tenant schema. A model placed in the wrong list is a critical defect: it either leaks a tenant table into the public schema or denies tenants a table they need. New apps declare their side in the same PR that creates them, and the DG suite (§18) asserts every Doc 02 table is reachable in exactly the schemas Doc 04 assigns it to.

7.3 Writing migrations

  • Generated, then read. makemigrations output is reviewed line by line in the PR — auto-generated does not mean auto-correct, especially renames, which Django guesses as drop-and-add. A rename is written as a rename.
  • Named for the change: 0042_sample_transfer_cancelled_status.py, not 0042_auto_20261020.py. The name states the Doc 02 section it implements.
  • Data migrations are separate from schema migrations, use RunPython with historical models, and are idempotent — a data migration runs against every existing tenant schema at deploy and against every future tenant at provisioning (Doc 04 §4), so it must be safe to run on a schema that already has the end state.
  • Never edit a merged migration. Once a migration is on main, it is history. Fixing it means a new migration. Editing it breaks every schema that already applied it — which, per-tenant, means some tenants migrate and some do not, the exact failure Doc 04's per-schema pg_dump discipline exists to recover from slowly.
  • Backwards-compatible within a deploy. The deploy order on the VPS is: new code and migrations roll together, but a rolling restart means old and new code briefly share the database. Additive changes (new nullable column, new table) are always safe; destructive changes (drop, rename, NOT NULL on existing data) split into two releases — add-and-backfill first, enforce-or-drop in the next (expand/contract). A one-release destructive migration needs the reason written in the PR.

7.4 Seeds

Seed data follows Doc 02 §16 as amended (including the v1.3 rule: no tenant-level 0% revenue_share_rule row — 0% comes from rule resolution, and the owner creates the first real rule per partner). Platform seeds (notification templates per Docs 02 §5.9 / 06, tenant_setting defaults) live in data migrations or fixtures owned by the module doc that defines them. Demo seed for local development is a separate, clearly-named command (§16.3) that only ever runs against the local demo tenant.

7.5 The drift check

CI runs makemigrations --check --dry-run on every PR: if the models and the committed migrations disagree, the build fails. A second CI step applies all migrations to a fresh database, creates one tenant schema, and runs the Doc 02 conformance assertions from the DG suite (table presence per §7.2, the REVOKE grants of Doc 02 §6, the seed invariants of §7.4). Schema drift between code, migrations and Doc 02 is therefore caught in minutes, on the PR that caused it.

8. API development conventions

This section governs how endpoints are built. What the endpoints are — routes, shapes, error codes — belongs to Docs 03–06 and Doc 08 §4, and is not restated or extended here.

8.1 Building an endpoint, in order

  1. Find the contract in the owning module doc. If it is not there, stop: the endpoint is an amendment (§20), not a coding task.
  2. Serializer first, with the exact field names the doc fixes. Money fields serialise to strings (§5.4, §6.3).
  3. Permission class and branch scoping per the module doc's matrix; the SPA hiding a button is courtesy, every check is server-side (Doc 08 §5, Doc 07 FP-6).
  4. One service call per write (§5.2), which brings the audit row (§5.5) and idempotency (§5.6) with it.
  5. Tests named for the scenario IDs the endpoint serves (§9.2), plus the audit contract test (§5.5) passing.

8.2 Error codes

Error codes are a registry, not a habit. Every code the API returns is defined in the owning module doc (invalid_state_transition in Doc 03, rule_overlap in Doc 05, subscription_read_only in Doc 04, refresh_reuse_detected in Doc 08). Adding a code means adding it to the doc in the same PR. Codes are snake_case, stable once shipped (the SPA maps them to i18n strings, §6.2), and never renamed to sound nicer — a rename is a breaking change for every client that branches on it.

8.3 The OpenAPI schema

The backend publishes its OpenAPI schema from the running serializers (drf-spectacular), and §6.1's generated frontend types derive from it. The schema is a build artifact of the code, checked in CI for drift against the committed copy. It is documentation of what shipped — it does not override the module docs, and where the two disagree the module doc wins and the code is fixed.

8.4 Pagination, filtering, ordering

List endpoints follow the shape the module docs already use: cursor or page pagination as the owning doc specifies, explicit ordering (never database-default order — tenant schemas grow at different rates and "usually insertion order" is not an ordering), and filter parameters named after the fields they filter. A list endpoint without a stated ordering is a review defect, because its tests will pass on a small fixture and its behaviour will wander on a real tenant.

Traceability rule. A scenario is "covered" when a test with its ID in the name exists and runs in CI. The coverage report §9.3 publishes is by scenario ID, not only by line: a release that cannot show T, TN, RS, AU, FE and SE all green does not ship (§11.5).

9.3 Coverage gates

  • Scenario coverage is the hard gate: 100% of the scenario IDs in Docs 03–08 must map to a running test before v1 launch; after launch, a new scenario lands with its test in the same PR (GP-5).
  • Line coverage is a ratchet, not a target: CI fails if backend or frontend line coverage drops below the previous merge to main. No absolute percentage is fixed in v1 — a number chosen today would be gamed tomorrow; a ratchet only moves one way. (The absolute-floor question was considered and rejected, §20.)
  • Money and state machines are exempt from the ratchet's mercy: billing, partners services and every state transition function require branch coverage of every transition the owning doc's state machine names, asserted by tests named for them.

9.4 Test data

Factories (factory_boy on the backend, fixture builders on the frontend) generate synthetic tenants, staff, patients, samples and invoices. Names are obviously fake (Test Patient 001), phone numbers use reserved fake ranges, and no factory default resembles a real person. The two-schema tenancy fixture (one platform, two tenants, interleaved IDs) is shared test infrastructure — the TN suite and every isolation-sensitive test build on it rather than re-inventing it. Test data never leaves CI: no production data is copied down for debugging (GP-6); a production bug is reproduced from its audit rows and correlated hashes (Doc 08 §9), not from its patient rows.

9.5 Flaky tests and bug fixes

  • A flaky test is a bug with an owner. It is quarantined (marked, ticketed, excluded from the gate) within one working day of being identified as flaky — never retried-until-green in CI config, which trains everyone to ignore red builds.
  • Quarantined tests are counted; the count is in the CI summary. A quarantine older than two weeks blocks non-urgent merges until it is fixed or the test is deleted with a reason. (§18 DG-19 tests this rule's reporting.)
  • Every bug fix lands with its regression test first or in the same commit. "Fixed without a test" is an incomplete fix by definition (§17.3).

10. Test IDs and UI copy (OQ-49)

Doc 07 left two frontend conventions unassigned: how Playwright test IDs are named, and who owns UI copy. Both are development-process questions, so this document resolves them (§19.1 records OQ-49 as resolved here).

10.1 Locator priority

Following F-8, FE tests locate elements in this order:

  1. Role + accessible name (getByRole, getByLabel) — tests what the user perceives, and fails when the accessibility tree breaks, which Doc 07's WCAG AA baseline (D-2) wants caught.
  2. data-testid (getByTestId) — where role/name cannot identify the element stably: repeated rows, icon-only controls, dynamic regions (toasts, badges, tables).
  3. Text (getByText) — only for asserting that specific copy is shown, never as a handle to click through.

CSS classes, generated class names and positional XPath are banned in the FE suite. A selector that breaks when a designer changes a class was never testing behaviour.

10.2 The test-ID grammar

data-testid = <screen>-<region>-<element>[-<qualifier>]

screen     the Doc 07 route/screen name, kebab-case:  login, sample-detail,
           result-entry, settlements, report-view
region     the area of the screen:  form, queue, table, banner, modal, toast
element    what it is, by purpose not appearance:  submit, patient-name,
           approve, balance-due, status-badge
qualifier  only when the same element repeats:  the row's stable key
           (e.g. accession suffix), never a row index

Examples: login-form-submit, sample-detail-banner-status, result-entry-table-flag, settlements-queue-approve, report-view-toast-success. Rules: kebab-case only; purpose, never appearance (red-button is a defect, reject-button is an ID); unique within a screen; stable across languages — the same ID in English and Urdu renders, which is why IDs are never derived from visible text; an ID, once an FE test uses it, changes only with the test in the same PR. A test ID is not a styling hook and carries no CSS.

10.3 UI copy ownership

  • Copy lives in the i18n resource files (frontend/src/i18n/en.json, ur.json), keyed screen.element.state (settlements.approve.confirm_title). Components reference keys; they never contain the words (enforced in §12.2).
  • The developer owns copy in v1 — the same solo developer who owns the docs. Every key is added with both languages in the same PR; an English-only key fails CI. Urdu wording follows the register the module docs use for patient-facing text; patient-facing messages additionally obey Doc 04 A-16 (the tenant's report_default_language decides which language a delivered message uses — that is runtime behaviour, separate from the copy existing in both).
  • Copy changes are normal PRs, reviewed like code, because a changed label can break an FE test's accessible-name locator — that failure is a feature: it forces the copy change and the test update into one reviewed change.
  • Error-code copy is special: the strings for API error codes (§8.2) live under errors.* keys and change only when the owning module doc's code list changes.

11. Version control: branches, commits, pull requests

11.1 Branching model: trunk-based

Per F-5: one long-lived branch, main, always deployable and always releasable. Work happens on short-lived branches named <type>/<short-scope> — feat/settlement-mark-paid, fix/transfer-receive-409, docs/doc-09-guidelines — using the same type vocabulary as commits (§11.2). A branch lives at most two working days; work that cannot land in two days is split into landable pieces (a migration, then the endpoint, then the screen), each green on its own. There are no develop, staging or release branches in v1 — releases are tags on main (§11.5), matching the single-VPS deploy (Doc 01 §15). Incomplete features merge behind the mechanisms the product already has (role checks, tenant settings) or do not merge.

11.2 Commit messages: Conventional Commits

<type>(<scope>): <description>

types   feat | fix | refactor | test | docs | chore | ci | perf | revert
scope   the owning module: core, patients, samples, results, billing,
        reports, partners, tenancy, platform, automation, frontend,
        infra, docs
rules   imperative mood, no trailing full stop, first line ≤ 72 chars;
        body states WHY when the why is not obvious from the diff;
        a breaking change carries a BREAKING CHANGE: footer (F-1)

Examples: feat(partners): add POST /settlements/{id}/mark-paid · fix(samples): reject receive for a lost transfer with 409 · test(security): SE-28b privileged-write marker behaviour. The scope vocabulary mirrors the doc modules on purpose: git log --grep by scope is how the §15.2 changelog gets assembled, and how a reader finds when a module's behaviour changed.

11.3 Pull requests

  • One concern per PR. A PR that changes a migration, an endpoint and a settings screen for three different reasons is three PRs. Size guide: reviewable in one sitting — roughly 400 changed lines; bigger needs the split explained up front.
  • The PR description is a form: what changed and why; the doc sections it implements (e.g. "Doc 05 §10, RS-31"); the scenario IDs covered; migration notes (§7) or "no migration"; screenshots for UI changes — of synthetic data only (GP-6).
  • Squash-merge to main, with the squash commit following §11.2 (the PR title is the commit line, so PR titles follow it too). Branch deleted on merge. No merge commits, no direct pushes to main — branch protection enforces both, plus green CI (§12).
  • Docs ride along. If the PR changes behaviour a doc describes, the doc edit is in the same PR (§15.3). A PR that makes a doc false is not mergeable, even if the code is right.

11.4 Review

Review checks, in order: (1) does the code do what the cited doc section says — nothing more, nothing else; (2) the structural rules machines cannot check (§5.3 status strings, §5.2 layer boundaries, §6.3 storage writes, §7.3 migration content); (3) tests named for the scenarios claimed; (4) the §17.3 definition of done. Solo form (AS-1): while there is one developer, review is a self-review pass against this list, done after a break from writing the code, with the checklist pasted into the PR. That is weaker than a second pair of eyes and this document says so plainly — the compensating controls are the CI gates (§12) and the scenario suites (§9), which do not get tired. The moment a second developer joins, every PR needs their approval; nothing else in this section changes.

11.5 Releases and versioning

Production releases are SemVer tags on main (F-6): v1.4.2. MAJOR for a release that breaks the API contract or a callback integrators depend on, MINOR for new backwards-compatible capability, PATCH for fixes. A release is: tag → CI builds the images from that tag (§12.3) → deploy to the VPS (Doc 01 §15's Compose) → changelog section (§15.2) cut from Unreleased. There is no long-lived release branch to patch; a hotfix is a normal PR to main, a new PATCH tag, and — only if an older release must be patched in place, which v1's single deployment makes rare — a short-lived hotfix/… branch from the tag, deleted when the fix reaches main.

12.3 Merge and release pipelines

On merge to main: the full PR pipeline re-runs, the full Playwright suite runs, and images are built and tagged with the commit SHA. On a version tag (§11.5): images are rebuilt from the tag, pushed to the registry, and the deploy step updates the VPS Compose stack and runs tenant migrations across schemas (Doc 04 §14's mechanics). A failed migration on any tenant schema stops the deploy and pages the operator — partial migration across tenants is the one deploy state v1 refuses to continue from (§17.2).

12.4 Pipeline hygiene

  • CI configuration lives in the repo (.github/workflows/) and is reviewed like code — a PR that weakens a gate is a §20-visible change, discussed as one.
  • CI never holds production secrets. It uses its own throwaway keys (a CI-only Fernet key, CI-only JWT key); the secrets scan (§12.2) covers workflow files too.
  • Target wall-clock for the PR pipeline is under 15 minutes. A pipeline that is slow gets split or cached — a slow gate is a gate developers route around, and a routed-around gate is worse than none because it looks like protection.

13. Dependencies and supply chain

13.1 Pinning

  • Python dependencies are pinned to exact versions in a committed lockfile (requirements.txt generated from pyproject.toml); Node dependencies are pinned by package-lock.json, committed. Dockerfiles name base images by tag and digest. Nothing in any build resolves "latest".
  • Adding a dependency is a decision with a paragraph in the PR: what it does, why the standard library / existing stack cannot, its maintenance state, its licence. A dependency that duplicates an existing one is removed, not layered.
  • The major framework versions are Doc 01's (Django 5, React 18) — upgrading a major framework version is a planned project with its own PR series, never a drive-by in a feature branch.

13.2 Update cadence

13.3 Vulnerability handling

The dependency scan in CI (§12.2) fails the build on a new critical or high CVE in a pinned dependency. A CVE that appears in already-merged code opens a fix(deps) PR the same day it is triaged; if the vulnerable code path is reachable with patient data, the fix follows Doc 08 §14's incident order (contain, notify, document, review) rather than the routine cadence. Transitive dependencies count: the scan reads the full lockfile, not only direct dependencies.

14. n8n workflow development

Doc 06 owns what the workflows do and the protocol they speak. This section owns how they are changed safely.

14.1 Workflows are code

Each of Doc 06's workflows (the WF-* set — WF-EMAIL-SETTLEMENT among them) is exported as JSON into workflows/, one file per workflow, named for its Doc 06 ID. The export in the repo is the source of truth: production n8n imports from it, and a change made only in the n8n UI is drift that the next import silently reverts — so UI edits are working copies, never the change itself. Workflow changes go through PRs like code, with the AU scenario IDs they affect (§9.2).

14.2 Credentials never travel

Exports are scrubbed before commit: credential objects are replaced by name references (the credential name in n8n, never its value), and webhook secrets (N8N_WEBHOOK_SECRET, N8N_CALLBACK_KEY — Doc 08 §6) exist only in the n8n instance's environment. The CI secrets scan (§12.2) runs over workflows/ with the same rules as code. A workflow may call only the surfaces Doc 06 allows: Django's signed webhook/callback endpoints and the tenant's mail/WhatsApp providers — a workflow node that reaches for the database directly violates Doc 06's network rule and is a critical review defect.

14.3 Testing a workflow change

A workflow PR runs against the local stack (§16): the harness fires the Doc 06 event payloads (synthetic, from the AU fixtures) at a local n8n, and asserts the outgoing calls — the callback signatures, the rendered template in both languages where the template is patient-facing, and the attachment rule from Doc 06 (statement PDFs travel base64 in the payload; report emails carry the signed link and no PDF). Production workflow activation follows the release (§11.5): import, verify one synthetic event per changed workflow on the operator's own test tenant, then enable.

15. Documentation discipline

15.1 The series is the contract

Docs 01–10 are versioned documents with changelogs, exactly as the series has practised (Doc 02 v1.3, Doc 03 v1.3, Doc 04 v1.1, Doc 07 v1.1, Doc 08 v1.1). A doc's version bumps when its decisions change; a fix pass changes only what it names. Doc 02's special status is process, not courtesy: schema facts are edited in Doc 02 first (§7.1).

15.2 The project changelog

CHANGELOG.md follows Keep a Changelog (F-7) with SemVer release headings (F-6): an Unreleased section maintained in the PR that makes the change (one line under Added / Changed / Fixed / Security, written for a lab owner, not a compiler), cut into a dated version section at each tag (§11.5). Commit history (F-1) is the raw material, never the substitute — the changelog is curated, the log is complete, and they serve different readers.

15.3 Code and docs in one motion

  • A behaviour change without its doc update is an incomplete PR (§11.3). An internal-only change (refactor, perf) that alters no documented behaviour says so in the PR description, which is itself the check.
  • New architectural decisions get an ADR in docs/adr/, continuing Doc 01's ADR numbering, in the same PR that implements them. An ADR records the decision, the alternatives, and the cost accepted — like Doc 08 §15's threat entries, in miniature.
  • Comments in code explain why, and cite the doc rule when the why is a rule (# Doc 05 §7: reversal copies percent_applied, never re-resolves). Comments that restate the code are deleted in review; comments that cite a doc are how the next reader finds the specification.
  • README files exist at repo root and in backend/ and frontend/: how to run it, how to test it, where the docs live. A README that disagrees with §16 is a bug.

"It works on my machine" is not on the list, because §4.4 makes machines interchangeable.

21. What is NOT built in v1

  • No GitFlow — no develop, release or long-lived staging branches (§11.1). Trunk-based only.
  • No split repositories — backend, frontend, workflows and infra stay in the one monorepo (§4.1); no per-module repos, no internal package publishing.
  • No feature-flag platform — incomplete work hides behind existing role checks and tenant settings (§11.1); no flag service, no flag SDK.
  • No staging environment (§4.3) — the question is Doc 10's (OQ-55), the default until then is parity + nightly suites.
  • No remote devcontainers or cloud dev environments — local Compose is the dev environment (§16.1).
  • No mutation testing, no visual-regression service, no performance budget gates — the DG suite and golden-file PDF tests (§5.8) are the v1 quality tooling beyond the scenario suites.
  • No auto-merge bots or automatic dependency merging — dependency PRs are batched and reviewed by a human (§13.2), including the solo developer's own.
  • No code-generation from the docs — the OpenAPI schema is generated from code (§8.3); the docs remain human-written specifications, and drift is caught by review and the §7.5 checks, not by a generator.

22. Interview talking points

  • Why a monorepo for a solo developer? Because the unit of change in this system is cross-cutting: one feature is a migration, an endpoint, a screen, two i18n files and a workflow. Split repos turn that into five coordinated PRs with version skew between them. One repo makes the change atomic, reviewable, and revertible as a unit — and the doc that specifies it rides in the same commit (§4.1, §15.3).
  • Why trunk-based instead of GitFlow? GitFlow's branches exist to stabilise releases for teams shipping versioned software to many environments. LabFlow ships one deployment from one trunk to one VPS (§11.1, §11.5). Long-lived branches would buy ceremony and pay for it in merge divergence — the exact cost F-5's model exists to avoid. Releases are tags; the trunk is always the truth.
  • Why is "the migration must match Doc 02" a merge gate? Because schema-per-tenant multiplies every schema mistake by the number of tenants, and un-multiplies it slowly — per-schema restores, tenant by tenant (§7.3, §17.2). Catching drift in CI costs minutes (§7.5). The rule converts "Doc 02 is the source of truth" from a slogan into something a machine checks.
  • Why a coverage ratchet instead of an 80% target? A fixed target is met by writing tests at the number, including worthless ones. The ratchet (§9.3) only forbids going backwards, and the real gate is scenario coverage: every behaviour Docs 03–08 promised has a named, running test. Lines are a proxy; scenarios are the contract.
  • Why are Conventional Commits worth the fuss for one person? Because history is the project's memory when the team is one person's future self — and the changelog, the scope-based archaeology (git log by module), and the release mechanics all derive from the format mechanically (F-1). The cost is one prefix per commit; the return is that "when did settlements change and why" is a query, not an excavation.
  • Why role-first locators, test IDs second? A getByRole test fails when the accessibility tree breaks — it is an accessibility test smuggled into the functional suite, which matters for Doc 07's WCAG AA baseline. Test IDs are the fallback for what roles cannot name, under a grammar (§10.2) that keeps them stable across the English/Urdu switch — a text-based locator would fail half the product's UI by design.
  • Why does self-review count as review? Honestly labelled, it barely does (§11.4) — which is why the system leans on gates that do not get tired: thirteen CI checks (§12.2), scenario suites by ID, and contract tests for the rules (audit, migrations, i18n) that reviews most often wave through. The checklist self-review is the human layer over an automated floor, and the document says which is which.
  • Why are workflow JSON files in the repo the source of truth for n8n? Because the alternative — workflows edited in a UI, existing only in a running instance — is unreviewable, unversioned configuration holding production behaviour (Doc 06's deliveries). Treating exports as code (§14.1) gives the automation layer the same review, test and rollback story as everything else, and §14.2 keeps the credentials out of the bargain.

23. Glossary

Trunk the single long-lived branch, main, always deployable (§11.1) · Conventional Commit the type(scope): description commit format of F-1 (§11.2) · Squash-merge collapsing a PR branch into one commit on the trunk, titled per §11.2 · Scope (commit) the owning module name in a commit or branch, mirroring the doc modules (§11.2) · Service layer the services.py home of module behaviour, called identically by views, tasks and commands (§5.2) · Drift check CI's proof that models, migrations and Doc 02 still agree (§7.5) · Expand/contract splitting a destructive schema change across two releases — add and backfill, then enforce or drop (§7.3) · Scenario ID a named test case owned by a module doc (T, TN, RS, AU, FE, SE) or by this document (DG) (§9.2) · Ratchet the coverage gate that forbids decrease versus main without fixing an absolute floor (§9.3) · Quarantine the owned, counted, time-boxed exclusion of a flaky test from the gate (§9.5) · Golden file the reference PDF a template must reproduce page-for-page in CI (§5.8) · Test ID a data-testid value under the §10.2 grammar — purpose-named, language-stable, never a styling hook · Gate a CI check whose failure blocks merge (§12.2) · Hotfix branch the short-lived exception of §11.5, cut from a release tag and deleted once the fix reaches main · Proposed anything beyond Docs 01–08 as written — §20 proposes nothing, and records what was considered instead.
