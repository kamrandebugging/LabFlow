1. Purpose, scope, inputs, consistency check

1.1 Purpose

Doc 01 fixed the architecture. Doc 02 fixed the data model. Doc 03 fixed billing behaviour. Doc 04 fixed tenancy. This document fixes the revenue-share module: how a partner earns a share of what patients actually pay, how that share is recorded, how it is settled each month, and how the partner is told.

After reading it, a developer should be able to build this module without inventing rules. Every money rule here is decided. Anything this document needs that Doc 01 or Doc 02 does not have is marked Proposed and listed in §14.

Reports and settlements are different things. One report per sample (Doc 02 §11, OQ-15 resolved) is about report_version: a corrected report is a new version row. Settlement versioning does not exist. A settlement is drafted once. If it is wrong, it is cancelled and re-drafted as a new settlement row. Do not confuse the two.

  • AS-3. All money is PKR. There is one currency and no tax engine in v1 (§15).

3. Design principles

Doc 03's principles P-1 to P-10 govern the lab modules. These govern revenue share. Where they meet, Doc 03's P-1 (patient safety first) still outranks everything.

#PrincipleWhat it means here
RS-1The ledger is the truth.share_ledger_entry rows are facts. They are never updated and never deleted (Doc 02 §6). Everything else — status, totals, statements — is derived from them or snapshotted from them.
RS-2Share follows cash, not paper.Share is computed per payment, on the amount paid — never on the invoice total (Doc 02 §12). A discount, a part payment and a refund all follow from that one choice. No special cases.
RS-3Corrections are new rows.A refund never edits a ledger row. It writes a new negative row. Both rows stay visible. An auditor can replay the whole history.
RS-4One entry per payment.UNIQUE (payment_id) is the idempotency guarantee. A retried task, a double event or a replayed sweep cannot pay a partner twice for the same payment.
RS-5State is derived, not stored, where it can be.A ledger entry has no status column. Its status is read from settlement_line → settlement.status. One fact, one place. Nothing to keep in sync.
RS-6Rules are history.A rule change closes the old row (effective_to) and opens a new one. Past payments keep the percent that was applied to them, stored on the ledger row as percent_applied.
RS-7Money is Decimal, always.Every computation uses Python Decimal. Every stored or printed amount is quantized with Decimal.quantize(Decimal('0.01'), ROUND_HALF_UP). Money crosses the API as a string (Doc 03 §6.1). No float touches money, ever.
RS-8Money is the Owner's surface.Only the Owner manages partners, rules and settlements. Staff who handle patients and samples never see money owed to partners (§4).

5. Referral partners and rules

5.1 Referral partners

Responsibility. One durable record per referring doctor or facility, per tenant. The record holds who the partner is and where the monthly statement goes. Nothing else in the system stores partner identity.

Tables used. referral_partner (Doc 02 §5.8). The table name is fixed. The UI label for the module is tenant-renamable (Doc 01 §7); the table name is not.

referral_partner — fields as used here

name text NOT NULL — the doctor's or facility's name, printed on the statement. · organisation text NULL — clinic or hospital name, printed under the name when present. · phone text NULL — contact number for the lab's own use; never used for statement delivery in v1. · email text NULL — the statement recipient. A partner with no email still gets settlements; delivery fails visibly (§7.7). · is_active boolean NOT NULL DEFAULT true — an inactive partner receives no new patients' attribution in the SPA pickers, but history is untouched. · deleted_at — soft delete (RP-5). · created_at / updated_at.

  • RP-1. Create, read and update are Owner only (§4). name is required. email, when present, must be a valid email address (422 validation_error).
  • RP-2. Setting is_active = false is the normal way to end a relationship. The record stays. The ledger stays. Past settlements stay. The partner simply stops appearing where staff attribute new invoices.
  • RP-3. Attribution happens on the invoice: invoice.referral_partner_id (Doc 02 §5.4). This module does not decide attribution. It consumes it.
  • RP-4. A partner's identity fields may be edited at any time. An edit changes future statements. It never rewrites a stored statement PDF or a ledger row.
  • RP-5. Soft delete sets deleted_at. It is refused while any share_ledger_entry row points at the partner: 409 partner_has_ledger_entries. Ledger rows hold a RESTRICT foreign key to the partner (Doc 02 §5.8), and they are immutable — they can never be re-pointed. So a partner with ledger history can never be deleted, only deactivated (RP-2). Soft delete exists for the case Doc 02 §5.8 names: a duplicate record created in error, before it earned anything, which must be recoverable. The API offers no “reassign ledger entries” action, because the immutable ledger makes reassigning impossible. A duplicate with history is merged by deactivating one record and keeping both histories.
  • RP-6. Every create, update, deactivation and soft delete writes one audit_log row (Doc 02 §13).

5.2 Revenue-share rules

Responsibility. The percent a partner earns, effective-dated, resolvable by partner, branch and test category. Rules are the commercial history of the relationship. They are never rewritten.

revenue_share_rule — fields as used here (Doc 02 §5.8)

referral_partner_id uuid NOT NULL FK → referral_partner(id) RESTRICT. · test_category text NULL — NULL means all categories. · branch_id uuid NULL FK → branch(id) RESTRICT — NULL means all branches. · percent numeric(5,2) NOT NULL, CHECK percent BETWEEN 0 AND 100. · effective_from date NOT NULL. · effective_to date NULL — NULL means still in force. · created_at / updated_at.

  • RR-1. Rules are Owner only (§4). percent outside 0–100 is refused by the database CHECK and by the API (422 validation_error).
  • RR-2. A rule applies on a date d when effective_from <= d and (effective_to IS NULL or d <= effective_to). Both bounds are inclusive. Dates are Asia/Karachi dates.
  • RR-3. Editing a rule never updates percent or effective_from on an existing row. An edit is one transaction: set effective_to on the old row to the day before the new rule starts, then insert a new row. The only update this module ever makes to a rule row is setting effective_to — the supersede Doc 02 §5.8 allows. History stays readable: anyone can answer “what was the percent on 14 March?” from the rows alone.
  • RR-4. There are no retroactive rule edits. A new rule's effective_from may not be earlier than the latest effective_from already in its bucket (RR-6) unless the Owner first closes the later rule. Payments already recorded keep the percent_applied stored on their ledger rows (§6). Nothing recomputes the past.
  • RR-5. The Owner creates the first real rule for each partner. No rule is seeded at tenant provisioning. See §5.4.

5.3 Specificity order and overlap

Several rules can match one payment: one for the branch, one for the category, one general. Resolution must pick exactly one, the same way every time. The order is fixed here. Branch beats category.

RankBucketMatches when
1 — most specific(partner, branch, category)branch_id = the invoice's branch, and test_category = the invoice's category
2(partner, branch, NULL)branch_id = the invoice's branch, test_category IS NULL
3(partner, NULL, category)branch_id IS NULL, test_category = the invoice's category
4 — least specific(partner, NULL, NULL)Both NULL — the partner's general rate

Why branch beats category. A branch deal is made with the people at that branch, for patients served at that branch. It is the more deliberate agreement. A category is a property of a test; it varies line by line. When both exist, the branch agreement is the one the Owner negotiated for that place, so it wins.

  • RR-6. A specificity bucket is one exact triple: same referral_partner_id, same branch_id (NULL counts as a value), same test_category (NULL counts as a value).
  • RR-7. Overlap inside one bucket is rejected at save time. If a new or closing rule would make two rules in the same bucket apply on the same date, the API returns 422 rule_overlap and writes nothing. Resolution is then deterministic by construction: inside a bucket, at most one rule applies on any date.
  • RR-8. Overlap across different buckets is allowed and expected. Precedence (§5.3 table) resolves it. That is what the buckets are for.
  • RR-9. The branch used in resolution is invoice.branch_id — the branch that billed the patient. Not the branch that processed the sample. Money follows billing.
  • RR-10. Category matching is all-or-nothing per invoice. One ledger entry is written per payment, so one percent must apply to the whole payment (Doc 02 §12). A category-specific rule matches only when every invoice_item on the invoice is in that one category. A mixed-category invoice matches only NULL-category rules (buckets 2 and 4). Splitting one payment across categories would need one entry per item. v1 does not do that (§15).

5.4 When no rule matches: the 0% fallback

This is stated plainly because an earlier design got it wrong. No 0% rule row is seeded at tenant provisioning. The seed was impossible: revenue_share_rule.referral_partner_id is NOT NULL, and no partner exists at provisioning time (A-10, accepted in Doc 02 v1.3; Doc 02 §5.8, §16).

Instead, the fallback lives in resolution:

  • RR-11. If no rule in any bucket applies on the payment date — including the case where the partner has no rules at all — resolution returns percent = 0. Resolution never errors. It never blocks a payment. A patient can always pay.
  • RR-12. A 0% resolution writes no ledger row. The zero-amount rule in §6.6 covers it: the computed amount is 0.00, and 0.00 rows are skipped. The payment row itself is the complete record — the patient paid, the partner earned nothing, and no rule said otherwise.
  • RR-13. This is safe to rely on. A partner created today, with a rule starting next month, earns nothing this month and the correct percent next month. No back-filling is needed or allowed (RR-4).

6. Share ledger

6.1 What the ledger is

The ledger is the list of money facts: this partner earned this much from this payment. One row per payment. Rows are written once and never change. Doc 02 §5.8 defines the table. Doc 02 §6 enforces it: UPDATE and DELETE on share_ledger_entry are revoked from the application role. Application code that tries either one gets a database error. That error is the safety net, not the design.

share_ledger_entry — fields as written here (Doc 02 §5.8)

payment_id uuid NOT NULL FK → payment(id) RESTRICT, UNIQUE (uq_share_ledger_entry_payment_id). · referral_partner_id uuid NOT NULL FK → referral_partner(id) RESTRICT — copied from the invoice. · rule_id uuid NULL FK → revenue_share_rule(id) RESTRICT — the rule that was applied; NULL when no rule matched (0% fallback, §5.4) or, for a reversal, when the original predates rules. · amount numeric(12,2) NOT NULL — negative means a compensating (reversal) entry. · percent_applied numeric(5,2) NOT NULL — the percent used, copied onto the row so history survives later rule changes. · basis_amount numeric(12,2) NOT NULL — the payment amount the share was computed on. · period text NOT NULL — YYYY-MM, Asia/Karachi (§6.5). · created_at only — there is no updated_at, because nothing ever updates.

  • SL-1. The formula is Doc 02 §12, fixed: amount = payment.amount × rule.percent / 100, in Python Decimal, then .quantize(Decimal('0.01'), ROUND_HALF_UP). percent_applied stores the percent used. basis_amount stores payment.amount.
  • SL-2. Walk-in: if invoice.referral_partner_id IS NULL, no ledger row is created. There is no partner to pay. The payment stands alone.
  • SL-3. Discounts need no ledger row and no special handling. The basis is the paid amount (RS-2). A discount reduces what the patient pays. The share follows the smaller amount on its own.
  • SL-4. Partial payments need no special handling. Each payment writes its own row. Two part payments write two rows.

6.2 Creation: synchronous, in the payment transaction

Decision: the ledger row is written synchronously, in the same database transaction as the payment insert. Doc 01 §12 Flow C shows the same shape: the payment request inserts the payment, resolves the rule, and inserts the ledger entry.

Why not async. A payment without its ledger row is silent money loss. Nobody sees an error. The partner is simply underpaid, and the lab finds out weeks later, if ever. An async design creates exactly that risk: if the queue message is lost, the payment stands and the share does not. The write is one extra insert in a transaction that already exists. It costs almost nothing. Synchronous removes the whole failure class. The UNIQUE constraint on payment_id is still kept — as the backstop for retries and replays (§6.4), not as the mechanism.

6.4 Idempotency and the reconciliation sweep

  • SL-5. UNIQUE (payment_id) means a retried call cannot double-pay. The consumer inserts with conflict handling on payment_id: a second call for the same payment finds the row and does nothing. It returns the existing row. It never raises for a duplicate.
  • SL-6. Defence in depth: an hourly Beat sweep, partners.reconcile_missing_ledger_entries, scans for partner-attributed payments with no ledger row and replays record_share_entry() for each. In a correct system it finds none. It exists for the day a deploy, a restore or a bug breaks that. Because the consumer is idempotent and uses the same zero-amount rule (§6.6), a replay is a no-op for payments that were correctly skipped — the sweep does not retry them forever.
  • SL-7. The sweep runs per tenant, through the normal per-tenant fan-out (Doc 04 §13.2). Its count of repaired rows is a metric and an alert (§12.7). A non-zero count is a bug report, not a routine event.

6.5 Refund reversal: the compensating entry

A refund is a new payment row with kind = refund and a positive amount; kind supplies the sign in every sum (Doc 02 §5.4, §12). Its ledger entry is a new negative row. The original row is never edited. There is no REVERSED status — an entry's status is derived (§6.7), and a reversal is just another entry with a negative amount.

  • SL-8. The reversal copies percent_applied and rule_id from the original payment's ledger entry. It never re-resolves the rules. Rules may have changed since the original payment. The refund must reverse the share that was actually given, at the percent that was actually applied — not today's percent.
  • SL-9. Reversal amount: amount = −(refund.amount × percent_applied / 100), Decimal, quantized to 0.01, ROUND_HALF_UP. basis_amount = refund.amount. referral_partner_id = the original entry's partner.
  • SL-10. If the original payment produced no ledger row — walk-in, 0% resolution, or a zero-amount skip — the refund produces no row. There is nothing to reverse.
  • SL-11. The reversal's period is decided by the original entry's state, exactly:
    — If the original entry's period is closed — the entry sits on a settlement with status IN ('APPROVED','SENT','PAID') — the reversal's period is the refund payment's own YYYY-MM: the current open period. The historical period is never reopened.
    — If the original entry's period already has a live settlement in any other state (a DRAFT exists for it), the reversal also takes the refund payment's YYYY-MM. A drafted settlement is a snapshot (§7); the reversal joins the next cycle, not the snapshot.
    — Otherwise — the original entry is still pending and no live settlement exists for its period — the reversal's period is the original period. Reversal and original then settle together and net to the right figure in one statement.
  • SL-12. A partial refund reverses partially, by the same formula. Two partial refunds write two negative rows. The sum of reversals can never exceed the original entry, because Doc 03 BL-7 already caps cumulative refunds at cumulative payments (422 refund_exceeds_payments) before this module runs.

6.6 Rounding and the zero-amount rule

All arithmetic is Decimal, quantized to 0.01 with ROUND_HALF_UP (RS-7). Worked cases:

  • SL-13. Zero-amount entries are skipped. If the quantized amount is 0.00, no row is written. This rule applies with equal weight to payments and to refunds. Reason: a 0.00 row carries no money and no information the payment row does not already carry. Writing it would add a settlement_line and a printed line to a partner's statement that says the partner earned nothing from a payment — noise on a financial document. The payment row remains the audit record. The reconciliation sweep (SL-6) uses the same computation, so a skipped payment is recognised as correctly skipped, not missing.
  • SL-14. Skipping is not losing. Any reader who needs to prove a payment earned nothing resolves the rule for that payment date and gets 0% or a sub-paisa amount. The inputs — the payment row and the rule rows — are all still stored.

6.7 Derived status

An entry's status is never stored. It is read from settlement_line and the settlement that line belongs to (Doc 02 §5.8):

Derived statusCondition
pendingNo settlement_line on a live settlement points at the entry. Includes: no line at all, and a line only on a CANCELLED settlement.
in-draftA line on a settlement with status = 'DRAFT'.
settledA line on a settlement with status IN ('APPROVED','SENT','PAID').

A line on a CANCELLED settlement does not count. The entry is pending again and can be picked up by a re-draft (§7.6). Note the database fact behind the middle row set: settlement_line.share_ledger_entry_id is UNIQUE, so an entry has at most one line in total. “Live” is a read-time judgement on that line's settlement, not a second line.

7. Monthly settlement

7.1 What a settlement is

One partner, one calendar month, one document. A settlement row gathers the partner's pending ledger entries for a period into settlement_line rows, states their total, and carries the statement the partner receives. A settlement is all-or-nothing per partner per period: it includes every pending entry for that period, or it does not exist. There is no partial settlement in v1 (§15).

settlement — fields as used here (Doc 02 §5.8)

referral_partner_id uuid NOT NULL FK RESTRICT. · period text NOT NULL, CHECK period ~ '^\d{4}-\d{2}$' — YYYY-MM, Asia/Karachi. · status text NOT NULL DEFAULT 'DRAFT', CHECK DRAFT | APPROVED | SENT | PAID | CANCELLED. · total numeric(12,2) NOT NULL DEFAULT 0 — the Decimal sum of its lines' amount values, set at draft time and never recomputed after (§7.4). · statement_pdf_key text NULL — settlements/{partner_id}/{period}.pdf (Doc 02 §9), set by the finalize task. · approved_by uuid NULL FK → staff_user(id) RESTRICT. · approved_at timestamptz NULL. · created_at / updated_at.

settlement_line — fields as used here (Doc 02 §5.8)

settlement_id uuid NOT NULL FK RESTRICT. · share_ledger_entry_id uuid NOT NULL FK RESTRICT, UNIQUE — an entry appears in exactly one settlement. · amount numeric(12,2) NOT NULL — a snapshot of the entry's amount at draft time. · created_at only. Lines are never updated by the application. A re-draft cancels the old settlement and creates a new one (§7.6).

7.2 Generation: the monthly draft

  • ST-1. On the 1st of each month at 01:00 Asia/Karachi, Celery Beat enqueues referral_partners.generate_monthly_settlements (Doc 01 §13 schedule; Doc 02 §12). Beat is a single scheduler (F-7). It never loops over tenant schemas.
  • ST-2. Fan-out follows Doc 04 §13.2 (TP-5): the parent task enqueues one child task per tenant. Inside a tenant, generation enqueues one draft task per partner with pending entries. One tenant's failure cannot abort the rest. One partner's failure cannot abort the tenant's other partners (§12).
  • ST-3. The draft task for one partner selects that partner's ledger entries for the previous calendar month whose derived status is pending (§6.7) — entries with no line on a live settlement. Late entries and reversals that carry an older entry's period are selected by that stored period value (§12.5).
  • ST-4. It inserts one settlement row with status = 'DRAFT', one settlement_line per selected entry with amount copied from the entry, and sets settlement.total to the Decimal sum of the line amounts. The insert runs in one transaction per partner.
  • ST-5. A partner with no pending entries for the period gets no settlement. No empty DRAFT. No empty statement. Silence means nothing was earned, and that is correct.
  • ST-6. A settlement whose total is negative is still drafted. It happens when a month holds more reversals than earnings. The total is shown as a negative figure on the statement (§8). The Owner decides what to do; the system does not hide it or clamp it to zero.
  • ST-7. Generation is idempotent. Re-running it for the same period is a no-op for a partner who already has a live settlement for that period — the partial unique index uq_settlement_partner_id_period refuses a second live row, and the task treats that refusal as “already drafted”. Where no live settlement exists, a re-run picks up only the entries that are still pending.
  • ST-8. When drafting completes for a tenant, the Owner is notified that drafts are ready for review. The notification uses the existing notification pattern (Doc 02 §5.9). The exact n8n workflow is Doc 06's (OQ-42).

7.4 Approval and the finalize task

  • ST-9. The Owner reviews a DRAFT in the SPA: the lines, the total, the partner. Approval is POST /api/v1/settlements/{id}/approve with an If-Match header (§12.2). Only a DRAFT can be approved; anything else returns 409 invalid_state_transition.
  • ST-10. Approval sets status = 'APPROVED', approved_by and approved_at, writes one audit_log row, and enqueues the finalize task, referral_partners.finalize_settlement, on the referral_partners queue (Doc 01 §13). The API call does not render the PDF itself.
  • ST-11. The finalize task renders the statement PDF (§8), stores it at settlements/{partner_id}/{period}.pdf under the tenant's storage prefix (Doc 04 §13.4), sets statement_pdf_key, records the template version (A-18 interim, §8.4), and only then fires the “settlement approved” webhook that delivers the statement (§9). The order matters and matches Doc 02 §12: PDF first, webhook second. A webhook never points at a PDF that does not exist.
  • ST-12. settlement.total is not recomputed at approval. The number the Owner approved is the number on the PDF is the number in total. If a line is wrong, the Owner cancels and re-drafts (§7.6). Approval never silently adjusts a figure.

7.5 PAID: confirming the partner was paid

  • ST-13. LabFlow does not pay partners. The Owner pays outside the system, then confirms it: POST /api/v1/settlements/{id}/mark-paid, Owner only, allowed only from SENT (409 invalid_state_transition otherwise).
  • ST-14. The request body carries one field, { "reference": "..." } — the bank reference, or “cash” with a note. Doc 02 v1.3 has no column for who confirmed payment or when, and this document does not invent one. The reference, the actor and the time are recorded in the audit_log row the action writes (Doc 02 §13). updated_at on the settlement row also moves, as it does for every status change. If a stored paid-by/paid-at pair is wanted later, it needs a Proposed amendment to Doc 02 first.
  • ST-15. PAID is terminal for the money flow. It changes nothing in the ledger. The entries were already settled from APPROVED onward.

7.6 Cancellation and re-draft

  • ST-16. Only a DRAFT can be cancelled. Cancelling an APPROVED, SENT or PAID settlement returns 422 settlement_not_cancellable. Money already promised or paid is not un-promised by a button. An error after approval is corrected in the next period, by compensating entries — the same rule as the ledger itself (RS-3).
  • ST-17. Cancellation sets status = 'CANCELLED' and writes one audit_log row. Nothing else is written. The settlement_line rows stay on the cancelled settlement — they are the record of what the draft contained. The share_ledger_entry rows never change.
  • ST-18. Because a line on a CANCELLED settlement does not count (§6.7), the entries are pending again at once. No cleanup task runs. Nothing is deleted.
  • ST-19. Re-draft is a new generation run for that partner and period (Owner-triggered from the SPA, or the next scheduled logic that finds them pending). It inserts a new settlement row. The partial unique index allows this precisely because the old row is CANCELLED (F-6). The new draft picks up the same entries, plus any that arrived since (§12.5).

7.7 Partners with no email

  • ST-20. referral_partner.email is nullable. A partner with no email still gets settlements drafted normally. Money owed does not depend on an inbox.
  • ST-21. At delivery, the finalize flow records a notification row with status = 'FAILED' and last_error = 'partner_email_missing'. The settlement stays APPROVED — approval is real; only the sending failed. The Owner sees the failure on the settlement and on the dashboard, and can download the statement and hand it over by any other means. Adding the email later and re-sending (§9) completes the flow normally.

8. Statement PDF specification

8.1 What the statement is — and is not

The statement is a settlement statement: “this is what you earned from this lab in this month, line by line.” It is not a legal invoice and it is not a tax document. It creates no tax obligation and settles no tax question. That sentence is printed on the document itself (§8.2, footer) so a partner who asks gets the answer from the paper, not from a phone call.

Language: English only. The statement uses the en row of the settlement_ready notification template (Doc 02 §5.9). An ur row exists in the schema. It is not used for statements in v1. The reason is plain: the reader is a doctor or a facility's accounts person, reading a professional financial document. Patient-facing Urdu exists because patients need it (Doc 03 §9.2). Partners read English professional documents, and one language keeps one canonical figure set — a bilingual financial statement invites “which total is right?” disputes that help nobody. The email that carries the statement is likewise the en template.

8.3 Rendering rules

  • PDF-1. Rendering reuses Doc 03 §9's WeasyPrint approach in full: the same installed fonts, block layout and tables only, @page margin boxes for the running footer, CSS counters for “Page X of Y”, no JavaScript, no web fonts loaded at render time, no external images. Deterministic render: the same settlement renders the same bytes-shaped document every time.
  • PDF-2. The lines table header repeats on every page (thead), and a line never splits across pages (break-inside: avoid) — the same rules as the report results table (Doc 03 §9.5).
  • PDF-3. Rendering runs in the finalize task on the referral_partners queue, under Doc 01 §13's retry policy. A render exception fails the task cleanly. No partial PDF object is kept (Doc 03 §9.5's rule, applied here too). The settlement stays APPROVED with statement_pdf_key still NULL, which is the visible, retryable state (§12.3).
  • PDF-4. Amounts print from the stored Decimal values with 2 decimals. The template never recomputes a figure. Printed total = settlement.total = sum of the stored line amounts, by construction at draft time (ST-4).

8.4 Template version

When the statement template changes, support needs to know which template produced a stored statement. settlement has no column for that in Doc 02 v1.3. A-18 (Proposed, §14) adds settlement.template_version. Until it is accepted, the interim behaviour is: the template version is written into the PDF's document metadata and into the audit_log row written at approval. A re-render always uses the current template. This mirrors Doc 03's still-Proposed A-6 for report_version — the same gap, the same interim answer.

9. Delivery

  • DL-1. Delivery is by email only in v1. The statement PDF is attached to the email. The channel is the partner's email (ST-20 covers a missing one).
  • DL-2. The path is Doc 01 §13's signed webhook protocol, unchanged: Django writes a webhook_delivery row and emits the event with payload {event, tenant_slug, callback_url, idempotency_key, timestamp, data}, signed with HMAC-SHA256. n8n verifies the signature, rejects timestamps older than 5 minutes, de-duplicates on the idempotency key, sends the email, and calls back. The callback lands on the tenant's own subdomain, and the body's tenant_slug must match the resolved tenant. Doc 06 owns the workflow internals (OQ-42).
  • DL-3. The delivery itself is tracked as a notification row (Doc 02 §5.9): template_key = 'settlement_ready', recipient_type = 'partner', recipient_id = the partner's ID, channel = 'email', status starting at PENDING, with a UNIQUE idempotency_key per settlement delivery attempt series. On the success callback the row becomes SENT and the settlement moves APPROVED → SENT (ST, §7.3). The settlement status is set by the callback, never assumed at send time.
  • DL-4. No WhatsApp for statements in v1. A statement is a financial document. It needs the PDF attached and a delivery record the lab can point to. WhatsApp in v1 is a staff-clicked wa.me link with no receipts and no unattended sending (Doc 01 §13). That channel is wrong for money documents, and a doctor's personal WhatsApp is not the lab's filing system. The settlement_ready template's WhatsApp channel rows are not used in v1.
  • DL-5. Failed deliveries retry on the notification pattern: attempts and next_attempt_at on the row, and the 15-minute Beat sweep that retries failed deliveries (Doc 01 §13). Retry counts and backoff follow the notifications queue policy in Doc 01 §13 (5 retries, 30 s to 30 min). When retries are exhausted the row stays FAILED with last_error set, Sentry alerts, and the settlement shows the failure to the Owner. The settlement stays APPROVED. A delivery failure never un-approves money.
  • DL-6. The Owner can re-send manually from the SPA: POST /api/v1/settlements/{id}/send (§10). A re-send creates a fresh notification row — the failed row stays as the record of the failure. Re-send is allowed only when the settlement is APPROVED or SENT (§10). Re-sending a SENT settlement sends a second copy, labelled as a copy in the email subject by the template. That is deliberate: partners lose email.
  • DL-7. Staff can always download the statement directly: GET /api/v1/settlements/{id}/statement.pdf (§10). Delivery trouble never locks the lab out of its own document.

10. API reference

10.1 Conventions

Doc 03 §6.1 applies in full and is not repeated: base path /api/v1, tenant resolved from the host, cursor pagination (cursor, limit default 50, max 200; response { "results": [...], "next_cursor": ... }), application/problem+json errors with a machine-stable code, money as strings with 2 decimals, and no tenant identifier in any path or body. Role codes are §4's. The conventions specific to this module:

  • AP-1. Every endpoint in this section enforces §4's matrix in the API. A role with “—” gets 403 forbidden. This includes list endpoints: a Receptionist does not get an empty settlement list. She gets a refusal.
  • AP-2. Mutating settlement actions (approve, cancel, mark-paid) require an If-Match header carrying the settlement's current version token (its updated_at-derived ETag, per Doc 03 §6.1's versioning convention). A stale token returns 409 version_conflict (§12.2).
  • AP-3. Error codes introduced here: rule_overlap (422), partner_has_ledger_entries (409), settlement_not_cancellable (422), partner_email_missing (422, on send), owner_approval_required (403, refund ceiling — §13, OQ-31; the refund endpoint itself is Doc 03 §6.4's and is not redefined here). Standard codes from Doc 03 §6.1 apply unchanged: validation_error (422), not_found (404), forbidden (403), invalid_state_transition (409), version_conflict (409), subscription_read_only (403, Doc 04 §11.2).
  • AP-4. All list ordering is created_at DESC, id DESC unless an endpoint says otherwise. The ledger list orders by created_at DESC; settlement lines inside a settlement detail order by the entry's payment date, then entry created_at.

12. Concurrency, failure handling, observability, test plan

Every case below was chosen by asking: “what does the retry, the second click, or the crash leave behind?” The answer must always be a consistent state a human can see and fix.

12.1 Double payment event

The same billing.payment_recorded event is delivered twice — a retry, a replay, the reconciliation sweep racing a slow request. The consumer is idempotent on payment_id (SL-5): the second call finds the existing row through UNIQUE (payment_id) and does nothing. One payment can never produce two rows, so a partner can never be paid twice for it. The sweep (§6.4) depends on this property to be safe.

12.2 Two Owners approve at once

Approve, cancel and mark-paid require If-Match (AP-2). Two Owners open the same DRAFT. Both submit. The first request updates the row; its version token changes. The second request's token is stale and returns 409 version_conflict, with the settlement's current state in the response. The Owner reloads and sees what actually happened. A double approval can therefore never enqueue two finalize tasks for two different decisions. The finalize task is also idempotent: if it runs twice, the second run finds statement_pdf_key already set to the same key and the PDF already stored, and the delivery webhook carries the same idempotency key, which n8n de-duplicates (DL-2).

12.3 PDF render failure

The finalize task renders under Doc 01 §13's policy for its queue (the referral_partners queue: 3 retries, backoff). A render exception fails the task cleanly and keeps no partial PDF (PDF-3). The settlement stays APPROVED with statement_pdf_key NULL. That pair — approved, no PDF — is the visible retryable state. It shows on the settlement list. When retries exhaust, Sentry alerts (Doc 01 §13) and the Owner's re-send is not the fix; support re-runs the finalize task, which is idempotent (§12.2). The approval is never rolled back: the lab did approve the number.

12.4 Email delivery failure

Covered by DL-5 and workflow 6: the notification row carries attempts, next_attempt_at and last_error; the 15-minute Beat sweep retries; exhaustion leaves a FAILED row and an alert; the Owner re-sends by hand (DL-6) or downloads the statement (DL-7). The settlement stays APPROVED throughout. Delivery state and money state are separate, on purpose.

12.5 Late-arriving entries

A payment can be recorded late for a period that has already been drafted or settled — a back-office correction, a restored record, a reversal under SL-11. The rule is fixed:

  • CF-1. An entry never joins a settlement that already exists. A settlement is a snapshot taken at draft time (ST-4). Its lines and total never change after drafting.
  • CF-2. If the entry's period settlement is still DRAFT: the entry stays pending. It is counted in the dashboard's late_entries (§10) so the Owner can see it before approving. It joins only if the Owner cancels that draft and re-drafts (§7.6), which picks it up with the rest. The Owner chooses. The system does not silently grow an open draft either — that would change a total the Owner may already be reviewing.
  • CF-3. If the entry's period is already closed (APPROVED, SENT or PAID): the entry stays pending until the next monthly generation. Generation selects by derived status pending, so the entry is picked up as a line on that partner's current-period settlement — alongside that month's own entries, keeping its own stored period value. The statement shows that period on the line (§8.2), and the two-period statement prints subtotals (§8.2). The partner can see exactly which item is late and which month it belongs to.
  • CF-4. Selection detail, so generation cannot miss these: the draft task selects entries whose derived status is pending and whose stored period is the target month, plus any still-pending entries from earlier periods whose period settlement is closed. Those older entries are written as lines on the new settlement. Their rows keep their original period — a line's period is the entry's fact, not the settlement's.

12.6 Approval when an entry's original period is closed

This is the normal refund case, not an edge case. A settlement in front of the Owner may hold a reversal whose original entry settled two months ago (workflow 3). Approval acts on the settlement in front of the Owner — its lines, its total. Historical settlements are never reopened, never edited, never re-totalled. Their PDFs stay as issued. The compensating entry in the current settlement is the whole correction. That is the reversing-entry pattern of F-3, applied end to end.

12.7 Beat crash mid-fan-out

Generation fans out per tenant, then per partner (ST-2, Doc 04 TP-5). If the parent task or a worker dies mid-fan-out, some partners have drafts and some do not. Nothing is half-written: each partner's draft is one transaction (ST-4). Recovery is “run generation again”. For partners already drafted, the partial unique index makes the re-run a no-op (ST-7). For the rest, the re-run drafts normally. There is no fan-out progress table and no resume logic. Idempotency is the resume logic. The same holds inside delivery: a crash between storing the PDF and firing the webhook leaves APPROVED with statement_pdf_key set and no notification row — the finalize re-run detects that exact state and fires the webhook (§12.3).

16. Interview talking points

Why is the ledger append-only, with no status column? Because a status column would be a second copy of a fact that already lives in one place. Whether an entry is settled is fully determined by settlement_line and its settlement's status. Storing it twice invites the two copies to disagree — and in a money system, the disagreement is always found by the person you owe. Deriving it costs one join. It can never be stale, because there is nothing to update. And revoking UPDATE outright (Doc 02 §6) means even a buggy deploy cannot rewrite history; the database refuses.

Why one entry per payment, instead of one per invoice? Because share follows cash (RS-2). Patients pay in parts, late, and sometimes not at all. An invoice-total entry would pay the partner for money the lab has not received, then need corrections when the balance never arrives. Per-payment entries make part payments, discounts and refunds fall out of one rule with no special cases — and UNIQUE (payment_id) turns that rule into an idempotency guarantee for free.

Why compensating negative entries instead of editing the original row? Because the original row was true when it was written: that payment did happen, at that percent. A refund is a second true event, later. Accounting has known the pattern for a long time (F-3): you reverse with a new entry and keep both. Editing the original would falsify the record of the month it belonged to — a month whose statement the partner may already hold.

Why does settlement membership live in settlement_line, not on the ledger row? A settlement_id column on the ledger would make the ledger mutable — every draft, cancel and re-draft would update ledger rows. That breaks immutability for a bookkeeping convenience. The line table holds membership, a snapshot amount, and nothing else. Cancelling a settlement then touches only settlement tables. The ledger never moves. That separation is what makes “the ledger rows never change” a provable sentence instead of a promise.

Why does a refund reversal land in the current open period, not the original one? Because the original period is closed: its settlement is approved, its PDF is issued, the partner has it. Rewriting it would make the partner's copy wrong. Putting the reversal in the current period keeps every issued document true forever, and the correction appears once, visibly, in the next statement. This is Doc 02 §12's rule. It is also how accountants treat closed periods (F-3).

Why skip zero-amount entries instead of writing them for audit completeness? Because the audit record of a zero-share payment already exists: the payment row, plus the rule rows that resolve to 0% for it. A 0.00 ledger row adds a line to a partner's financial statement that says “you earned nothing from this” — noise that erodes trust in every other line. The skip rule is deterministic and the reconciliation sweep applies the same computation, so “skipped” and “missing” are always distinguishable (§6.6). Audit completeness comes from inputs being preserved, not from storing derived zeros.

Why synchronous ledger writes, when the rest of the system loves queues? Because the failure modes are asymmetric. A queued report PDF that fails is visible and retryable. A lost ledger write is invisible: no error, no queue depth, just a partner underpaid. The insert is one row inside a transaction that already exists, so synchronous costs almost nothing and deletes an entire failure class. The hourly reconciliation sweep then exists purely as a tripwire — it should find zero rows, forever (SL-6).

Why does settlement generation keep running when a tenant stops paying? Because the debt belongs to the lab, but the partners did nothing wrong (OQ-36). Generation is the platform keeping an exact record of a third party's money. If it paused, the record would silently rot, and the lab's first day back would start with wrong figures. Delivery pausing is different: email is a service the subscription buys, and read-only mode (Doc 04 §11.2) already defines it as stopped. Compute the truth always. Send the email when the account is live. That split is the whole answer.
